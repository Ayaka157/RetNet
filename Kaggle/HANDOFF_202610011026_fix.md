## 1. 这个项目在做什么

从头训练/继续训练一个 **RetNet 语言模型**，最终目标是角色扮演（RP）对话模型。

| 项 | 值 |
| --- | --- |
| 模型 | RetNet causal LM，**272M** 参数（`retnet_272m_rp`） |
| 架构 | d_model=1024, 20 层, 16 heads, key_dim=64, value_dim=2048, ffn_dim=2048 |
| 词表 | 20000（自训练 BPE） |
| 特殊设计 | `use_gla=true`（decay 门控可学习）、`use_growth_ln=true` + `growth_old_dim=768`（768→1024 宽度生长，函数保持式初始化）、`embed_scale=sqrt(1024)` |
| 训练模式 | `chunkwise`（RetNet 论文式 (7)：chunk 内并行 + chunk 间递推） |
| 上下文 | **8192** token，chunk_size=64 → 每序列 128 个 chunk |
| 硬件 | **Kaggle TPU v5e-8**（8 core，PJRT，data parallel，PyTorch/XLA） |
| 全局 batch | 4/device × 8 core = 32 序列 = **262,144 token/step** |
| 计划步数 | 30,000 步（≈ 7.86 G token） |
| 优化 | AdamW lr=1.1e-4 → 1.1e-5，warmup 300，cosine；wd=0.1（1 维参数为 0）；clip=1.0 |
| 精度 | `XLA_USE_BF16=1` + 参数 bf16，但 **decay 门控 / norm / loss 保持 fp32**（手动混合精度） |
| 检查点 | 每 500 步（同时 eval），只保留最近 3 个；训练结束导出 HF `safetensors` |

### 训练数据（chat_pack_v11）

v10（512 宽）重打包成 8193 宽窗口的 8K 数据：

| 项 | 值 |
| --- | --- |
| `train.ids.npy` | 54,015 行 × 8193（int16），**442.5 M token** |
| `val.ids.npy` | 约 0.68 M token |
| 构成 | reply 265.2 M / prompt 144.5 M / plain 32.9 M token |
| 1 epoch | 442.5e6 / 262144 ≈ **1,688 步** |
| 30,000 步 | ≈ **17.8 epoch** |

loss 是 **wcode 加权交叉熵**：`wcode` 0=pad（权重 0）、1=reply（1.0）、2=prompt（0.1）、3=plain（1.0）。

### 训练进度（重要）

- **目前没有任何有效训练产出。** 所有历史 TPU 运行都在 step 1 左右就崩了，`/kaggle/working` 里从未写出过一个可用 checkpoint。
- 目标 checkpoint `checkpoints/retnet_97m_wikitext103/`、`retnet_23m/` 是更早的小模型，与本次 272M·8K 计划无关。
- 因此这次修好后是**实质上的第一次正式开跑**。

### 历史踩坑链（别重复走）

按 `Kaggle/archived/FixThis/RetNet_TPU_修复分析报告.md`：

1. `torch.autocast("xla")` 与 `torch_xla.experimental.scan` 的两条 trace 通道 dtype 不一致 → `INVALID_ARGUMENT: f32 vs bf16`。
2. **`torch_xla.experimental.scan` 在此栈上不可用**（上游 #7839/#8913 类问题，While loop 形参 dtype/顺序错乱）→ 改成**普通 Python chunk 循环**（当前版本已如此，数学等价）。
3. `torch.utils.checkpoint` 在 XLA 上不可用（torch 2.7 无 `torch.xla` 模块）→ 改用 `torch_xla.utils.checkpoint.checkpoint`。
4. bf16 会把 `gamma` 衰减谱塌缩（16 个头里 12 个变成 1.0）→ decay 门控全程 fp32。

**结论：不要改回 scan，不要用 `torch.utils.checkpoint`。**

### 2.1 致命：学习到的 decay 门控 > 1 会让 8K 训练直接 NaN

| # | 位置 | 问题 | 修复 | 触发条件 | 证据 |
| --- | --- | --- | --- | --- | --- |
| **F-GATE** | `train_worker`（新增 `GAMMA_MAX` 钳位） | 权重里 `blocks.12.msr.gamma[10] = 1.0117193`（320 个门控里唯一 >1 的，26 个 >0.99）。chunkwise 状态每 chunk 乘 `gamma**64`，128 个 chunk 就是 `gamma**8192 = 2.83e41`，远超 bf16 上限 3.39e38 | 载入时 +**每步 optimizer 之后**把门控钳到 `GAMMA_MAX = 1 - 1e-6`，并在日志里报告钳位次数 | **本身就是这次要跑的配置**，step 1 即 NaN | 用真实 gamma 跑 notebook 自己的 `_chunkwise_retention`：seq=1024 干净、seq=4096 max 1.2e20、**seq=8192 输出 48896 个 NaN / 1527 个 Inf**；钳位后 seq=8192 max 0.127、0 NaN 0 Inf |
| F-CAST | `train_worker` | `model.to(dtype=bfloat16)` 会把 fp32 的 `gamma` **和 `inv_freq`** 一起转成 bf16，数值精度当场丢失；事后 `.to(float32)` 只能改 dtype，**改不回数值** | 转换**之前**快照 fp32 原值，转换后用 `.data = master.to(dtype=float32)` 换回（注意 `copy_` 会按目标 dtype 回写，等于没修） | 一直生效，静默损坏 | 对真实权重实测：0/20 门控可还原；4 个头合并成同一个值（0.8862733/…768/…786/…795 → 0.88671875）；`gamma**64` 相对误差最大 1.37e-01。修复后 40/40 张量按位还原 |
| F-INVFREQ | `MultiScaleRetention.__init__` | `inv_freq` 是 **non-persistent buffer**，不进 state_dict，但 `model.to(dtype=...)` 同样会转它 | `inv_freq` 注册为 fp32，并纳入上面的快照-还原 | 一直生效 | 独立验证：`.to(bfloat16)` 确实会转 non-persistent buffer；bf16 频率在 8192 处累积相位误差可达 9.9 rad |
| F-ROT | `_rotations` | 把 **compute dtype（bf16）** 直接传给 `torch.arange` 算旋转位置 | 位置/频率全程 fp32，末端 cast | 一直生效 | bf16 位置 7296/8192 不精确、最大误差 31.0；端到端 `max\|sin−sin(fp32)\|` 从 **2.000** 降到 **1.953e-03** |

> 关于 F-GATE 为什么必须改：这是**本轮训练跑不出结果的头号原因**。即使把崩溃修好，step 1 的 loss 也会是 NaN，存下来的 checkpoint 全是垃圾。
> 钳位把门控从 1.0117193 修到 0.9999990，只影响这 1 个头，其余 319 个不动。

### 2.3 被证伪的候选（不要再"修"一遍）

| 候选 | 为什么是错的 |
| --- | --- |
| `world_size` 只在 master 分支绑定 → rank 1..7 NameError | **错**。cell 4 line 764（缩进 4）就在函数作用域绑定，在 master 分支之前。模拟 rank=1/8 跑原始代码不报错；崩溃日志里 8 条 mark_step 也证明 8 个 rank 都过了这一行 |

| `_chunkwise_retention` 没接收 `g`，所以 GLA 门控是死的 | **错**。`g` 是输出门控；GLA 的 decay 门控是 `gamma` |
| `_chunkwise_retention` 不是 RetNet 式 (7) / 与参考实现不一致 | **错**。与显式递推在 fp64 下差 7.1e-14；与本仓参考实现逐位一致（rel = 0.0） |

| 需要给 checkpoint 的 `_xla_checkpoint` 打补丁 | **错**。r2.7 源码逐行核对：非张量参数、tuple 输出、零 grad_output 均正常 |

### 2.4 已知但**本次不改**的设计遗留（会影响推理，不影响训练）

`_parallel_retention`（**只被 `generate()` 用来预填 prompt**）多了一步参考实现没有的分数归一化：

```python
scores = scores / scores.detach().abs().sum(dim=-1, keepdim=True).clamp_min(1.0)
```

实测（fp32，相同 q/k/v）：chunkwise 与"**不含**该归一化的 parallel"相等到 `4.0e-07`（这正是 RetNet 式(1)≡(7) 的体现），
而**含**该归一化时输出量级从 1.33e+02 掉到 3.04e+00（差约 44 倍）。

- 训练路径（`MODEL_MODE="chunkwise"`）不经过它，**训练不受影响**；
- 但在这个 checkpoint 上做生成时，prompt 段的表示会与训练时的 chunkwise 不一致。
- 两个独立审查都建议：**不要动它**（它属于参考行为，而且正是它让 >1 的门控在 parallel 路径下不炸）。
  要改应该改 chunkwise 侧，而 chunkwise 侧已经用钳位解决了。

### 一个必须知道的历史遗留问题（本次未改）

`_parallel_retention`（**只用于 `generate()` 预填 prompt**，训练路径不用）多了一步
reference 没有的归一化：

```python
scores = scores / scores.detach().abs().sum(dim=-1, keepdim=True).clamp_min(1.0)
```

实测（fp32，相同 q/k/v）：

| 路径 | 输出量级 | 与 chunkwise 的相对差 |
| --- | --- | --- |
| chunkwise（= 参考实现） | 1.33e+02 | — |
| parallel **去归一化** | 1.33e+02 | **4.0e-07**（等价） |
| parallel **带该归一化**（当前代码） | 3.04e+00 | **4.4e+01**（差 44 倍量级） |

也就是说：`_chunkwise_retention` 与"不带归一化的 parallel"是同一个函数（这正是 RetNet
三种形式的等价性），而当前 `_parallel_retention` 因为那一步归一化，输出被压小约 44 倍。

- 训练完全不受影响（`MODEL_MODE = "chunkwise"`）。
- 但 `generate()` 先用 parallel 预填 prompt，**用这个 notebook 的 checkpoint 做推理时
  prompt 段的表示会与训练时的 chunkwise 不一致**，生成质量可能异常。
- 没有改它的理由：改 `_parallel_retention` 会连带影响 `generate()` 与任何
  `mode="parallel"` 的调用方，属于"设计遗留决策"而非本次笔误；而且那 44 倍缩放本身就是个
  过强的抑制。**建议单独确认后再动**，不要顺手改。

## 4. 尚未解决 / 需要上 TPU 才知道的

1. **原始 notebook 那次 `BrokenProcessPool` 的真正原因仍未确定。** 保存的输出里没有 worker 的 Python traceback：8 个 worker 都跑到了 step-1 日志块的 `xm.mark_step()`，然后被 kernel（PID 14）SIGTERM，父进程抛 `BrokenProcessPool`。既不是 `world_size`（已证伪）也不像 `import re`（只在续训触发）。**最可能是第一步编译/集合通信层面的失败，没有以 Python 异常形式浮出来。**
2. 没有真机验证过：首步 XLA 编译时间（128 chunk × 20 层展开 + 逐 block 梯度检查点，可能几十分钟）、显存峰值、稳定性。Kaggle TPU 会话有时限，建议先把 `MAX_STEPS` 设小（如 20）跑一次冒烟，确认 `[train] step=1` 打印出来、checkpoint 落盘，再放大。
3. `_parallel_retention` 的归一化遗留问题（见第 3 节末）只影响推理/`generate()`，需要单独决策。
