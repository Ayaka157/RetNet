# RetNet-272M 分词器审计：token 利用率与迁移可行性

**结论先行**

1. **不存在"极低的 token 利用率"。** 生产分词器 `data_cache/chat_pack_v13/bpe_tokenizer.json`（vocab 20000）在 1020 题基准上做到 **1.468 chars/token**，与 Qwen2.5-0.5B 的 151,665 词表分词器（**1.472**）持平，比 DeepSeek-LLM 的 100,015 词表（**1.433**）更好，是 GPT-2 的 50,257 词表（**0.645**）的 2.27 倍。Lead 提出的「1.29 chars/token ≈ 浪费 3 倍」是把**中文题**的 chars/token 与英文 BPE 的经验值相比，属于跨语言指标误用 —— 见 §1.3 的复核。
2. **真正的低效只有一处，且是分布错配不是中文挤压英文**：这个分词器是用 `legacy/prepare_chat_corpus.py` 的旧语料（LCCC + GLM 对话 + ShareGPT-zh + 中文维基 + wikitext103，按字符约 63% 是英文维基）训出来的，而 v13 实际在训的是 R1 数学 CoT + I_Wonder_Why + 角色扮演/小说。在**真实训练流的留出行**上，一个同 vocab=20000、但用语料自身训出来的对照 BPE 只要 **1.1435×** 更少的 token，即 **省 14.35%**；vocab 32000 省 **20.79%**。
3. **不存在真正的非破坏性迁移。** id 层面的"权重兼容"可以做到（追加 merge、保留 0–19999，实测基座 19,996 个条目全部仍可达，且任何文本都不会变长）；但"分布不变"做不到 —— 即使只是追加 500 条 merge，已有 token 边界仍有 **7.4%** 移位；换 20k 重训是 **30.0%** 移位。**GrowthLayerNorm 的"零初始化实现严格函数保持"无法搬到这里**，理由是离散重切分会改变序列长度与位置结构，而 RetNet 的衰减是位置相关的（§5.3）。
4. **建议：这一版不换；下一版从零开始时换，走"追加 merge + 新 embedding 行"这条路，vocab 控制在 32767 以内。** 硬约束：`train.ids.npy` 是 `int16`，id 上限 32767（§6.1）。数据重编码代价极小：实测编码吞吐 4.2–4.7 M token/s，552.33M 槽位纯编码 **2.2–3.8 分钟**。

所有数字都由本目录脚本实测，脚本与中间产物一一对应。文档、任务描述里的转述数字一律另行标注。

### 1.3 复核 Lead 的 1.29 chars/token

`1.29` 来自 `lc_d8k_*` 中文题（1.280–1.324），**中文题的 chars/token 天然接近 1**：一个汉字 3 字节，1 汉字/token 就是 3 bytes/token。判断"利用率低"必须用**同语言、同信息量的参照物**：

| 参照物 | vocab | 中文 chars/token | 英文 chars/token | 数据 |
|---|---|---|---|---|
| **本项目生产分词器** | 20,000 | 1.302 | 3.598 | 本目录实测 |
| Qwen2.5-0.5B | 151,665 | 1.285 | **4.472** | 同批文本实测 |
| DeepSeek-LLM-7B-Base | 100,015 | 1.253 | 4.270 | 同上 |
| GPT-2 | 50,257 | 0.544 | 4.406 | 同上 |

**中文侧：生产分词器的 1.302 比 DeepSeek-100k 的 1.253 好 3.9%，与 Qwen-151k 的 1.285 基本持平。** 英文侧：3.598 比 Qwen 的 4.472 差 19.5% —— 这是真的短板，但不是 3 倍。所以「中文吃掉了词表导致英文被切碎」这个假设**只部分成立、且幅度小**：「常见英文单词」的单 token 率是 107/111 = **96.4%**（`09_examples.py`），真正的洞在**中等频率长词**：

- 中文维基模板残留：`邮政编码为P`、`INSEE市镇编码为P`、`面积P`、`时的人口数量为P`、`所属的省级选区为`
- 英文维基残留：`owever`、`ccording`、`quadron`、`ugoslav`、`respectively`、`vess`、`passeng`

这些是「中文维基 + 英文维基」语料的指纹，在 R1 数学 CoT / 中文科普 QA / 角色扮演语料里永远不出现。

**是否因为中文挤压英文？** 反向对照实验给了否证（`05_compare.md`）：

| 训练语料（vocab 均 20000，4M 字符） | bench_all chars/token | 留出行 chars/token | `aga_r1` 的 Latin run chars/token |
|---|---|---|---|
| 生产分词器 | 1.468 | 1.687 | 2.673 |
| 仅中文语料（CJK ratio ≥0.9） | 1.360 | 1.650 | **1.469** |
| 仅英文语料（CJK ratio ≤0.02） | 0.596 | 0.649 | 3.091 |

一个**纯中文**训练的词表整体更差（1.360 < 1.468），其 Latin 效率只有 1.469（生产 2.673）。所以 41% 的 Latin 词表不是摆设，而是承重的。问题不是"中文太多"，是"**语料领域不对**"。

## 3 对照实验（同 vocabulary、同分布、同配置）

配置与生产完全一致：`models.BPE(unk_token="<unk>")` + `pre_tokenizers.ByteLevel(add_prefix_space=True)` + `decoders.ByteLevel()` + `trainers.BpeTrainer(vocab_size, min_frequency=2, special_tokens=[<pad>,<bos>,<eos>,<unk>], initial_alphabet=ByteLevel.alphabet())`，见 `retnet/tokenizer.py:30-40`。

### 3.1 语料（`04_train_controls.py`）

| 语料名 | 来源 | 字符数 | 抽样方式与代表性 |
|---|---|---|---|
| `v13_4M` | `train.ids.npy` 行解码 | 4,000,000 | `rng(20260418).permutation(269561)` 顺序取，覆盖全文件；1,204 行占 0.45% 的行、约 0.45% 的文档 |
| `v13_20M` | 同上 | 20,000,000 | 6,015 行，用于分离"语料规模"这个混淆因子 |
| `v13zh_4M` | 同上，行 CJK 占比 ≥0.9 | 4,000,000 | 扫 3,058 行取 1,421 行 |
| `v13en_4M` | 同上，行 CJK 占比 ≤0.02 | 4,000,000 | 扫 9,044 行取 567 行 |
| `orig_4M` | `legacy/prepare_chat_corpus.py` 的 5 个原始来源，按原**条数**权重等比缩放 | 4,000,000 | lccc 341k + glm 598k + sharegpt 97k + 中文维基 451k + wikitext103 2.51M 字符 |

**抽样代表性与其局限**：`v13_*` 从 `train.ids.npy` 解回文本，解码会丢 `<bos>/<eos>`（`skip_special_tokens=True`）。这不是分词器不可逆 —— `03_stream_census.py` 的往返检验显示差值基本等于该行内的文档数（如 41 行差 −10、26 行差 −4），即**每丢一个 `<eos>` 就少 1 个 token**。对"训练一个分词器"这件事，丢几个特殊 token 不改变字分布。**语料规模只有 4M 字符，按 §0.2 的推算（生产语料约 1.8 亿字符）只有约 1/45**，所以额外交了 `v13_20M` 来量化这个混淆：4M → 20M 只带来 1.2% 的改善（1.9290 → 1.9518），**规模效应远小于分布效应**。`orig_4M` 缺 wikitext 原始缓存，我用 `04b_fetch_wikitext.py` 从 HF 拉了 12,000 行 wikitext-103-raw（7,182,053 字符）补齐。

读法：
- **同 vocab=20000，仅仅把训练语料换成实际训练分布，就省 14.35%。** 这是"分词器不匹配"的真实幅度。

## 4 影响量化

全部由 `08_impact.py` 从 02/03/03b/05/06 的 JSON 推出。

### 4.1 一个 2048 token 窗口里有多少内容

| 量 | 值 |
|---|---|
| 内容 token / 槽位 | 96.3173%（pad 2.9196% + bos/eos 0.7631%） |

### 4.2 训练量折算

### 4.3 "如果分词器更好，等于多训了多少"

| 换法 | 内容放大 | v13 等效覆盖 | v13+v14 等效覆盖 |
|---|---|---|---|
| 换成语料自身重训的 20k | ×1.1435 | 21.20% | **106.00%** |
| 追加 merge 到 27,597 | ×1.1478 | 21.28% | 106.40% |
| 重训到 32,000 | ×1.2079 | 22.39% | 111.97% |
| 重训到 48,000 | ×1.2571 | 23.31% | 116.53% |
| 换 Qwen2.5-151k | ×1.1001 | 20.39% | 101.97% |
| 换 DeepSeek-100k | ×1.0749 | 19.93% | 99.64% |

**必须说清楚：这不是"多跑了 14% 的梯度步"。** 梯度步数不变，是每一步吃到的内容多 14%。等价说法：整个 v13+v14 训练过程从 92.70% 一遍数据，变成 106.00% 一遍数据的**内容量**。它提高的是 token 预算的利用效率，**不修任何能力问题**（CoT 不闭合、think 泄漏、七个零分类，与分词器无关）。

**责任划分（这是本节要回答的）：**

## 5 迁移方案

### 5.1 (a) 权重兼容：**可以做到，且已实测验证**

做法：保留 `0..19999` 的 vocab 映射与全部 19740 条 merge **一字不动**，把在目标任务分布上训出来的 merge **追加到 merge 列表尾部**，新产生的 token 拿 `20000+` 的新 id。

`07_reachability.py` 的结果（从 256 个单字节出发、按 merge 顺序走一遍判定可达性）：

| 变体 | vocab | merges | 会触发的 merge | 不可达 merge | 基座 20000 中仍可达 |
|---|---|---|---|---|---|
| `prod_v13` | 20,000 | 19,740 | 19,740 | **0** | 19,996（另 4 个是 special） |
| `app_top500` | 20,424 | 20,240 | 20,240 | **0** | **19,996** |
| `app_top8000` | 27,597 | 27,740 | 27,740 | **0** | **19,996** |
| `app_ctl_v13_20k` | 29,278 | 29,466 | 29,466 | **0** | **19,996** |
| `app_ctl_v13_48k` | 53,651 | 54,165 | 54,165 | **0** | **19,996** |

三条可验证的结论：

1. **基座 19,996 个非 special 条目全部保持可达**，所以"老 id 的 embedding 仍然对应同一段字节"在表示层成立。
2. **追加不会让任何文本变长。** 这是可以证明的：追加的 merge rank 高于所有基座 merge，最低 rank 优先的贪心 BPE 在一次追加 merge 触发之前的行为与基座**逐符号相同**；追加的 merge 只能在基座切剩的片段上触发，每次触发恰好少一个符号。**实测检验**（`10_monotonic.py`，1500 行留出文本，5 个变体）：变长的条数 **全部为 0**；`app_top500` 让 1470/1500 行变短、30 行不变，`app_ctl_v13_48k` 让 1500/1500 行变短。
3. 追加越多收益越大但有边际递减：+500 merge → 省 4.40%；+2000 → 8.32%；+8000 → 14.78%；+9726（到 29,278）→ 15.93%；+34425（到 53,651）→ 24.24%。

**收益/漂移取舍（`08b_gain_vs_drift.py`，300 条留出文本的 LCS span 一致率）**

| 换法 | vocab | 省下的 token | 边界一致率 |
|---|---|---|---|
| 什么都不做 | 20,000 | 0% | 100% |
| `app_top500` | 20,424 | 4.40% | **92.61%** |
| `app_top2000` | 21,822 | 8.32% | 86.78% |
| `app_top8000` | 27,597 | 14.78% | 78.13% |
| `app_ctl_v13_20k` | 29,278 | **15.93%** | 76.70% |
| `ctl_v13_20k`（真重训同 vocab） | 20,000 | 14.35% | **69.98%** |
| `ref_deepseek-llm` | 100,015 | 7.49% | 74.53% |
| `ref_qwen2.5-0.5b` | 151,665 | 10.01% | 70.68% |

**反直觉但成立的一条：`app_ctl_v13_20k` 用 29,278 词表省了 15.93%，比同 vocab 全量重训（14.35%）省得更多，而边界漂移还更小（76.70% vs 69.98%）。** 原因是追加永远不会动已有 merge，漂移只来自新 merge 触发；而全量重训会重排整条 merge 列表，把原有边界一起改掉。

### 5.2 (b) 分布不变：**做不到**

同一段文本在新分词器下必然产生不同边界。实测一致率（prod 的 token span 里能在候选编码中作为对齐 span 保留的比例）：追加 500 条 merge 就已经掉到 **92.61%**；追加 8000 条掉到 **78.13%**；换 20k 重训掉到 **69.98%**；换 Qwen 掉到 **70.68%**。**哪怕只动一点点，也至少有 7.4% 的边界会移位。**

移位的直接后果是隐藏状态漂移，而且 RetNet 的漂移不是"多一维少一维"那种可补偿的：boundary 一变，序列长度变、注意力/衰减的相对距离 `γ^(n−m)` 变、每个位置的 LayerNorm/FFN 作用次数变。

### 5.3 GrowthLayerNorm 的类比：**搬不过来**

`retnet_hf/modeling_retnet.py:292,381` 的 GrowthLN 用 `γ_new=β_new=0` 让新增的 256 维在初值上输出恒为 0，于是 `f_new(x) ≡ f_old(x)` **对所有输入严格成立**。它能成立的前提是：**输入序列不变，只是在函数内部多了一组恒零坐标。**

词表扩张没有这个前提。分词器是网络**之外**的离散映射，换分词器改的是**输入序列本身**。不存在任何 embedding 初始化能让重切分后的序列恢复旧激活：

- 序列长度变了 → RetNet 的位置衰减 `γ^(n−m)` 在同样两个内容位置之间的取值变了；
- 位置数变了 → 每个内容位置上的逐点非线性（norm1 / FFN / norm2）被作用的次数和上下文变了；
- `group_norm` / key-value 分组是跨位置的，分组边界也随之改变。

**唯一真正函数保持的词表改动，是加入"任何现有文本都产不出"的 token**（例如全新的控制符），它不改变旧文本的切分，因此也不带来任何效率提升。**"零初始化"这条路在词表上是空的。**

### 5.4 新 embedding 行怎么初始化（含对 Lead 那条提示的判断）

我读了 `checkpoints/retnet_272m_v13/model.safetensors` 的 `embedding.weight [20000, 1024]`（`tie_weights=true`，所以同时是输出头），实测：

| 统计量 | 值 |

| 行范数 mean / std / min / max | 0.9556 / 0.8206 / 0.3162 / 4.1358 |
| 参考 `N(0, 1/d)` 的 std（d=1024） | 0.031250 |

按类别：

| 类别 | 行数 | 行 std | 平均行范数 |
|---|---|---|---|
| cjk | 10,528 | 0.03919 | 1.0398 |
| latin | 8,213 | 0.03033 | 0.8437 |

按**训练频率**（用 `03_counts.npz` 的精确 id 计数）：

**对 Lead 提示的判断（不完全同意）：**
- 结论一致：新行应该从**经验统计量**里取，不要写死公式。
- **但理由不同。** `embed_scale` 是前向里对整张表乘的一个**全局标量**（`x = embedding(ids) * 27.7128`），它同时放大所有行，在做"新行的量级要和已有行匹配"这件事时**自动约掉**。所以 `embed_scale=√768` 并不会让 `N(0,1/d)` 错配 0.866 倍。

| 初始化 | 范数区间 | 该 token 真实行范数 |
|---|---|---|
| `sum(E_a, E_b)` | 0.559 – 0.850 | 0.348 – 0.540 |
| `0.5·(E_a + E_b)` | 0.279 – 0.425 | 0.348 – 0.540 |

**取均值系统性偏小约 15%，求和系统性偏大约 65%。** 均值更接近，但建议再按该频率档的经验行范数做一次重标定，而不是直接使用。

### 5.5 是否存在"真正的非破坏性迁移"？——**不存在**

| 层面 | 能不能 | 实测依据 |
|---|---|---|
| id → 字节 语义不变（老 embedding 还指同一个东西） | **能** | 基座 19,996 条目在追加变体里 100% 仍可达；0 条 merge 变不可达（§5.1） |
| 任何文本都不变长 / 不丢信息 | **能**（追加式） | 1500 行 × 5 个变体，变长条数 = 0（§5.1） |
| 模型**函数**对旧输入不变 | **不能** | 边界一致率最高只有追加 500 条时的 92.61%；换分词器 69.98%（§5.2） |
| 训练分布/表示不变 | **不能** | 同上；且序列长度与位置结构改变（§5.3） |

**最小损伤方案**：`app_top2000`（vocab 21,822）——省 8.32% token、坐标漂移 13.22%；或 `app_top8000`（vocab 27,597）——省 14.78%、漂移 21.87%。两者都保留全部老 id，只需要新增 embedding 行 + 重编码数据，不必重启学习率调度（旧 id 的语义没变，模型不该被重置）。

| 编码吞吐（`app_top8000`，merge 表更长） | **4.74 M 字符/s，2.45 M token/s** |
| 552.33M 槽位纯编码耗时 | **2.2–3.8 分钟** |
| 参考：v13 构建时的 reader/IO 耗时 | r1 147.9M token = 155.0 s，wiki 118.9M = 96.7 s，ruozhiba 0.12M = 0.1 s（v13 `meta.json`） |
| 参考：v9 基座 285M token 的重切分 | `build_chat_mix_v13.py` 的 `reslice`，不重新分词 |

**编码本身几乎不要钱**（分钟级）。真正的成本在：训练必须从新的数据包重新跑（tokenizer 变了就没有意义去 resume 旧优化器状态），以及方案 C 里 embedding 全表重置导致的前期损失。

> 关于"要不要重启 cosine"：方案 B 里 `0..19999` 的语义没变，**不需要重置优化器/学习率**；但数据是全部重编码的，输入分布确实变了，模型需要一段适应期 —— 这是"不重启"和"没有代价"之间的区别，我没做训练实验去量化这段适应期。

### 6.3 具体建议

1. **不要为了 v14 中断当前训练。** 收益是"每步多吃 14% 内容"，不是能力修复；而 v14 的 cosine 已接近终点，换分词器会让已学的 embedding 全部作废。
2. **下一版（v15 / 1-epoch 对照）从零开始时，换。** 走**方案 B（追加式）**：
   - 用 v13 训练分布（或更好的 v14 数据）训一个 vocab 48,000 的 BPE，只取它相对生产 merge 列表**新增**的前 N 条（按需要控制到 vocab ≤ 32767，N ≈ 12,700 条 merge）。
   - 保留 `data_cache/chat_pack_v13/bpe_tokenizer.json` 的 vocab 与 merge 前缀字节不变，追加新 merge，新 token 分配 `20000+`。
   - 新 embedding 行按其组成片段的经验行统计初始化（§5.4），不要用 `N(0,1/d)` 直接填。
   - 重编码 `a_grade` + v9 基座来源，生成 `chat_pack_v15`。
   - 预期：同等 token 预算下内容 +15%，v13+v14 那种量级的训练从 92.7% 一遍等价变成 106% 一遍等价。
3. **如果只做一件事、且愿意接受全表重学**：方案 C（vocab 32,000，省 20.79%）更好。但必须重启 cosine（embedding 全表重置），并且要接受前期 loss 上升。
4. **不要动 `embed_scale`，至少在换分词器的那次实验里不要动。** 它是一个遗留的约定不一致（√768 vs √1024，实测训练过的行 std 0.01596–0.0359，无效行 0.0715），但 v10/v13/v14 全都在它下面训练，模型已经适应；它**不是缺陷**。如果将来要从零重跑，把它改成 √d_model 是一次**超参变更**，应该独立做实验、不要和分词器变更混在一起，否则两个变量分不开。
5. **不要靠换分词器解决长上下文。** 中文 8K 材料在任何现实词表下都要 2.2 倍以上窗口（§4.4）；要解决超窗得改窗口/位置外推，不是换词表。
6. **英文短板值得单独修，但收益有限**：生产分词器在纯英文上 3.598 vs Qwen 4.472（省 19.5%）。不过 v13 流里 Latin 只占 13.25% 的 token，即使英文全部优化到 4.47，整体也只再省约 2–3%。

## 7 未能核实 / 存疑

| # | 事项 | 状态 |
|---|---|---|
| 1 | **v14 的实际训练进度** | 本机只有 `checkpoints/retnet_272m_v14/checkpoint-10000`（step 10000，epoch 0.14839，max_steps 50000）。92.6% 只能按"v13+v14 累计 512.0M/552.33M = 92.70%"复现；v14 自己是否跑到 50,000 步、以及是"到 50,000"还是"再跑 50,000"，需要远程日志。我没有登录笔记本（要求不碰它的 GPU）。 |
| 2 | Lead 的「lc_d8k：7409 字符英文 → 5744 token」 | **在 `bench/` 全目录（含 `items/`、`pools/`、`data/`）grep `8192` / `5744` / `5745` / `7409` 零命中。** 最接近的真实数据是 `lc_d8k_03`（7410 字符英文 → 2074 token）与 `lc_d8k_01`（7354 字符中文 → 5745 token）。判定为两题数字拼接，非真实条目。 |
| 3 | `v14_272m_2k_opt.json` 用 `batch=1, grad_accum=4` 而 v13 用 `batch=4` | 两者有效 batch 都是 4，但优化器不同（`adamw_bnb_8bit` vs 默认）。这不影响分词器结论，我未追查。 |
| 4 | 生产分词器的确切语料 | 仓库里只有 `legacy/prepare_chat_corpus.py` 一处训练这条 tokenizer，词表交集实验（72.9% / Jaccard 0.573）支持同源。但 `data_cache/chat_mix_v20k/` 目录已不在，无法做"同一脚本重跑 → 文件级一致性"的终局验证。 |
| 5 | `orig_4M` 的字符占比（英文 63%） | 由每源 400 条探针的**平均长度 × 原抽样条数**推算，不是原始语料的精确字符统计；wiki 源 30 万条里我只探了 400 条。数量级可信，小数点后不可信。 |
| 6 | `ctl_*` 对照的发散 | 每个对照只训了一个种子。BPE 训练基本确定性（`tokenizers` 的 `train_from_iterator` 在相同输入上确定），但没有第二种子验证。 |
| 7 | 留出行与对照语料的严格不重叠 | 我对 `v13_*`（全类）采样器做了精确排除（它们只取 `permutation[:9044]`，留出集取 `[9044:]`）。`v13zh_4M`/`v13en_4M` 的过滤器扫过 `permutation[:9044]`，所以也被排除。**无重叠。** |
| 8 | `a_grade` 测试集与对照组语料 | `02/05` 里的 `aga_*` 用的是**前 1500 条**文档，对照语料按行等概率抽样，理论重叠约 0.45% 的文档。可能让对照组的优势被高估约 0.5 个百分点（相对 14% 的差距可忽略）。**基准 (bench) 侧无任何重叠。** |
| 9 | 从 `.npy` 解码回文本再测的保真度 | **已核实为可信，我先前的一个怀疑被自己否掉。** 我一开始把 `02` 的 `stream_decoded`（1.6545 chars/token）与 `corpus_r1`（1.438）相比，以为解码丢了约 13% 的 token —— 那是拿两个**不同语料**在比。正确的对比是两个独立的解码样本：`02` 的 2000 行得 1.6545，`06` 的 1500 行得 1.6868，相差 1.9%（抽样噪声）。解码的真实损失只有 `skip_special_tokens` 丢掉的 `<eos>`：2,107,300 / 269,561 行 = **7.82 个/行 = 窗口的 0.38%**。段首 `Ġ` 前缀在解码文本里是保留的，所以"解码回文本"这条路径的偏差 <0.4%。 |
| 10 | `retnet/data.py` 里的 `BPETokenizer.train` | 那是 wikitext 预训练线（默认 `vocab_size=8192`，缓存目录独立），与 chat 分词器不是同一条线；我没有逐行追它的实际调用参数，判定为与本次结论无关。 |
| 11 | cos 学习率与"重启"的具体影响 | 我只给出定性判断（方案 C 需要重启、方案 B 不需要），**没有做训练实验**去量化重启损失。GPU 被 3070 基准作业与笔记本 v14 占用，本次审计全程零 GPU。 |
| 12 | 「追加式」在训练中的实际收益 | 只测了分词效率（token 数），**没有测** 15.93% 的内容放大在 loss/基准上折成多少。按 token 效率线性外推是合理的一阶近似，但不等价于能力提升。 |
