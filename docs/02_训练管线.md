## 1. 两套训练入口

| 入口 | 用途 | 数据模式 |

| `retnet_hf/train.py` | **143M / 272M 线全用它**（HuggingFace Trainer + Accelerate + safetensors） | 只吃 packed |

## 2. packed + 权重码（核心设计）

### 2.1 为什么长这样

第一版 SFT（`retnet_100m_chat_sft`，ppl 13.96）评测时**答非所问**。贪心解码证明条件相关性
其实是好的（问番茄炒蛋答得对），问题出在三个可修复处：

| # | 症状 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 回答跑题 | `repetition_penalty` 把**提问里的词**也惩罚了，把回答推离问题 | 默认只惩罚新生成的 token（`penalize_prompt=False`）+ `no_repeat_ngram_size=4` |
| 2 | 模型很少见到真正的推理输入 | 旧管线把对话拼成一条流再切 256 块，样本大多从对话中间开始 | 按样本对齐 + best-fit 装箱 |
| 3 | 容量浪费在建模问题上 | loss 算在所有 token 上，提问也参与 | 按 token 打权重码 |

### 2.2 现在的设计

- 每样本 = `<bos>[设定：persona\n]用户：{q}\n助手：{a}<eos>`，BOS 对齐、EOS 收尾、**截断保头**
- 每 token 带权重码：

  | 码 | 含义 | 是否算 loss |
  | --- | --- | --- |
  | 0 | padding | 否 |
  | 1 | 助手回复 | 是 |
  | 2 | 提问 + 设定块 | `--prompt_loss_weight 0.1` |
  | 3 | 纯文本回放 | 是 |

- **编码器唯一实现** `retnet/chat.py`（`encode_dialogue` / `encode_prompt` /
  `encode_dialogues_batch`），训练与推理共用，保证 token 边界逐 token 一致
- **打包**：`retnet/packing.py` 的 `Packer` 做 best-fit 装箱，padding 占比约 1.6%（旧管线 16%）
- **persona**：`设定：` 块走 prompt 权重——模型学「按设定说话」，不学「生成设定」

### 2.3 行布局（改数据时要懂）

`retnet_hf/data.py` 的 `PackedChatDataset` 读的是 `(N, seq_len+1)` 的 int16 行：

```text
行 = [x_0 ... x_{seq-1} x_seq]
input_ids = 行[:-1]      labels = 行[1:]      wcodes = 行[1:] 对应的权重码
```

每一行是**多个样本 best-fit 装进去的**，不是一条对话。所以「行」和「样本」不是一对一。

## 3. 截断陷阱（本项目踩过最贵的坑）

**读取端和打包端的两级截断都从尾部切，而答案在尾部。**

| 环节 | 默认值 | 后果 |
| --- | --- | --- |
| 读取端 `clean(output, N)` | v10 用 **1200 字符** | R1 输出中位 1,912 字符 → **砍掉 52%**，正好砍掉 `</think>` 与答案 |
| 打包端 `encode_dialogues_batch(max_len=seq_len)` | v10 用 **512 token** | 再把超出部分切掉 |

实测漏斗（抽样 3,010 条 R1）：

```text
原始 output 含 </think>         100.0%
经 clean(output,1200) 后仍含     71.7%
再经 512 token 打包后
  → 只剩 <think> 没有 </think>   74.7%
```

后果：模型学会的是「开一个 think 块，**永远不收尾**」——实测 26.5% 的生成样本泄漏
（`<think>` 无 `</think>`），且集中在 R1 数据本来想改善的填空/问答/结构化上。

**修法**：窗口与字符上限必须同时抬。

```powershell
scripts\build_chat_mix_v13.py --base data_cache/chat_pack_v9 `
    --out_dir data_cache/chat_pack_v13 --seq_len 2048 --r1_max_chars 4000
```

效果：`<think>` 闭合率 23.7% → **86.0%**（R1 部分 95%），R1 token 从 44.8M 涨到 147.9M。
完整证据见 [`13_基准测试重设计与评测结果.md`](./13_基准测试重设计与评测结果.md) §2。

> ⚠️ **不要用 `build_chat_mix_v9.py --seq_len 2048` 从原始语料重建大窗口。**
> 长文本读取器会涨到 13 GB RSS 然后被 OOM 杀掉。宽窗口只重切 v9 已有的 token 流，
> 仅对需要完整 CoT 的源重新编码——这就是 `build_chat_mix_v13.py` 的做法。

## 4. 生长脚本

| 脚本 | 作用 | 实测 |
| --- | --- | --- |
| `scripts/grow_143m.py` | 100M → 143M：深度 12→18 层 | 函数保持 |
| `scripts/grow_272m.py` | 143M → 272M：宽 d768→1024 + 深 18→20 层 | Δ7.25e-4 |
| `scripts/grow_150m.py` | 早期深度生长实验 | — |

宽度生长的关键是 `GrowthLayerNorm`：pre-LN 下直接扩宽会让新通道进入每层 LN 的均值/方差，
旧通道的归一化输出被系统性改变，18 层级联后 loss 从 4.5 涨到 17.8。
解法是 **LN 只对旧 D 维生效，新通道走 `gamma_new=0` 的零侧分支**。
另需 `embed_scale = OLD_D**0.5`——少了它 Δ 会从 7.25e-4 爆到 23.5。
原理综述见 [`08_chunkwise_growth_research.md`](./08_chunkwise_growth_research.md)。

## 5. 修过的坑（历史记录）

| 问题 | 原因 | 修复 |
| --- | --- | --- |
| PPL 锯齿（跌了又涨） | `scripts/train_loop.py` 分段时每段把 cosine LR 当新周期重置 | 改用 `train.py` 直接带 `--lr_total_steps <全局总步数>`（`pretrain_v4` 就是这么跑的）；`train_loop.py` 的锯齿至今仍在，见 [`12`](./12_训练状态盘点.md) §6 |
| Windows 上 `--compile` 崩溃 | 无 Triton，Inductor 失败 | 自动检测：有 triton 用 inductor，否则降级 aot_eager；后已安装 triton-windows |
| `train_loop.py` 参数错误重试 5 次 | Windows 下 `--` 分隔符残留 + `sys.path` 缺项目根 | 自动去 `--`、加 `sys.path`、参数错直接退出 |
| 半角逗号污染（`地方,比如说`） | 中文语料夹杂半角标点 | `clean()` 中 CJK 间半角标点转全角（英文不受影响）+ `is_fragment` 碎句过滤 |
| 口癖合成 bug | `t_cold` 的 `rstrip('。！')` 漏 `？`；`t_short` 未硬截断 | 修复 + 严格 ≤20 字截断 |
| PowerShell 5.1 跑含中文的 `.ps1` 报 ParserError | ANSI 编码读文件 | 一律用 `pwsh`（PowerShell 7）执行链脚本 |
| **SSH 启动的训练永远起不来** | `Start-Process` 起的进程隶属 SSH 会话，断开时 Windows 连带杀整棵进程树 | 改用 `schtasks` 触发；症状是日志只有启动横幅、`nvidia-smi` 占用 0 |
