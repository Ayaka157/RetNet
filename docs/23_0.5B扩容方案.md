**三条核心结论**：

1. **稠密路线没有「同速」解，而且这次是定理不是经验。** 固定形状族下
   `MAC/token = κ(d,C) · P_active`。κ **不是**普适常数，但跨配置散布只有 **±1%**
   （C=128 时 1.037~1.049），所以**线性关系是精确的**；而总参数量 `P_total` **根本不进成本**（§2）。
   所以「参数翻倍 = 算力翻倍」在稠密里无法绕过。
   **0.5B 实测 2.65×（vs 713）/ 2.87×（vs 今天的 660 ms），0.6B 装不下**（§4.5、§4.7）。
2. **唯一能「加参数不加算力」的机制是条件计算**（MoE / MoD）。它能做到
   **名义 0.69B @ 现状步时 + 40%**，但它换到的是**名义**参数量，
   **不等于同参数量的稠密模型**（§7 给了六条反面证据）。
3. **能改变分母的只有数据。** 当前 272M 只吃到约 **2.5 token/参数**，
   文献位置在 20+。吃完已落地的 3.4 B token：272M 要 3.8 天、0.5B 要 8.3 天。

## 2. 核心恒等式：为什么稠密守不住速度

`【推导】` 固定形状族（`vdim/d`、`ffn/d`、`key_dim` 恒定）下逐层数张量：

```
前向 MAC/token = κ(d, C) × P_active
```

`κ` **不是**一个普适常数，但只要形状比例固定，它就在一个**很窄**的带里
（下表是实算，非估计）：

| 配置 | C=64 | **C=128（实际配置）** | C=256 |
|---|---|---|---|
| d1024 / L20（现状 272M） | 1.0386 | **1.0494** | 1.0773 |
| d1408 / L20（**0.5B**） | 1.0287 | **1.0367** | 1.0574 |
| d1408 / L24（**0.6B**） | 1.0290 | **1.0370** | 1.0580 |
| d1216 / L26（0.5B 窄深） | 1.0334 | 1.0427 | 1.0669 |

**跨配置的散布只有 ±1%（C=128 时 1.037~1.049），所以
`MAC/token ∝ P_active` 是**线性**的，这一点是精确的**；但 `κ` 本身
**不是**与 d 无关的常数——它随 `C` 涨（O(C·d) 的块内项）、随 d 略降。

⚠️ **方向**：加宽会让 `κ` **变小**（1.049 → 1.037），即宽模型的「每参数算力」
反而略低——这是 §3 选宽浅的又一条（很弱的）支持。本文早期版本写的
「κ = 1.033，与 d、L、heads 都无关」**是错的**：1.033 对应的是 C=64 的窄深配置，
而且 κ 确实随 d 与 C 变化。**结论（线性 ⇒ 没有同速解）不受影响，但那句话本身要撤回。**

于是

```
T_step − floor ≈ 6 · κ · P_active · tokens / TFLOPs_eff      ← 对 P_active 严格线性
```

**只有「每 token 激活参数量」进成本，总参数量不进。** 稠密下 `P_active ≡ P_total`，
所以**要守住步时就必须守住参数量**。这就是「没有同速解」的证明。

**四条独立校核**（`scripts/flops_model.py --check`，任一不过退出码非 0）：

| 校核 | 模型 | 独立来源 | 差 |
|---|---|---|---|
| 272M 参数量 | 272,304,448 | checkpoint 实测 | **0（逐位）** |
| 单层 FFN 参数 = `2·d·ffn` | 83,886,080 | meta device 加宽 ffn 的实测差分 | **0** |
| 272M MAC/token | 282.8M（chunk 64） | `docs/16` §4.3 的 281.3M | 0.54% |
| S1（`value_dim` 减半）MAC/token | 215.2M | `docs/16` §4.3 的 214.5M | 0.35% |
| **700M 步时（d1024/L54）** | **2,358~2,423 ms** | `docs/16` §4.1 用**另一套方法**估 ~2,300 ms | ~3~5% |
| **容量上限** | d1024 → **L≤54**（700M） | `docs/16` §4.1 独立算 L≤54.8 | **一致** |

最后两行是**第三方方法的交叉验证**：`docs/16` 用「每层边际字节数 × 层数」的容量口径，
本文用「逐张量 MAC ÷ 实测 TFLOPs + 发射地板」的计算口径，**两条路在 700M 上收敛到同一答案**。

### 2.1 逃逸口只有一个：条件计算

既然成本只认 `P_active`，那就让 `P_total > P_active`。穷举之后**只有条件计算能做到**：

| 机制 | 对 `P_total` | 对每 token 算力 | 结论 |
|---|---|---|---|
| **MoE**（E 专家 top-1） | ↑ | **平** | ✅ 唯一能「加参数不加算力」 |
| **MoD**（部分层按容量跳层） | 平 | ↓ | ✅ 反向的同一个旋钮 |
| 权重共享（ALBERT 式） | ↓ | ↓ | ❌ 减的是唯一参数，方向相反 |
| 量化训练 | 平 | 平 | ❌ 不改「每 token 要算多少」 |
| GQA / MQA | 平 | 平 | ❌ 本架构推理用 O(1) state，**没有 KV cache** |
| 加宽词表 | ↑ | ↑ | ❌ LM head 是 `V·d` MAC/token，同比例涨 |
| S1（`value_dim` 减半） | ↓ | ↓ | ❌ 参数与算力**一起**减。实算：0.6B 上 L24→L32，参数都是 599.4M，MAC 621.6M→**617.0M（−0.7%）**。**对「同参数更快」完全无效** |

## 4. 步时预测

### 4.1 模型（只用实测锚点，不做幂律外推）

```
T_step = floor · (L/20) + (713 ms − floor) · (MAC_active / 286M)     [关检查点]
再 × 检查点倍率 ckpt（目标尺寸必须开检查点）
```

`MAC_active` 由逐张量形状数出（chunkwise 的 O(L·C) 形式，不是 O(L²)）。

### 4.2 两个自由参数的区间

`floor` = 发射/空闲地板，`ckpt` = 检查点倍率。**二者不能同时定死**：

| 约束来源 | 给出 |
|---|---|
| 实测锚点 713 ms（关检查点） | 分母 |
| 同批形状 936 ms【**实测·异条件**：batch1×accum4 + 检查点，但那次的优化器是 **fp32 AdamW**，不是 8-bit，故与本表的 713 ms 基线**不可比**】 | `ckpt ≈ 1.313`（偏高） |
| **发射地板的反解** | `floor ∈ [92, 148] ms` ↔ `ckpt ∈ [1.27, 1.31]` |
| **profiler 第三条约束** | 内核 10,116 个 × 14.6 µs = **148 ms**；空闲率 20.8% × 713 = **148 ms** |

`【推导】` profiler 两条独立路径都给 `floor ≈ 148 ms`（`docs/15` §0.2：C 配置 10,116 内核、
20.8% 空闲；B 配置 3,427 内核、4.4% 空闲）。

⚠️ **它带来一个必须写下来的张力**：若 `floor = 148`，则 936 ms 反解出 `ckpt = 1.264`，
**低于**同批形状比值的 `[1.27, 1.31]`。三种解释都能自圆其说、**现在无法区分**：
profiling 膨胀不等倍 / 936 那次是 fp32 AdamW / 重算那遍效率更高。
**只有 E1a/E1b 能分开**（见 §8）。所以区间保留为**覆盖三者全部后果的保守包络**。

### 4.3 预测结果（**模型口径**，系统性偏保守——完整区间见 §4.4）

| 方案 | MAC/token | 步时（微基准口径） | **vs 713** | 端到端换算（×788 ms） |
|---|---|---|---|---|
| 现状 272M | 286M | **713 ms**（锚点，实测 713） | 1.00× | 788 ms（实测 1.27 it/s） |
| **A. 0.5B 宽浅** | 523M | **1,500~1,609 ms** | **2.10~2.26×** | 1.65~1.78 s |
| B. 0.5B 窄深 | 507M | 1,517~1,599 ms | 2.13~2.24× | 1.68~1.76 s |
| **C. 0.6B 宽浅** | 622M | **1,786~1,914 ms** | **2.51~2.68×** | 1.98~2.11 s |
| D. MoE E=6 | **286M** | 951~1,075 ms | 1.33~1.51× | 1.05~1.19 s |

⚠️ **本表是「全部算力按 d² 缩放」的口径**，而真实步时里约一半是只 ∝ d 的逐元素算子，
所以**这些数字偏高**（详见 §4.4，降幅 6~16%）。**对外引用请用 §4.4 的完整区间。**

步时区间 = `floor ∈ [92,148]` × `ckpt ∈ [1.27,1.31]` × 条件计算开销带的**端点组合**，
取同向端点给出最宽的诚实误差带，**不是置信区间**。

### 4.4 这个模型**偏保守**（单侧界，方向确定）

⚠️ **§4.3 的数字系统性偏悲观**，原因是模型的一个结构性近似，必须写出来：

`【推导】` **GEMM 成本 ∝ d²，而非 GEMM 的逐元素/归一化/损失 成本 ∝ 张量元素数（∝ d）。**
但 §4.1 的模型把**全部** compute 按 MAC 比（即 ∝ d² 那个）缩放 → 对加宽配置**系统性高估**。

**这一条只需要上面那句【推导】，不依赖任何有争议的常数。**
所以：**在相同的 `floor`/`ckpt` 下，真实步时 ≤ 模型预测，方向确定，永远是更快。**

**量级（依赖较弱的前提）**：`docs/15` §0.3 记「GEMM ~49% / 逐元素 ~51%」，
但它**没写清分母是墙钟还是忙时**。两条读法给出 GEMM 占忙时的比例 `b`：

- 若分母是忙时 565 ms → `b = 0.49`
- 由 10.28 TFLOP 与 **batch1 形状峰值 26~42 TFLOPs**（`docs/15` §0.4）反推，
  GEMM 时间 ∈ [245, 395] ms → `b ∈ [0.43, 0.70]`

取可辩护的 `b ∈ [0.49, 0.70]`，并给损失占逐元素的 0~40%（**无数据**，损失 ∝ V·seq 与 d 无关）：

| 方案 | MAC 比 | 元素比 | 模型 | 稀释后 | 降幅 |
|---|---|---|---|---|---|
| 0.5B 宽浅（d1408/L20） | 1.829 | 1.375 | 1,500 ms（2.10×） | **1,279~1,403 ms（1.79~1.97×）** | **6.5~14.7%** |
| 0.5B 窄深（d1216/L26） | 1.773 | 1.544 | 1,517 ms（2.13×） | **1,353~1,467 ms（1.90~2.06×）** | **3.3~10.8%** |
| 0.6B 宽浅（d1408/L24） | 2.175 | 1.650 | 1,786 ms（2.51×） | **1,499~1,673 ms（2.10~2.35×）** | **6.3~16.1%** |
| 0.6B 窄深（d1216/L32） | 2.163 | 1.900 | 1,853 ms（2.60×） | **1,625~1,796 ms（2.28~2.52×）** | **3.1~12.3%** |

（同一 `floor/ckpt` 端点 148 ms / 1.27，以隔离出稀释效应本身。）

> 📌 **一个反直觉的副产品：窄深的稀释收益只有宽浅的一半。**
> 原因是窄深要更多层来补参数（L26/L32 vs L20/L24），而逐元素算子的量 ∝ **L×d**，
> 所以它的「元素比」更大（1.544/1.900 vs 1.375/1.650）——**逐元素这块长得更快，
> 稀释能省的就更少**。
> 这不推翻 §4.6 的「宽度胜出」，但**削弱了它在这个具体选择上的分量**：
> 0.5B 宽浅 vs 窄深在稀释后是 1.79~1.97 对 1.90~2.06（宽浅快约 5%），
> 而不计稀释时是 2.10 对 2.13（只快 1.4%）。
> **宽浅真正的优势因此主要是「同样步时下多 9% 参数」（504M vs 486M），
> 而不是速度。**

`【推导】` **降幅有闭式**，这让敏感性一眼可见：

```
降幅 = (1 − b) × (MAC比 − 元素比) / MAC比        其中 b = GEMM 占 compute 时间的比例
0.5B：(1 − b) × (1.829 − 1.375) / 1.829 = 0.248 × (逐元素占比)
0.6B：(1 − b) × (2.175 − 1.650) / 2.175 = 0.241 × (逐元素占比)
```

即**逐元素占比每 10 个百分点，降幅约 2.4 个百分点**。
所以即使逐元素占比只有 30%，降幅仍有 7%；有 51% 时是 12.7%。
**方向恒定，只影响量级。**

> 📌 **因此完整区间应把低端下移**（低端 = 上表稀释后的最低，高端 = 未稀释的 `floor/ckpt` 最差端点）：
>
> | 方案 | 模型口径 | **完整区间** |
> |---|---|---|
> | 0.5B 宽浅 | 2.10~2.26× | **1.79~2.26×** |
> | 0.5B 窄深 | 2.13~2.24× | **1.90~2.24×** |
> | 0.6B 宽浅 | 2.51~2.68× | **2.10~2.68×** |
> | 0.6B 窄深 | 2.60~2.77× | **2.28~2.77×** |
>
> **这是更大的不确定带，不是更好的结果预告**——它意味着 0.6B 有可能落在 2.1× 附近，
> 而这恰好是「值不值得做」的边界。**E3a/E3b 是唯一裁决。**
>
> ⚠️ 上表 0.6B 窄深的「模型口径」上限 2.77× 是按 §4.3 同法推的（它不在 §4.3 表里，
> 因为 §3.2 没给它做显存预算；**只作对照，不推荐**）。
>
> 它**不改变** §2 的恒等式，也**不改变**「稠密没有同速解」：稀释只是让斜率比 d²
> **略缓**，不会让斜率变成 0——§6 里那个恒为 1.01 的「参数/算力比」才是根因。

#### 🚨 更正 1：**0.6B 装不下**——本文 §3.2/§3.3 的「两者都装得下」是错的

E3b 的 `peak_reserved = 8.18 GiB = 8,376 MiB`，而**整卡只有 8,192 MiB**。
保留量超过物理显存 → WDDM 把页换到系统内存 → **步时 16,814 ms，是 500M 的 8.9 倍**。
卡上 nvidia-smi 当时显示 7,914/8,192 MiB（97%），功耗却只有 **87 W @ 98%「利用率」**——
**满利用率 + 低功耗 = 显存颠簸**，与 §9.1 那次笔记本事故同一个签名。

**所以 0.6B 在 batch1×accum4 + 全量检查点下不可用**：标称能算，实际慢 8.9 倍。
**真正的墙在 500M 与 600M 之间**，不在 §3.2 预测的位置。

我的显存模型错在哪：**`frag`（碎片）一项取了 154 MiB，太小。**

| 配置 | 我预测的合计 | **实测 reserved** | 差 |
|---|---|---|---|
| 272M **无**检查点 | 6,940 MiB | **6,932 MiB** | −8 ✅（这一档我的模型是准的） |
| 272M 全检查点 | 3,279 MiB | **3,881 MiB** | **+602** |
| 500M 全检查点 | 5,542 MiB | **7,076 MiB** | **+1,534** |
| 600M 全检查点 | 6,472 MiB | **8,376 MiB** | **+1,904** |

误差随规模增长（+602 → +1,534 → +1,904），说明缺的不是常数项而是**随规模放大的项**
（allocator 碎片 + `torch.compile` 工作区 + 重算瞬态的实际峰值）。
**「余量」因此全部要重算**：0.5B 的真实余量是 `7,593 − 7,076 = 517 MiB`，**不是 2,052 MiB**。

#### 🚨 更正 2：检查点代价是 **1.965×**，不是 1.27~1.31×

E1a/E1b 是本文一直缺的那对**同口径**测量（同一个真实模型 v13、同 batch、同 8-bit Adam，

而本文 §4.2 由 `936/713` 推出的区间是 `[1.27, 1.31]`——**低了约 50%**。

> 为什么会差这么多：**`torch.compile` 与梯度检查点叠加会掉融合**。
> 检查点把图切成多段，编译后的融合收益部分丢失，加上重算本身（理论 +1/3 前向，
> 即 1.33×），实测到了 **1.965×**。这也解释了为什么 §4.2 反解出的 `floor`/`ckpt`
> 怎么凑都对不上——**我那两个约束的前提（重算只按 4/3 算 FLOPs）在这个栈上不成立**。

#### ✅ 更正 3：参数缩放比我的模型**更慢**（好事），但被检查点抵消掉了

同样开全量检查点，**500M / 272M = 1,891 / 1,297 = 1.458×**，而参数比是 **1.852×**。
拟合出有效幂律 **`α = ln(1.458)/ln(1.852) = 0.612`**——**远低于我模型里的 1.0（线性）**。
§4.4 那个「逐元素占比稀释」的方向是对的，但**实测幅度（20% 降幅）超出了我给的上界（14.7%）**。

#### ✅ 两个待确认项**都已结案**（其中第 1 项推翻了我自己上一版的解释）

1. **`loss 0.0000 -> 0.0000` 不是「HF 损失记录」的问题，是探针检查点真的坏了。**
   上一版我写「CPU 上实测 train() 模式 loss 是 11.7334，所以只是记录有问题」——
   **那句话是错的**，而且错得很有代表性：我拿一个**别的口径**的数字去解释当前口径的异常。
   实测：`probe_500m` 在 **CPU/fp32、seq=128** 下 logits 就是 `nan`（`finite=False`），
   与 seq 长度、与 autocast 都无关。根因与完整证据链见 **§8.9**：
   `MultiScaleRetention._init_weights` 把逐头门控 `gamma` 置成了 0 →
   批量 chunkwise 的对数空间掩码在对角线算出 `-inf × 0 = NaN`。
   **所以 E3a/E3b/E4a/E4b 是在 NaN 模型上测的。**
   它们的**步时与显存仍然成立**——NaN 不改变任何矩阵乘的形状与次数，显存也由形状决定——
   但这是**推导**，不是实测。已按 §9 的纪律在健康探针上重测（`logs/scale_probe2`，§4.7）。
2. **E2a/E2b 的重编译污染：机制已定位，且**大概率不进入统计量**。**
   `set_checkpoint_layers(n)` 在 `torch.compile` **之前**调用（`bench_trainer.py` L139→L143），
   所以新 K 的图在**第一次前向**就编译，落在 `--warm_skip 12` 的丢弃窗口内；
   `opt_ms` 取的是第 13 步之后的中位数，因此重编译**不进中位数**。
   日志里 `[2/8]` 那 8 次重编译属于 warmup。这一条会在 §4.7 的 V2b（健康探针 + K=16/20）
   里连同**逐步分布**一起复核；在那之前只能算【推导】而不是【实测】。

### 4.7 复测与提速探测（2026-10-11 下午，**健康探针**）——把 §4.5 的推导换成实测

**为什么要复测**：§4.5 的 E3/E4 是在 `gamma=0` 的坏探针上测的（根因见 §8.9）。
NaN 不改变矩阵乘的形状与次数，所以「步时/显存应当仍成立」——但那是**推导**。

#### (a) V 轮复测：旧测量有效，且显存是形状决定的

| 实验 | 旧（坏探针） | 新（健康探针） | 差 |
|---|---|---|---|
| V1a 500M 全量检查点 chunk128 | 1,891 ms / 6.91 GiB | **1,831 ms / 6.91 GiB** | 步时 −3.2%，**显存逐位一致** |

| V2a 600M chunk256 | 10,933 ms / 8.05 GiB | **13,881 ms / 8.07 GiB** | 显存一致；时间 **+27%** |

1. **显存由形状决定，与权重值无关。** 四次复测的 `peak_reserved` 全部逐位一致

#### (c) 更正：E6（CPU 卸载激活）的**算术错了，结论靠本轮实测才立住**

§5 曾把 E6 标为「值得花 20 分钟证伪」，依据是「PCIe 往返 0.17~0.72 s vs 重算 0.052 s
→ 串行慢 3~14 倍」。**那个 0.052 s 错了约 18 倍**：由检查点代价 1.965× 反解，
每优化步的重算成本是 `1,887 − 1,887/1.965 =` **927 ms**（每微步 232 ms），
而要卸载的层边界激活只有约 115 MB/微步——按 PCIe 单向 ~5 ms 算，**卸载看起来比重算便宜一个数量级**。

所以本轮把它当成「最有希望的杠杆」专门去测，**结果相反**：

- 与 `torch.compile` **不兼容**（O5 报错）；
- 不编译时（O6）**卸载不重叠**，每层都在等 PCIe，实测 **6,798 ms**，
  比同条件（不编译 + 检查点）基线 **2,083 ms** 慢 **3.26×**。

**净结果：E6 否决。** 方向上的教训是：文档里那个 0.052 s 让这条被过早搁置，
而它的错误又让它在下一轮被过早看好——**两次偏差都来自同一个没验过的数**。

两条结论：

1. **b4a1 在真实路径上快 7.7%**。每优化步都是
   4×2048 = 8192 token，三种拆法梯度等价，差别只在显存与内核效率。
   （探测里去比 b4a1 与 b2a2 是**比不出来的** —— b4a1 那档没探过，见上。）
2. ⚠️ **真实路径比探测慢 21%**：b2a2 探测 555 ms、真实 672 ms。原因是
   `bench_trainer.py` **没传 `--optim`**（用的是框架默认优化器，不是
   `adamw_bnb_8bit`），且不走 HF Trainer 的完整循环。
   → **以后做预算一律用真实路径的数字，探测值只用于同条件横向比较。**

还有一条**漂移**必须记下：同一次 b2a2 运行里，100 步窗口测出 625 ms、300 步窗口
测出 672 ms（1.64 → 1.51 it/s），期间 GPU 稳定在 327 W / 79 °C / 100% 利用率。
所以步时间有约 **±10% 的热漂移，单点测量不足以外推 12 小时**。

**被否证的一条**：`dataloader_workers`。曾怀疑「取数据与计算不重叠」（`train.py`
里硬编码 `num_workers=0`）是真实路径变慢的原因——实测 workers=0 时 20→100 步
50 s、workers=4 时 51 s，**无收益**。数据集是 memmap + 页缓存，取数本来就接近免费。
开关保留在 `train.py`（默认 0，行为与改动前逐位一致），免得以后有人再试一遍。

#### (f) 这一轮抓到的四个「静默失败」（都不是性能问题，是**判据问题**）

全部由「让真实训练跑起来」这件事逼出来的，且四个都属于同一类：
**日志看着正常，实际没跑／跑错了。** 每一个都补了**能失败**的控制实验。

### 5.1 bf16 主权重为什么不行（可复算）

`【推导】` bf16 只有 7 位尾数，`|w|` 处 ulp = `|w|·2⁻⁷`。用本项目超参 `lr = 1.1e-4`、
典型 `|grad| ≈ 1e-3~1e-2`，一次权重更新是 `lr·grad ≈ 1.1e-7 ~ 1.1e-6`：

| 权重绝对值 | 格式 | ulp | **ulp / 更新** |
|---|---|---|---|
| 0.1 | bf16 | 7.81e-4 | **710 ~ 7,102×** |
| 0.01 | bf16 | 7.81e-5 | **71 ~ 710×** |
| 0.001 | bf16 | 7.81e-6 | **7.1 ~ 71×** |
| 0.01 | fp16（10 位尾数） | 9.77e-6 | **8.9 ~ 89×** |

**12 组里 11 组的更新量比 ulp 小 7 倍以上** → **这次更新根本改变不了那个权重**。
这不是精度损失，是**梯度被静默吞掉**。`lr` 再小只会更糟。fp16 也不行。
**这就是所有框架都保留 fp32 master 权重的原因**，也是那 2,286 MiB 拿不到的原因。

| 来源 | 量 | 依据 |
|---|---|---|

> 本项目 **seq=2048、E≤6**，理想路由下 `cf` 只要 **1.04~1.09**——**长序列在这里帮了忙**。
> 这是唯一一条对 MoE 的正面证据，但它要求路由确实学得均匀（需负载均衡损失配合）。

## 7. MoE 的反面证据（省略任何一条都是误导）

| # | 反面证据 | 后果 |
|---|---|---|
| 1 | **名义参数 ≠ 稠密容量**。MoE 尺度律（[arXiv:2402.07871](https://arxiv.org/abs/2402.07871)）是在**等激活算力**下优于稠密；**同 `P_total` 的 MoE 明显弱于同 `P_total` 的稠密** | 692M/272M-active **不等于** 692M 稠密。`docs/04` §4 那条「≥0.5–1B」的证据是**稠密**的，**用它论证 MoE 的名义参数量无效**（而且那条证据本身也已降级，见 §8.2） |
| 2 | **每专家数据被稀释**：top-1 下每个专家只见 1/E 的 token | 272M 已只有 ~2.5 token/参数，再除 5 = **0.5 token/参数**。E 越大越糟 |
| 3 | **会打断 `torch.compile`**：数据相关的专家分桶让形状变化。而本项目 **2.41× 的提速全部来自 compile + 融合** | 必须用固定容量路由（cost 见上表）。**这是最大的工程风险** |
| 4 | 单卡、batch 1 | 无专家并行；分桶后每个专家 GEMM 的 M 从 2048 降到 ~2048/E，加剧已知的 occupancy 问题 |
| 5 | 需要路由器 + 负载均衡损失 | 在 272M 尺度是纯负担 |
| 6 | **本项目零证据** | 模型代码里没有 MoE。要做先加实现 + 负载均衡 + 固定容量，再跑 A/B |

**结论：MoE 能兑现「0.69B 名义参数 @ 现状步时 + 40%」，但它兑现的不是用户要的那个 0.69B。**
直接当「神秘训练技术」用，最可能**同时付两份代价**：名义参数没换来能力（第 1、2 条），
工程复杂度又吃掉了 compile 的收益（第 3 条）。

## 8. 路线建议与实验清单

### 8.1 分叉点

> **前提**：用户已经决定扩到 0.5B~0.6B（「我决定了」）。所以本文的任务是**怎么做**，
> 不是**要不要做**。§8.3/§8.4 的那些证据**不构成否决**——它们改变的是**收益预期**，
> 以及给出一个**配套**动作（见下面的第 0 条）。

| 路线 | 名义参数 | 步时 | 主要风险 |
|---|---|---|---|
| **B. 0.5B 稠密**（推荐先做） | 504M | **1.79~2.26×** | 状态余量 2,052 MiB；**实测 peak_reserved 7,076 MiB → 真实余量 517 MiB**（三者中最宽裕） |
| C. 0.6B 稠密 | 599M | **2.10~2.68×** | ❌ **实测装不下**（reserved 8,376 MiB > 可用 7,593 MiB） |
| D. MoE E=6 | 692M | 1.33~1.51× | §7 六条，尤其第 1、3 条 |
| （A. 272M + 只喂数据） | 272M | 1.00× | 仅作**对照**，不是替代方案 |

**建议顺序**：

0. **把「修数据 + 1 epoch 对照」当作扩容的配套，而不是扩容的替代。**
   理由：`docs/17` 指出 v13 有 **8.9% 未闭合样本、10% 答案被砍断、只跑到 0.19 epoch**。
   如果能力损失有一部分来自这些数据缺陷，那么**在缺陷数据上花 2.1~2.7× 的步时扩到 0.5B，
   等于用更大的模型去拟合更差的数据**——钱花了，能力买不到。
   这一步成本 **0.5 h CPU + 13.4 h 训练**，相对 0.5B 的永久步时代价可以忽略。
   **它不阻塞扩容，它是让扩容的投资能回收的前提。**
1. **用 B（0.5B 稠密）落地**：实测真实余量 517 MiB（三者中最好，但**并不宽裕** ——
   L1 与 chunk 调优基本没有试错空间，凡是要额外显存的改动都得先量再上），
   且它是三个候选里步时代价最低的稠密方案。
2. **在 B 上先做 E1→E3 的实测**（§8.6），把本文的预算与步时推算换成实测。
3. **B 跑出结果后再考虑 C 或 D**：C 只是再付 0.35× 的步时换 19% 参数；
   D 要先解决 §7 第 1、3 条（名义参数≠容量；会打断 compile）。
4. **无论走哪条，都同时把 token/参数 从 2.5 提上去**（§8.6 末表：20 token/参数的位置在
   5.4 B（272M）/ 10.1 B（0.5B）token）。

### 8.2 落地清单（按「先做哪个」排）

### 8.5 生长脚本：`scripts/grow_500m.py`（本轮补齐，已实测通过）

§8.2 第 2 步原先**没有工具**——`grow_272m.py` 只做 143M(d768)→272M(d1024)。
本轮补上并实测：`【实测·同条件】`（同一进程内新旧模型对同一输入的 logits 逐元素比较，
CPU、seq=128、fp32，无 GPU 参与；数字由 `grow_500m.py --verify` 直接打印）

```powershell
python scripts\grow_500m.py --src checkpoints\retnet_272m_v13 `
    --dst checkpoints\retnet_500m --verify
```

实测结果（**CPU 上完成，不需要 GPU**）：

| 检查 | 结果 |
|---|---|
| 参数量 | **504,179,896** —— 与 `probe_500m`、meta device 三方逐位一致 |
| 形状 | d=1408 / L=20 / H=22 / vdim=ffn=2816 ✓ |
| **函数保真** | max\|Δ logits\| = **2.232e-04**（噪声地板 1.326e-04，见下） |
| 落盘后可再加载 | ✓ `from_pretrained` + 前向可跑 |

**两个会让生长静默失效的坑**（都真实踩到，且都**不报错**）：

1. **归一化切点必须继承源模型的原始值 `growth_old_dim=768`，不能取"当前宽度" 1024。**
   `GrowthLayerNorm.forward` 只把前 `old_dim` 维当成**一个** LayerNorm 切片
   （见 `modeling_retnet.py:284`）。272M 本身已经是 768→1024 的产物，若再按 1024 切，
   前 768 维的归一化统计量就变了 → 不保真。
   ⚠️ `checkpoints/probe_500m` 的 config 写的是 `growth_old_dim=1024`；那是**随机权重探针**
   （参数总量与切点无关），**不能当配方**。
2. **配置字段必须一并继承**：`mode`（源是 `chunkwise`）、`chunk_size`、`prompt_loss_weight`、
   `embed_scale`。第一版漏了 `mode`/`chunk_size`，新模型落到别的保留模式，
   **数学等价但数值不同** → 保真校验给出 **1.9**（差四个数量级）。

**容差 1e-3 的来源（是量出来的，不是放松出来的）**：同一个模型、数学等价的两种算法实测
max\|Δ logits\|：chunkwise(64) vs chunkwise(128) = **0.000**；vs **recurrent** = **1.326e-04**。
加宽会改变 matmul 的归约维（K: 1024→1408，多出部分是 0），**数学等价、浮点不等价**，
所以保真校验**不可能**为 0。取 1e-3：高于地板 7.5 倍、低于真 bug 1900 倍。
脚本在**校验失败时拒绝落盘**，避免静默产出一个"生长过但不保真"的检查点。

### 8.9 🚨 前置缺陷（**已修复**）：修复前，当前代码**无法从零训练**

> 这是本方案落地前必须先解决的东西：**所有候选配置在修复前都跑不起来**，
> 而且失败方式是「静默 NaN」而不是报错。发现过程见下，可复算。

#### 8.9.1 症状：探针前向恒为 NaN，但权重全都「有限」

重测 E3/E4 时发现 `checkpoints/probe_500m` / `probe_600m` 的前向**在任何序列长度下都是 NaN**：

| 检查 | 结果 |
|---|---|
| 权重有限性（365 个张量） | **全部有限，0 个非有限** |
| logits absmax，seq = 128 / 256 / 512 / 1024 / 2048 | **全是 nan** |
| fp32 与 bf16 autocast | **都 nan** |
| 模块级 forward hook 的断裂点 | 第一个「输入有限、输出 NaN」= `blocks.0.msr`（输入 absmax 4.27）；`msr.group_norm` **输入已非有限** |
| 四个投影 `q/k/v/g_proj` | 输出全部有限 |
| **参考路径**（`FAST_CHUNKWISE=0`） | **有限，loss = 3.0596** |
| **批量路径**（`FAST_CHUNKWISE=1`） | **nan** |

> ⚠️ **第一课：在权重上做有限性扫描抓不到这个 bug。** `gamma = 0` 是**有限值**，
> `isfinite` 一路放行。必须在**前向**上验，而上一轮我恰恰是在权重上验的。

#### 8.9.2 根因：一条「兜底 bias」的初始化规则，实际打到的是门控

`retnet_hf/modeling_retnet.py`：

```python
def _init_weights(self):
    for name, p in self.named_parameters():
        if name.endswith("_proj.weight"):
            ... xavier ...
        elif isinstance(p, nn.Parameter) and p.dim() == 1:
            nn.init.zeros_(p)        # ← 本意是兜底 bias
```

`MultiScaleRetention` 里所有 `_proj` 都是 `bias=False`，所以**唯一的 1 维 Parameter 就是
`gamma`**（`num_heads` 维的逐头门控）——这条「兜底 bias」的规则把**门控置成了 0**。

于是 `retention_fast._decay_tables` 的对数空间掩码炸了：

```python
log_gamma  = torch.log(gamma)                      # gamma = 0 → -inf
inner_mask = torch.exp(log_gamma[:, None, None] * expo[None])
#            expo 是对角线为 0 的下三角指数 → -inf * 0 = NaN
inner_mask = torch.where(causal, inner_mask, 0)    # ← where 只丢结果，不阻止 NaN 被算出来
```

参考实现用的是 `gamma ** delta`，`0**0 = 1` 是**良定义**的 —— 所以两条路径
**在 γ=0 处不等价**，这也正是「参考有限、批量 NaN」那条反差的来源。

**同一个 bug 的第三个受害者**：`group_norm.weight` 也是 1 维 Parameter，也被置了零
→ `_head_group_norm` 输出恒为 0 → `F.silu(g) * 0 = 0` → **retention 支路在初始化时
贡献恒等于 0**，模型开局等价于「没有注意力的一摞 FFN」。

#### 8.9.3 为什么整套测试都没发现它

| 为什么漏掉 | 证据 |
|---|---|
| `RetNetHFConfig.use_gla` **默认为 `False`**，此时 `gamma` 是 **buffer 不是 Parameter**，`isinstance(p, nn.Parameter)` 判据把它排除了 | `use_gla=False` 时 `named_buffers()` 含 `gamma`，`named_parameters()` 不含 |
| `test_fast_chunkwise.py` 的单元级用例用的是**独立 `MultiScaleRetention(cfg)`**，根本不经过 `_init_weights` | 该用例的「默认初值」实得 0.96875…0.99997（正确值） |
| **模型级等价用例是空过的**：`group_norm.weight = 0` 让 retention 支路输出恒为 0，两条路径当然逐位相同 | **实测**：把 `group_norm.weight` 置 0 → 两路径相对差 **0.000e+00**；置 1 → fp32 差 **8.6e-7** |

> ⚠️ **第二课（比第一课更贵）：一个「永远会通过」的检查等于没有检查。**
> 那个等价用例在旧初始化下**结构上不可能失败**——它比较的是两个全零贡献。
> 直到我把初始化修对，它才第一次真的开始比较，并立刻暴露出自己的阈值标定错误：
> 它在 **bf16 autocast** 下卡 `rel_mean < 1e-5`，而 bf16 只有约 3 位十进制有效位
> （实测 fp32 8.6e-7 vs bf16 4.8e-3）。**阈值必须和被比较的精度匹配。**

#### 8.9.4 影响范围：只有「从零构造」受影响，`from_pretrained` 不受影响

| `gamma`（首层） | 16 头，min 0.660300 | **22 头，min 0.660300 / max 1.000000**，0 个零 | ✅ 旧头照搬 + 新头公式值 |
| `group_norm.weight` | min −0.816308 | **min −0.816308 / max 1.000000**，0 个零 | ✅ 新头 weight=1，**未被置零** |
| **seq=2048** loss | 7.545864 | **7.545865** | ✅ **\|Δ\| = 4.768e-07** |
| seq=2048 批量路径 | 有限 | 有限 | ✅ |
| seq=2048 参考路径 | 有限 | 有限 | ✅ |
| 两路径 logits 最大差 | 2.06e-4 | 2.25e-4 | ✅（bf16 量级一致） |

**loss 在 seq=2048 上对上到 `4.8e-07`**，说明生长在这个长度上确实是函数保真的
（脚本自带校验只在 seq=128 报 `max|Δ logits|`，本轮实测为 `1.545e-04`；
`docs/23` §8.5 上一版记的是 `2.232e-04`——两次的数不同是因为校验输入没有固定种子，
两个值都远在容差 `1e-3` 内，但**报一个不可复现的精确数并不合适**，这里改为记区间）。

**结论**：

| 路线 | 是否受本缺陷影响 |
|---|---|
| **B. 0.5B（`grow_500m.py` 生长 + 继续训练）** ← 用户选定 | **不受影响**。`tasks/v15_500m.json` 的 `model_dir` 是生长产物，`gamma`/`group_norm.weight` 都从权重读入 |
| 任何**从零初始化**的新尺寸（含新加模块、新头、新基线） | **受影响**。修复前 `fast_chunkwise=true` 会 NaN；改回参考路径也会从「没有注意力」的状态开局 |

> 但要看清一件事：**这次能幸免，靠的是 `grow_500m.py` 恰好绕开了那条初始化规则，
> 不是靠检查发现的。** 若当初生长脚本改用 `RetNetForCausalLM(cfg)` + 拷贝可拷贝的权重，
> 这个 NaN 会直接进到 0.5B 的训练里，而且在随机权重探针上**同样表现为 `loss 0.0000`**——
> 与我在 §4.5 一度当成「HF 记录问题」的那个现象一模一样。

## 9. 口径纪律

任何两个数相减/相比之前，先各自回答「这个数是在什么条件、哪台机器、哪次运行下测的」；
拿不到同口径的第二个点就写「**不可比**」。本项目已因违反它返工**六**次：

| # | 类型 | 具体 |
|---|---|---|
| 1 | 跨机器 | 笔记本 `nvidia-smi`(7,226 MiB) − 桌面 `reserved`(6.61 GiB) |
| 2 | 跨 regime | 关检查点的实测 vs 开检查点的估算 |
| 3 | 跨冷热 | 冷评测 95.5 s vs 热评测 57.3 s |
| 4 | 自证不足当物理 | 激活枚举不完整，却当成「2,077 MiB 无法解释」 |
| 5 | **跨微批形状** | 拿 `903(batch4)/713(batch1×accum4)` 当检查点代价 |
| 6 | **跨 chunk 口径** | 拿 chunk 128 的 MAC 除以 chunk 64 的基准（锚点行会算出 722 而非 713） |
| 7 | **跨进程争资源** | 同一张 8 GB 卡上跑了两个训练进程 → 显存颠簸，健康进程 0.79→3.19 s/步（详见 §9.1） |

**四条加固纪律**：

1. **模型必须有锚点行**：任何预测脚本都要含一行「现状配置」，且必须**逐位复现实测值**。
   本文 `flops_model.py` 现状行 = 713 ms（实测 713）、272M 参数量 = 272,304,448（逐位）。
   锚点行算不对 → 口径错了，不是「有一点误差」。
2. **引用别人的结论前先确认问题相同**。本文曾用 `docs/16` §7.1「+31% 显存买 −17% 算力」
   否决 MoE——但 §7.1 问的是「MoE 能不能**省算力**」，而用户问的是「能不能**加参数不加算力**」。
   **引用的算术可以复核，引用的「问题设定」不会自己提醒你它答非所问。**
3. **区间优于点值**，且要说清区间来自哪两个自由参数的端点组合。
4. **同卡不跑第二个 GPU 作业，按设备实例判断，不按「我这台机器」判断。**

### 9.2 🚨 运行事故 2：**600M + 分页优化器把桌面整机弄崩两次**（2026-10-11）

这一条比 §9.1 严重：§9.1 只是拖慢，这一条是**整机冻结 + 一次内核蓝屏**。

#### 事故经过（全部为系统事件日志 `【实测】`，非推断）

| 时刻 | 事件 |
|---|---|
| 07:33:06 | 驱动第二轮启动 **E5b：600M + `paged_adamw_8bit`、chunk128**（第 1 次） |
| 07:35:18 | **`nvlddmkm` 事件 153**（显示驱动故障） |
| 07:49:18 | 生成 minidump `101126-13906-01.dmp`；07:49:21 事件 1001 报 **BugCheck `0x0000003b`**（`SYSTEM_SERVICE_EXCEPTION`，参数 1 = `0xc0000005` 访问违例） |
| 07:49:06 | 重启进入下一个会话 |
| 08:08:06 | 我**重新启动同一个 E5b**（第 2 次） |
| ~08:10:04 | E5b 训练**正常跑完 118 s**（结果有效，见下） |
| **08:10:42.527** | **再次 `nvlddmkm` 事件 153 —— 这是系统冻结前最后一条系统事件** |

| 08:15:15 | 用户强制重启后开机（事件 41 / 6008 记为「意外关闭」） |

**两次 E5b，两次 `nvlddmkm` 153。本机 10 个实验里只有这个组合出过该事件，其余一个都没有。**

#### 机制（推断，方向明确）

`bitsandbytes` 的分页优化器把优化器状态放在 **CUDA managed / 统一内存**（`cudaMallocManaged`）。
600M 在这块 8 GB 卡上 `peak_reserved` 本来就已经 **7.39 GiB（分页）/ 8.18 GiB（非分页）**，
统一内存超额后驱动必须不停在 host↔device 之间迁移页；Windows 的 **WDDM 显示路径**会被拖住，
于是先报 `nvlddmkm` 153，再整屏冻结。这和 §9.1 的「显存颠簸」是同一个物理根源，
只是这次颠簸发生在**统一内存**上，代价从「变慢」升级为「系统无响应」。

**我一度无法解析蓝屏调用栈**（minidump 需管理员权限、本机没有 WinDbg/`kd`），当时只能把它记为推断。
**现已解析出结论，这条从「推断」升级为「实测」**：

那份转储是 `PAGEDU64` 格式（不是用户态 `MDMP`），我直接解析了它的 `DUMP_HEADER64` 与
`TRIAGE_DUMP64` 驱动表（`scripts/analyze_kernel_dump.py`）：

| 项 | 值 |
|---|---|
| BugCheck | **0x3b** `SYSTEM_SERVICE_EXCEPTION` |
| Param1 | `0xc0000005`（ACCESS_VIOLATION） |
| Param2 = **出错指令地址** | **`0xfffff8067b13a4a0`** |
| Param3 / Param4 | `0xffff8b80c4266350` / `0x0` |
| 与事件日志 1001 的四个参数 | **逐位一致**（证明这份就是那次崩溃的转储） |
| 驱动表 | 231 项，全部解析出名字 |
| **地址归属** | ✅ **`nvlddmkm.sys`**，基址 `0xfffff8067b0b0000`，大小 108,277,760 字节，**偏移 `+0x8a4a0`** |

字段布局不是凭记忆猜的，而是**用自洽性实测定的**：每个条目 144 字节
（`231 × 144 = 33,264 = StringPoolOffset − DriverListOffset`，恰好整除），
`DllBase` 在偏移 `0x38`、`SizeOfImage` 在 `0x48` ——
判据是这组解释下 231 个模块**两两重叠 0 次**，而换成另一组候选字段则有 **71 次**重叠。
另有独立印证：同一次解析里 `ntoskrnl.exe` 拿到 17,063,936 字节、`dxgkrnl.sys` 3,842,048 字节，
量级都正常。

**我一度写成「根因是驱动本身不稳定，我的实验只是触发器」——这个框定被证据推翻了，必须更正。**

用户提供了一个关键事实：**在本次实验之前两个月，这台机器从未这样崩溃过**；
前天昨天还连打几小时全高画质游戏，没有任何卡死。于是我做了对账：
把 7 次 `nvlddmkm` 故障逐一对上当时**有没有我的 GPU 任务在写输出**——

### ⚠️ 关于 `check_doc_invariants.py` 的元教训（检查器本身必须做阳性对照）

这个检查器**写了四版才真正有效**，每一版的失败方式都值得记：

| 版本 | 缺陷 | 它报什么 |
|---|---|---|
| v1 | 查「同一行里 GiB 与 MiB 自洽」 | 2 个误报；而真 bug **跨两行两张表**，根本查不到 |
| v2 | 语义对了，但真值文件里每个标签出现**两次**（前沿行 + 显存分项行），后写覆盖了前沿行 | **一次比对都没做**，却报 ✅ |
| v3 | 容差按 MiB 算、拿去比 **GiB** → 容差 = **5.63 GiB** | `3.28 GiB` 与 `3.20 GiB` 被判**相等**，报 ✅ |
| v4 | 加「文档自身算术」（不依赖外部真值） | ✅ 有效；并抓到本节列的三个内部矛盾 |

**最关键的一条：检查器本身必须做阳性对照。**
v2 已经加了「比对次数为 0 就判失败」的空转守卫——但 v3 的 16 次比对**确实发生了**，
只是全部因为容差过大而通过，**空转守卫拦不住**。
只有把已知错误灌进去、确认它**会失败**，才能说检查器有效。

现在共 **约 42 项**检查（外部对真值 16 + 文档自身算术 13 + 跨文档引用 13），
