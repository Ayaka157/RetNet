2. **`scripts/reinit_gamma.py` 是错的**：它按 `n = len(gamma_keys) = 20 层` 生成 20 个值，再 `torch.full_like` 灌满每层 22 个头 → 每股只拿到**按层号**的值，而 docstring 写的是"按头 h"。而且 `--formula orig`（0.9688–0.99997）比实测能工作的 ep3 值（活头中位 0.848）高一大截。
3. **半衰期 1.22 token 与 held-out 3.2194 在数学上矛盾**：我在 CFE val 上量了经验条件熵，**二元熵 H(next|1 prev)=4.728 nats**。模型能到 3.2194，说明它至少用了 2 个 token 以上的上下文。原因是"单头半衰期"≠"网络感受野"：20 层、每层 1/(1−γ) 的等效跨度叠加，v21 约 **65 token**、ep3 约 **130 token**。所以"有效上下文只剩 1 token"这句我**不认**，"远距离上下文基本没用上"我**认**——后者用 §5 的探针量化，不靠嘴。

## 1. 结论（3 句）

**选救援：在 `checkpoints/retnet_500m_v21_export` 上继续训，不缩壳、不重训、不生长。**
**预算 ¥187（13.4 GPU 小时、4.65B token，其中 0.1B 是给对话复健的），把域内 held-out（5 文件加权）从 3.5023 压到 3.15–3.30，判据 3.2659 我估六成能踩过；踩不过的最小可交付是"比 ep3 好 0.13 nat 的权重 + 一套不再白烧钱的代码 + 一张测出来的斜率表"。**

### N01–N04 我新发现的问题（不在 00 表里，但会直接影响这一轮）

- **N01 `scripts/reinit_gamma.py` 与它自己的 docstring 不符**：`n=len(keys)=20`（层数），循环写成 `for h in range(n)` 再 `torch.full_like(sd[k], g)` → 每层 22 个头被灌成同一个值，而 docstring 说的是"按头 h=0..21"。同时 `--formula orig` 给 0.9688–0.99997，换算成半衰期是 **21.8–33M token**，而实测能工作的 ep3 活头中位 0.848 只对应 **4.2 token**——不是"稍微激进"，是换了个模型。
  **改法**：新增 `--from-checkpoint checkpoints/retnet_500m_v15b_ep3`，**逐头**拷贝活头的 gamma（死头保持原值，它们不参与前向）。
- **N02 00 表的"gamma 中位 0.5656"不能用**：它是 22 头混算，45% 是死头。活头 0.848(ep3) → 0.693(v21)，v21 这一段被 wd 吃掉 **×0.82**，层 0 的活头从 0.27–0.62 塌到 0.11–0.23。**这才是 2.8471→3.5023 最像的元凶**（层 0 感受野从 1.3–2.4 token 掉到 1.1–1.3）。
- **N03 层 18/19 全宽活**（见 §0）→ 缩核不可行，吞吐只能按 504M 壳算：**¥35.3/1B token**，不能按 157M 核的 ¥13/1B 算。
- **N04 上一轮所有 held-out 数字都是 `mode=parallel` 测的**（`eval_holdout.py:62`），而训练是 `chunkwise`。E16 修完后基线会变，**判据必须转成 delta**，否则我们会拿两个不同函数比大小。

### 3.3 重复（这是本方案**最硬的约束**，比钱硬）

- 本预算的**预训练部分** 4.55B 里中文 token ≈ **3.391B**，本地中文唯一只有 **1.247B** → **中文要过 2.72 遍**。`[推算]` 3.391/1.247。
- 之前已经过多少遍，**只算得清一段**：v21 的 Stage 0 在 `pretrain_v2` 上跑了 35,205 步 = 2.307B token（不含 skypile），中文 54% → 1.25B 中文 ≈ **1.0 遍**；更早的预训练轮次（v13/v14 用的 `pretrain_merged` 1.317B）遍数无法从现存文件确认。**保守估：本轮之后中文累计 3.7–4.7 遍**（1.0 + 2.72 + 更早的 0~1 遍）。
- 另一条相关的事实：**ep3/v21 的起点是 `chat_pack_v13` 上 3 个 epoch 的对话 SFT**（`tasks/v15_500m.json`、`v16_ep2`、`v17_ep3` 的 `data_dir` 全是 `chat_pack_v13`，16,848 步/epoch × 65,536 = 1.104B token/epoch）。`[实测]` 所以本轮之后**对话能力一定退化**，这不是副作用，是预算的直接后果——P6 的 0.1B SFT 复健就是为它准备的。
- 处理办法（不是消除，是盯住）：
  1. 训练/验证 gap 停机规则（§6 S3）：`train_loss` 低于 `val_cfe` 超过 **0.60** 就停。
  2. 英文不重复：M1/M2 用**不同分片**，各 1 遍。
  3. 退火段只做 0.40 遍，且 LR 已降到 2e-6。
- **`pretrain_merged`（1.317B）不用**：来源与 `pretrain_v2` 无法区分（它俩的 token 计数对不上任何单一来源），本机没有 tokenizer 也解不开，**宁缺勿重**。
- **`chat_pack_*`（v13 共 552M token）不做预训练语料**：对话分布，会拉偏 CFE/wiki。只留给 P5 的可选 SFT。

### 3.4 缺 eos 怎么办

- `pretrain_v2` **不缺**：`prepare_pretrain_v2.py:129-131` 每条 append bos/eos，实测 eos 密度 0.071%（每 1,409 token 一个）。`[实测]`
- 因此 E12 的"固定宽度切片"在这份数据上是**可接受的**：2048 窗里平均 1.45 个边界，被算错的 token 只占 1/2048 ≈ 0.05%，我估对 loss 的影响 ≤0.02 nat。
- 但**必须上审计**（§6 S6）：开阶段时抽 1,000 行，eos 率 0 → 整包无边界 → 停机。这条同时替 E09/E10 站岗。

### 3.5 代码语料没了怎么办（硬缺口，我明确说清楚）

**事实：本地没有任何代码包。** `hf_pack_code`（1.64B）、`hf_pack_code2`（4.49B）、`hf_pack_prog` 与原始 parquet 都被 `_data_supervisor` 的 `rmtree` + `gc_stage` 双杀（E13），**不可重建**。`[实测：目录不存在]`

替代只有三条，按价值排序：

1. **权重继承（主）**：v21 的计划里代码段约 **5.4B token**（`code_ling` 0.885B + `code_ling2` 4.49B，`[文档] plan_ddp2.json`）；实际跑到哪一步没法从现存文件确认，但 2.8471→3.5023 的偏移（中文变差、cosmopedia/数学变好）证明代码/教材段确实跑了一大截。这一轮不喂代码，只要别把它冲掉。对冲手段 = 混料里保留 **26.7%（M1）/ 32.7%（M2）** 的英文教材/数学（cosmopedia+fineweb+open_web_math），这三类与代码在"符号密度"上最接近。
2. **SFT 复健（已计入预算，P6，¥4.0）**：跑 **0.1B**（1,526 步）在 `data_cache/chat_pack_v13` 上，LR 5e-6 恒定、`packed` 模式、`val.ids.npy` 排除。只为保住对话/代码块的**输出格式**，不指望抬 held-out；跑完**必须重测 held-out 并分开报告**（两套导出，见 §4 P6 行）。
3. **不许声称**：发布说明里不能写"代码能力保持"。要测就花 ¥3 跑 `scripts/capability_eval.py` 的代码子集（附录 A 第 6 条），否则不写。

**这轮换来的模型，代码能力一定比 v21 弱**——这是硬缺口的价格，不藏在预算表里。

## 5. 便宜的否决测试（¥30.7，≤¥50 ✅）

**要回答的问题**：中文 held-out 到底还有没有救？如果头 0.25B token 的斜率不够，后面 4B 也到不了判据，必须当场停。

### 5.1 为什么这三个数字能回答

- 判据要求 5 文件加权 **3.2659**，起点 3.5023 → 差 **0.2364**。`[推算]`
- CFE 占权重 **42.66%**（1,900,544/4,454,400）。按其余四域各改善 0.08–0.18 推算，**CFE 必须 ≤3.43**（算式 §8）。起点 3.8605 → **CFE 要降 0.43**。
- 4.55B 上摊 0.43 = **0.095 nat/B** 平均。收益递减意味着**头 0.5B 的斜率至少要是平均值的 3 倍**（0.28/B），否则后面 4B 补不回来。这就是 G1 的阈值来源，不是拍脑袋。

### 5.2 四个门（任一不过就停）

| 门 | 何时测 | 测什么 | 阈值 | 不过怎么办 |
|---|---|---|---|---|
| **G1a** | step 3,815（0.25B，≈¥11 累计） | CFE val | **≤3.79**（斜率 ≥0.28/B） | 停。走 §7-A。 |
| **G1b** | step 7,629（0.5B，≈¥21 累计） | CFE val + 5 文件 avg | **CFE ≤3.72** 且 **avg ≤3.42** | 停。走 §7-A。 |
| **G1c** | 同 G1b | ① 活头 gamma 中位 ② 远距探针 `Δ_ctx` | ① **≥0.72**（起点 0.693，证 no_decay_1d 生效且学习在往上推）② `Δ_ctx ≥1.15×基线` 或 `≥0.10` 绝对值 | ① 不过 → E06 没生效，**立刻停**（不是调参，是代码错）。② 不过 → 见 §5.4。 |
| **G2** | A2 结束（0.75B，≈¥31 累计） | 5 文件 avg | **≤3.39** → 直接进 B；**3.39–3.46** → 只有"A2 比 A1 末改善 ≥0.03"才进 B；**>3.46** → 停 | 停。走 §7-B。 |

### 5.3 两个探针怎么算（`eval_holdout.py` 加两个参数，约 40 行）

1. **`--by-position`**：把 4,463,629 token 的 val 窗口按位置分 8 桶（0–255 … 1792–2047），各桶单独报 loss。用途：看模型是不是"越往后越省"，以及**是否在 256 之后就走平**（走平 = 感受野 <256）。
2. **`--ctx-ablation`**：对每个窗口算两次 loss——`L(2048)`（全上下文）与 `L(256)`（只喂最后 256 token），**只统计最后 256 个位置的 loss**。`Δ_ctx = mean(L(256) − L(2048))`。这是"远距离上下文到底有没有用"的直接测量，不受 gamma 参数解释的影响。
   - 基线（P1）先测一次。**如果基线 Δ_ctx 已经是 0**，说明模型根本没用 256 以外的上下文，那么 A 段的全部收益只能来自"本地 n-gram 拟合"，B 段的天花板会低很多——这种情况下 G1b 的 avg 阈值要**收紧到** 3.36（更严）才准进。

### 5.4 G1c 的 ② 不过时（gamma 没修好，但 CFE 在降）

不推翻结论，改 A2 的内容：**跳过"还原 ep3 gamma"，改成只做 0.25B 同分布续训**，把省下的 ¥9.7 加给 B1（+0.25B token）。理由：CFE 在降说明"数据+LR"这条腿在起作用；此时动 gamma 只是引入一次分布突变。**A2 的预算不取消，只改用途。**

## 6. 停机规则（写死成 if）

每 200 步（≈2 min）跑一次 `check()`；`spend` 用云账单口径，不用估算。

```python
# S1 gamma 被衰减（E06 失效）——最优先，因为它会让后面 4B 全白跑
if step >= 500 and median(gamma_live) < 0.95 * gamma_live_at_step0:
    abort("E06 未生效：gamma 仍在被 weight decay 拉低")
    # 动作：不发新任务，改代码；回滚目标 = 无（权重未被破坏）

# S2 held-out 恶化（连续两次）
if n_evals >= 2 and avg_now > best_avg + 0.05 and avg_prev > best_avg + 0.05:
    stop_graceful(); restore(best_ckpt)          # best_ckpt = val_pack 上最优的那个 checkpoint-*
    # 只在 best_ckpt 与当前差 >0.05 时恢复；否则恢复反而引入二次扰动

# S3 loss 异常低（重复数据的信号）
if cfe_val < 3.00 and step < 30000:              # 起点 3.8605，30k 步内低于 3.00 不合物理
    stop_graceful(); restore(best_ckpt); audit("疑似重复/泄漏：查 M1 分片是否重复、val 是否在训练集里")
if train_loss_200 < cfe_val - 0.60:               # 记忆化
    stop_graceful(); restore(best_ckpt)

# S4 训练低于验证（泄漏）
if train_loss_200 < val_avg - 0.25:
    stop_graceful(); audit("val 进训练集：跑 E14 的交集断言")

# S5 显存不足
if OOM and batch == 16:  batch = 12; steps *= 16/12; restart_from(last_ckpt)   # token 预算不变
elif OOM and batch == 12: batch = 8;  steps *= 12/8;  restart_from(last_ckpt)
elif OOM and batch == 8:  stop_graceful(); restore(best_ckpt)   # 不降 seq_len（2048 是判据的一部分）

# S6 数据不对（开阶段时一次）
if eos_rate(sample_1000_rows) == 0:  abort("整包无边界（E09/E10 复发）")
if shard_count(stage) < min_shards and waited_steps > 200:  stop_graceful()

# S7 超时/超预算
if spend >= 196.0:  ctrl("next-checkpoint")      # 落盘后优雅退出，不走 taskkill
if wall_clock_h >= 15.5:  ctrl("next-checkpoint")

# S8 计划被改坏
if plan_file_parse_error or total_steps decreased mid-run:  stop_graceful()
```

| 规则 | 触发条件 | 动作 | 回滚到 |
|---|---|---|---|
| S1 gamma | 500 步时活头中位 <0.95×起点 | 立刻停，改代码 | 不回滚（权重没坏） |
| S2 恶化 | 连续两次 eval 都比 best 差 >0.05 | 优雅停 | `best_ckpt`（val_pack 最优） |
| S3 异常低 | CFE<3.00 且 step<30k；或 train 比 val 低 0.60 | 优雅停 + 审数据 | `best_ckpt` |
| S4 泄漏 | train 比 val_avg 低 0.25 | 优雅停 + 跑 E14 断言 | `best_ckpt` |
| S5 OOM | 逐级降 batch 16→12→8 | 改 batch 并**按 token 重算 steps** | 最近 checkpoint |
| S6 数据 | eos 率 0 / 分片不足 200 步 | 停机或等料 | 不适用 |
| S7 预算 | spend ≥¥196 或 ≥15.5h | `ctrl next-checkpoint` | 不适用 |
| S8 计划 | 解析失败 / 总步数被下调 | 优雅停 | 不适用 |

> S5 的要点：**钱由 token 决定，不由 step 决定**。降 batch 后必须把 steps 乘回去（16/12），否则同样的钱少买 25% token。
