# B · 长上下文缺陷与参数损伤（独立调查）

调查对象：`checkpoints/retnet_500m_v21_export/`（504,179,896 参数，fp32，训练窗口 2048，计划步数 159,857）。
所有数字来自我自己读代码 / 读权重 / 跑前向，脚本在 `%TEMP%\b_analysis\`，未修改仓库任何文件。
标注约定：**【实测】**＝我跑出来的；**【代码】**＝读代码直接推出；**【猜测】**＝未验证的判断。

---

## 1. 结论摘要

1. **这个 504M 模型里有 338,196,736 个权重（67.08%）是精确的 0**，非零权重只有 165,983,160（32.92%）。原因是宽度生长时把新维度零填充，而生长后的 `gamma_new`/`beta_new` 从头到尾都是 0，于是新维度被永久隔离、永远拿不到梯度。**有效模型只有约 166M 参数、d_model 实际是 768。**【实测】
2. **衰减参数已经练废**：440 个 `msr.gamma` 的中位数是 **0.5659（半衰期 1.22 token）**，96.1% 的头半衰期 < 128 token，**最大只有 604 token**（L2/h11）。而 chunk 大小是 128：一个头要跨 chunk 传信息，必须 γ^128 不小，实测只有 17/440 个头 γ^128 > 0.5。**【实测】**
3. **实测有效上下文 ≈ 300–400 token**：把 1792 token 之前的内容全部替换成随机 token，最后一个 256-token 区间的 loss 只变化 +0.005（d=512，4 窗口）；d=256 时 +0.031，d=128 时 +0.174，d=0 时 +0.479。换言之 **2048 窗口里约 80% 的位置对预测没有贡献**。**【实测】**
4. **跨 chunk 信息只走一个通道**：每层每头一个 `[64,128]` 的递归状态，20 层合计 14.4 MB，衰减是**每头一个标量**（不是每通道、不是每 token 门控）。实测跨 chunk 项与块内项的能量比 `||cross||/||inner|| = 0.228`，其中 6 个头恒为 0（死头）。**【实测+代码】**
5. **哪些必须重训**：`msr.gamma`（必须重初始化后重训）、全零的 338M 死权重（想用就得重初始化+重训，不想用就冻结）、以及**所有活权重都必须继续训练**——把 γ 直接改成 0.9999 而不训练，loss 从 2.26 崩到 **6.10**，说明现有权重与短衰减深度耦合，单改 γ 会毁模型。**【实测】**

## 2. 长上下文缺陷

### 2.1 结构：跨 chunk 信息到底靠什么传

**前向路径（训练用的 chunkwise）**

- `RetNetForCausalLM.forward` 在 `chunk_size=None` 时回落 `config.chunk_size`（`retnet_hf/modeling_retnet.py:484-485`），导出的 `config.json:6` 写的是 **128**，`config.json:13` 写的是 `mode: chunkwise`。训练配置 `tasks/v21_plan_ddp2.json` 也是 `chunkwise` + `chunk_size=128` + `fast_chunkwise=true`。所以：**chunk = 128 token，2048 窗口 = 16 个 chunk**。**【代码】**
- 每个 chunk 内部：`inner = (q_i k_iᵀ ⊙ γ^{i-j}) v_i`；跨 chunk：`cross = (q_i ⊙ γ^{j+1}) S_{i-1}`；状态更新 `S_i = γ^{128} S_{i-1} + k_iᵀ (v_i ⊙ γ^{127-j})`（`modeling_retnet.py:236-245`，批量版在 `retnet_hf/retention_fast.py:121-179`，两版数学等价）。**【代码】**
- 因此**跨 chunk 的唯一信息通道就是 S**：形状 `[B, H, kd, vd] = [1, 22, 64, 128]` = 180,224 个数/层，20 层合计 3,604,480 个数 = **14.4 MB (fp32)**。chunk 0 的状态恒为 0。**【代码+实测形状】**
- 结构上的三个硬限制：
  1. **每头只有一个衰减率**。γ 是 `[H]` 的标量（`modeling_retnet.py:98-101`），64 个 key 维、128 个 value 维共享同一个半衰期。想同时记"上一个 token 的局部搭配"和"1000 token 前的实体"只能靠不同头分工 → 22 个头就是 22 个固定时间常数。
  2. **没有门控/写保护**。RetNet 的衰减是乘性的、与内容无关；Mamba/DeltaNet 那类"由输入决定写不写、忘不忘"的机制这里没有。信息一旦进入 S，只能按 γ^t 指数消失，无法被"钉住"。
  3. **跨文档不重置**。`forward` 不接受 attention_mask，chunkwise 的 state 也不会在文档边界清零；`scripts/build_flat_corpus.py:188-189` 的 `--add-eos` **默认关闭**，flat 分片是把语料直接拼成 2048 宽的流。**模型因此学着忽略远处的上下文——那里本来就是他文噪声**。这条是训练/数据侧的成因，不是结构必然。**【代码，默认值可查；实际分片是否带 eos 未逐片核查】**
- 另一处**路径不一致（已量化，影响很小）**：`_parallel_retention` 对衰减掩码做了 `mask/√(Σmask)` 归一化（`modeling_retnet.py:177`）再对分数做 `scores/Σ|scores|.clamp_min(1)`（`:184`），而 chunkwise/recurrent 完全不做这两步。`generate()` 的 prefill 走的是 **parallel**（`:559-562`），decode 走 **recurrent**（`:615-618`）。我在 2048 token 上对比：`max|Δlogit| = 1.07`、`mean|Δlogit| = 0.0158`（logit std 3.45）、argmax 一致率 99.66%、loss 2.2606 vs 2.2602。**是真实的不一致，但当前权重下数值影响 <0.5%，不是长上下文的主因。**【实测】

### 2.2 权重：gamma 实际分布与半衰期

统计口径：20 层 × 22 头 = **440 个 gamma**（占全部参数 0.000087%）。半衰期 `T½ = ln0.5/lnγ`。**【实测】**（脚本 `%TEMP%\b_analysis\w2.py`，权重 `blocks.*.msr.gamma`）

| 统计量 | gamma | 半衰期（token） |
|---|---|---|
| min | 0.1057（L1/h0） | 0.31 |
| p25 | 0.2136 | 0.45 |
| **p50** | **0.5659** | **1.22** |
| p75 | 0.7564 | 2.48 |
| p95 | 0.9896 | 66.6 |
| p99 | 0.99843 | 442 |
| max | 0.998853（L2/h11） | **604** |

- 半衰期 < 1 token：199/440（45.2%）；< 2 token：322/440（73.2%）；< 128 token：423/440（96.1%）；**> 2048：0 个**。
- 跨 chunk 能力：γ^128 > 0.5 的只有 **17/440**；γ^128 > 0.01 的 42/440。也就是说 16 个 chunk 里，绝大多数头在第一个边界就把历史衰减到 1% 以下。
- **是按头算，也是按层算**：每个 layer 有独立的 22 个头（`gamma` 是 per-layer 模块参数），层间差异很大。L12–L19 的 h0–h11 全部落在 0.50–0.76 的窄带（半衰期 1.0–2.5 token，仅 L12/h10=0.983 例外），而 L0–L11 逐层差异很大（0.106 到 0.998 都出现）；越靠后的层越"短视"。逐层逐头全表见 `%TEMP%\b_analysis\w2.out`。
- **决定性证据：死头的 gamma 在不同层里逐位相同**。h16–h21 的 6 个头在 20 层里是 6 个完全一样的值（spread = 0.0，例如 0.21362184 在 40 个位置上出现 40 次）；h12–h15 在 L0–L17 也逐位相同（0.175451…），只有 L18/L19 不同。**同一个数在 20 个不同层里逐位一致，只可能是"没有任何梯度、只有乘性衰减"**。这直接说明 γ 不是学出来的，是被 weight decay 拉下来的。**【实测】**
- 机制在代码里：`retnet_hf/train.py:49-71` 的 `get_decay_parameter_names` 只在 `--no_decay_1d` 打开时把 1 维参数移出 weight decay，而 **v21 的配置没有这个开关**（`tasks/v21_plan_ddp2.json` 没有该字段，`run_task.py:54-84` 的 DEFAULTS 里也没有），于是 `gamma` 作为裸 `nn.Parameter` 吃满 `wd=0.1`。v21 计划 159,857 步、lr 1.1e-4 余弦到 1.1e-5（`tasks/plan_ddp2.json`）。只算 v21 这一段，∫lr·dt ≈ 9.6，乘性因子 e^-0.96 ≈ 0.38；要把 1.0 压到实测的 0.2136 需要 ∫lr·dt ≈ 15.4，也就是还要算上生长之后到 v21 之间的几轮训练（同一 `wd=0.1`、同样没开 `--no_decay_1d`）。方向、量级、以及"死头逐位相同"三者一致。**【实测+代码推断；具体累加步数未逐 run 核对】**
- 仓库自己的交接记录 `logs\_commitmsg_gamma.md` 说 gamma 掉到 0.667/0.601/0.543、有效上下文约 500 token —— **那是 ep3 时点的旧数字**，我实测终版更低（中位半衰期 1.22 token），"约 500 token"这个量级我独立测出来也差不多（见 2.3），但成因的数字必须换成上表。

### 2.3 行为：实测有效上下文

数据：`data_cache/chat_pack_v13/val.ids.npy`（int16，833 行 × 2049）。测法：取 2048 窗口，**把"距离 d 之前"的所有 token 换成同分布的随机 token**（位置/旋转相位不变），只测最后 256 个目标 token 的 loss。d 越小＝真正可见的真实上下文越短。两个独立实现（GPU 单窗口 × 两个目标区间；CPU 4 窗口）方向一致：**【实测】**

| 可见距离 d | 4 窗口 loss（目标 1792–2047） | Δ | 单窗口 loss | Δ |
|---|---|---|---|---|
| 0（全噪声） | 3.1725 | **+0.479** | 2.4349 | +0.178 |
| 128 | 2.8675 | +0.174 | 2.3290 | +0.072 |
| 256 | 2.7243 | +0.031 | 2.2756 | +0.019 |
| 512 | 2.6988 | **+0.005** | 2.2550 | **−0.002** |
| 1024 | 2.6888 | −0.005 | 2.2561 | −0.0005 |
| 1792（完整） | 2.6935 | 0 | 2.2566 | 0 |

- **结论：512 token 以外的前缀对 loss 没有可测贡献（+0.005 nats，低于窗口间噪声）；256 以外只剩 0.03；真正被用上的约 300–400 token。**
- 第二组（目标区间 1280–1535，单窗口）：d=0/+0.327，d=256/+0.070，d=512/+0.004，d=1024/+0.001 —— 同样的拐点。
- 另一个反向对照：把全部 440 个 γ 强行设成 0.9999（半衰期 6931 token），同一窗口 loss 从 **2.2566 → 6.0986**。**说明"短记忆"不是外挂的推理设置，而是已经长进权重里了**；只改 γ 不训练只会更糟。**【实测】**
- 结构层面的旁证：在真实 2048 输入上，跨 chunk 项与块内项的能量比逐头为 0.04–0.46，总计 **0.228**；h16–h21 恒为 0（死头）。也就是说，即使跨 chunk 通道"有"信号，它承载的也只有块边界的残余，而不是 1000 token 外的实体。**【实测】**（`%TEMP%\b_analysis\b2.out`）

| 缺陷 | 归因 | 证据 |

## 4. 重训计划

### 4.0 先说结论：不要"修好 504M"，先承认它是 166M

- 想激活那 640 维死宽度，等于把一个训练好的 768-d 模型塞进 1408-d 壳里再从零学新通道：`gamma_new=1` 会立刻把随机/零的残差通道注入每一层，短期 loss 必然大幅变差，需要和"从零训"同量级的 token 才能填回来。**这笔钱建议留到第二阶段，且只在长上下文已经验证有效之后再花。**
- 因此下面两档都不动死宽度；死权重显式 `requires_grad=False`（顺便省掉 bnb 8-bit 优化器状态约 0.67 GB）。

### 4.1 共同前提（两档都要做，约 0.3 GPU 小时）

1. **重初始化 γ**：按"目标窗口内半衰期对数均匀"设 22 个头，例如 4096 窗口取 T½ ∈ [128, 4096]（γ = 0.5^(1/T½)）；不要再用 `1-2^(-5-h)`（那个公式的最小半衰期只有 22 token，比 chunk 128 还短）。8K 窗口取 [256, 8192]。
2. **把 γ 从 weight decay 里摘出去**：必须开 `--no_decay_1d`（`retnet_hf/train.py:260,386-388`），并在 step 100/1000 时打印 γ 与初值之比，**比值必须恒为 1.000**，否则说明开关没生效。
3. **冻结死权重**：对 `v==0` 的 338M 元素所在张量设 `requires_grad=False`（按张量粒度即可：`q/k/v/g/out/ffn.*` 的整块死区在这个模型里就是整张量的一部分，简单做法是只对 `gate/gamma_new/beta_new` 等做处理，或直接接受它们零梯度、只损失优化器显存）。
4. **验证脚本固化**：把本文 2.3 的"距离腐蚀"测法写成 `scripts/eval_effective_context.py`（8 窗口 × d∈{0,128,256,512,1024,2048}），作为唯一验收口径。

### 4.2 最低成本验证版（只回答"γ 修好 + 长数据能不能把有效上下文推到 2K+"）

| 项 | 设定 |
|---|---|
| 起点 | v21_export，γ 重初始化（4096 窗口配方） |
| 数据 | 文档级长文本为主：`data_cache/wikitext103_v16k`（已 16K 切好）+ literature/novel 分片 + 30% `hf_pack_sft` 防分布漂移；**必须带 eos/文档边界** |
| seq_len / batch | 4096 / 等效 65,536 token/步（2 卡 × 8 × 4096） |
| 步数 / token | 18,300 步 ≈ **1.2B token**（约 7 token/活参数） |
| LR | peak 2e-5，cosine → 2e-6，warmup 100，wd 0.1（**γ 除外**），clip 1.0 |
| 时间 | 1.2B / 396M tok/h ≈ 3.0 h，+20% 评测/重启/导出 ≈ **3.6 h** |
| 费用 | 3.6 × ¥13.97 ≈ **¥50** |

**验收（全部满足才算成功）**：① `loss(d=2048) − loss(full) ≤ 0.02` 且随 d 单调（当前是 +0.005@512 就归零，等于没有长程信号）；② 截断曲线 `loss(k=512) − loss(k=4096) ≤ 0.03`；③ `chat_pack_v13` val loss 不回退超过 +0.05（当前 4 窗口基线 2.6935）；④ γ 普查：无 γ<0.99 的长头、无 γ 被衰减。
**失败判据**：1.2B token 后 d=1024 的 Δ 仍 <0.01 → 说明 166M 有效容量的长程能力就是不够，转 4.4 的从零方案，别再往这条线烧钱。

### 4.3 完整版（把 0.5B 真的用起来 + 8K 上下文）

| 阶段 | 内容 | token | GPU h | 费用 |
|---|---|---|---|---|
| A | γ 重初始化 + 对齐（4K，短跑 300 步看 loss 是否回落） | 0.02B | 0.3 | ¥4 |
| B | 长上下文继续预训练，seq 8192，文档级打包（code 40% / 长文 30% / 网页教材 20% / SFT replay 10%） | 6.0B | 15.2 | ¥212 |

可选的 E 阶段（**只有 B 的验收通过才做**）：激活 640 维死宽度——`embedding[:,768:]`、各投影的 768:1408 块、`gamma_new=1` 重初始化，然后用 12B token 重训（30.3 h + 15% ≈ 35 h ≈ **¥489**）。这一步的期望收益是"名义 504M、真实 504M"，不是长上下文；不要把它和 B 混在一起做。

## 5. 我没有验证的部分 / 不确定的地方

1. **没有做真正的生成式 recall/needle 测试**。模型 val loss 2.69（4 窗口）说明它本身很弱，构造的合成 needle 大概率全是 0 分，区分度不如"距离腐蚀 Δloss"。我给的是因果腐蚀实验，不是端到端问答。
2. **单/4 窗口的噪声**：d=512 的 +0.005 与 d=1024 的 −0.005 都在窗口间噪声量级内（不同窗口 loss 从 1.59 到 3.40 不等），所以"≈300–400 token"是量级判断，不是精确拐点。要精确需要 32+ 窗口。
3. **v21 是否真的是最后训练的那一版**：`logs/curves/full_history_final.csv` 末行是 step 159,840、lr 1.26e-5，与 `tasks/plan_ddp2.json` 的 159,857 步计划吻合，但我没有核对导出时间戳与 step 的对应关系。
4. **`--add-eos` 的实际取值**：我只看了 `build_flat_corpus.py` 的默认值（False）和各 pack 的 `meta.json`（没有 add_eos 字段），没有逐片检查分片里是否真的没有分隔符。跨文档污染这条是【代码推断】。
5. **γ 掉到 0.1057（L1/h0）这种极小值，光靠 wd 解释不了**（纯乘性衰减到 0.21 就到底了）。可能叠加了早期 run 的 `gamma` 初始化差异、或某个 clamp 脚本，我没有回溯到具体哪一步。**但"是否学到"这一点不受影响**：死头逐位相同已经证明没有梯度。
6. **GPU 实测被挤占**：调查期间 `nvidia-smi` 显示 7.9/8.0 GiB 被其他 Agent 占用，我的 8 窗口 GPU 实验排队超时，最后用 CPU（4 窗口）复现；两者结论一致但样本不同。
7. **费用模型**：只按 token 吞吐折算，没算 8K 序列下显存不足导致的 batch 下降（v22 计划里 16K/batch2 的估算显示吞吐可持平，但 8K 下若只能 batch 4/卡，实际 tok/s 会掉 20–30%）。
