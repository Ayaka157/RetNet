# 16 低显存参数效率

> 日期：2026-10-10 · 作者：架构研究员（只读研究，未跑任何 GPU 任务）
> 平台：RTX 4070 Laptop 8GB（训练机）/ RTX 3070 8GB（本机）
> 模型：`retnet_272m_v13` → `retnet_272m_v14` 续训（272.30M）
> 范围：**在维持同等或更好表现的前提下，(a) 怎么让 8GB 装下更大的参数量，(b) 怎么训得更快。**
> 分工定位：本文只谈**显存 / 参数量 / FLOPs / 吞吐**这一轴；数据与 CoT 见方向二，架构变体见方向三。

## 0. 结论摘要

1. **8GB 的墙限制的不是参数量上限，而是每步的物理 batch。**
   打开梯度检查点后参数+梯度+优化器占用 2.54 GiB、激活值只剩 ~0.65 GiB，
   按每层 130 MB 的边际成本（状态 125.9 + 块输入 4.2）算，**同一块卡能装 54 层 ≈ 700M 参数**（§4.1）。
   但每步时间随参数量线性涨：700M 的每优化步约 2.3 s（现在是 713 ms），
   跑完 410M token 要 33 h 而不是 9.9 h。**装得下 ≠ 训得动。**
2. 当前配置（batch1×accum4、关检查点、8-bit Adam、compile）的显存构成是
   **激活 3.88 GiB（59%）> 参数 1.01 + 梯度 1.01（31%）> 优化器 0.51（8%）**（§1.2）。
   所以省显存的杠杆在**激活值**，不在优化器——这一点和直觉相反。
3. 想让 batch 2 在不颠簸的前提下装下，缺口不是简报里的 1.81 GiB 而是
   **2.28 GiB**（按 `audit_mem.py` 实测可用 7,715 MiB 计，§1.3）。
   纯工程手段凑不齐：8-bit Adam 已用掉、融合 CE 实测只给 452.7 MiB（batch 2）。
4. 单条改动收益最大的是 **`value_dim 2048→1024`**：激活 −1.13 GB、状态 −0.63 GB，
   合计 **−1.76 GB（−1.64 GiB）**，同时 **−24% FLOPs**；代价是参数量 −23%（272M→209M）。
   这是唯一一条"一条改动就跨过 batch-2 缺口的一半以上"的路线，但**必须重训或重新生长**。
5. 提速方面，`docs/15` §6 已经排除了 11 条路。**唯一还没被排除的大杠杆是内核发射数**：
   在真正生效的 chunk=64 下，`retention_fast.py` 的状态扫描是 **32 次 Python 循环 ×20 层 ×4 微步**
   ≈ 5,100–7,700 次内核发射，占 C 配置实测 10,116 次的**一半以上**；
   换成对数空间 `cumsum` 闭式解后每层只剩 ~6 次发射（§5.2）。
   但 C 已有 20.8% 的 GPU 空闲，而 §0.2 又实测过"摘掉几个内核 = 0%"，所以**这条的把握度最低**（§7）。
6. **明确不值得做的**：MoE、GQA/MQA（在本架构上对训练显存完全无效）、int8/FP8/4-bit 全参训练量化、
   LoRA 当主线、CUDA Graphs 配梯度累积、以及 `docs/15` §6 已实测否定的 11 项。理由与量化见 §7。

### 1.1 参数 / 梯度 / 优化器状态：精确可对账

use_gla=true, use_growth_ln=true, growth_old_dim=768, tie_weights=true, use_swiglu=false`。

按此逐项相加：

| 项 | 每个 | ×20 层 |
| --- | --- | --- |

| 3 | k 投影前/后（已 ×scale） | 2×(2.10M) | 8.4 |
| 4 | v / g | [1,16,2048,128] / [1,2048,2048] | 16.8 |
| 5 | 衰减表 `inner_mask` 等（fp32→bf16） | [16,64,64] 级 | 0.3 |
| 6 | `U` + `vr*value_decay` | [1,16,32,64,128] ×2 | 16.8 |
| 7 | 扫描 `S_list` + `stack(S_prev)` | 同上 ×2 | 16.8 |
| 8 | `inner`：A、A⊙mask、A⊙mask@vr | 4.19+4.19+8.39 | 16.8 |
| 9 | `cross` 左操作数 + 右结果 | 4.19+8.39 | 12.6 |
| 10 | `inner+cross` | [1,16,2048,128] | 8.4 |
| 11 | `_head_group_norm`：permute 拷贝 + GroupNorm 输出 | [2048,2048] ×2 | 16.8 |
| 12 | `silu(g)` | [1,2048,2048] | 8.4 |
| 13 | dropout 输出 + mask | [1,2048,2048] + 1B mask | 12.6 |
| 14 | out_proj 输出 + norm2 输出 | 2×4.19 | 8.4 |
| 15 | FFN：hidden、gelu、输出、dropout 输出+mask | 8.39×2+4.19×2+2.10 | 27.3 |
| | **单层合计** | | **~188 MB** |

**20 层 = 3.76 GB。** 再加上模型级 LM head / 损失：

| 项 | 形状 | MB |
| --- | --- | --- |
| `logits` bf16 | [1,2048,20000] | 81.9 |
| `logits.float()` | 同上 fp32 | 163.8 |
| `F.cross_entropy` 内部保存的 `log_softmax` | 同上 fp32 | 163.8 |
| **小计** | | **409.5** |

**激活总计 ≈ 4.17 GB = 3.88 GiB。**

**两个独立实测锚点校准：**

| 配置 | 手算 | 实测 | 偏差 |
| --- | --- | --- | --- |
| batch1 / seq2048 / 无检查点 / 8-bit Adam | 参数 1.015 + 梯度 1.015 + 优化器 0.507 + 激活 3.883 = **6.42 GiB** | reserved **6.57 GiB**（简报给的 v14 实测） | **+2.3%**（手算偏低，差值是 cuBLAS workspace + 碎片，≈0.15 GiB） |
| batch4 / 有检查点 / **fp32 Adam**（≈`docs/01` §4 的 7.58 GB 那行） | 状态 4.36 + 块输入 0.34 + 重算瞬态 0.75 + 损失头 1.64 ≈ **7.09 GB** | **7.58 GB** | +6.5% |

两个锚点方向一致（手算偏低 2–7%），可以放心用来算**增量**。
误差来源：部分被保存的中间量在反向早期即被释放；`torch.compile` 会改变个别张量的 dtype 与生命周期。

> ⚠️ **与 `docs/15` §0 的冲突**：那里写"C 的显存构成：…+ batch 1 激活（无检查点）≈ 2.5 GiB ≈ 5.2 GiB"。
> 2.5 GiB 与本文的 3.88 GiB 差 1.4 GiB，而 5.2 GiB 与实测 reserved 6.57 GiB 差 1.37 GiB。
> 两个方向一致的偏差说明**那句"≈2.5 GiB"是把差额藏进了一个不存在的"其它"里**。
> 按本文的逐张量账，6.42 GiB 手算 vs 6.57 GiB 实测，账是平的。

**结论：激活值占 59%，是显存墙的主体。** 这也解释了为什么"关掉梯度检查点"能省 1/3 步时，
却必须先把物理 batch 压到 1——它省掉的正是这 3.88 GiB。

### 1.3 batch 2 的缺口到底有多大

简报给的是"batch 2 需要 9.81 GiB reserved，超 1.81 GiB"。对着实测口径修正一下：

| 口径 | 数值 |
| --- | --- |
| batch 2 需求（实测 reserved） | 9.81 GiB |
| 卡标称容量 | 8.00 GiB → **缺口 1.81 GiB** |
| **实际可用**（`scripts/audit_mem.py` 的算法：8192 − 477 MiB 驱动/桌面占用）= 7,715 MiB | 7.53 GiB → **缺口 2.28 GiB** |
| 相对当前 batch 1 峰值（6.57 GiB）的增量 | **+3.24 GiB** |

**缺口应按 2.1–2.3 GiB 记，不是 1.81 GiB。** 差 0.3–0.5 GiB 会让方案评估整体偏乐观一档。
（batch 2 的激活 ≈ 1.98×batch 1：损失头那 409 MB 与全部逐层张量都随 batch 线性涨，
只有衰减表/坐标表不涨——那部分 <1%。）

## 2. 先把"文档 vs 代码"的不一致钉住

这一节是后面所有结论的前提。**以代码和任务配置为准。**

### 2.1 `chunk_size` 根本没被生效：实际跑的是 64，不是 128

`RetNetForCausalLM.forward(..., chunk_size=64, **_kwargs)`【代码】只把 `chunk_size`
**当成函数参数**往下传，**从不读 `self.config.chunk_size`**：

```python
# modeling_retnet.py:456-487
def forward(self, input_ids, labels=None, wcodes=None, mode=None,
            states=None, offset=0, return_state=False, chunk_size=64, **_kwargs):
    if mode is None:
        mode = getattr(self.config, "mode", "parallel")   # ← 只有 mode 读了 config
    ...
    elif return_state or mode == "recurrent" or mode == "chunkwise":
        logits, new_states = self._forward_hidden(..., chunk_size=chunk_size)
```

而 HF `Trainer` 只传 collator 给的三个键（`input_ids/labels/wcodes`，见 `retnet_hf/data.py`），
**不传 `chunk_size`**。于是：

- `tasks/v14_272m_2k_cont.json` 写着 `chunk_size: 128`，`retnet_hf/train.py` 也把它塞进
  `model.config.chunk_size` 并打印 `chunk_size=128`，**但训练跑的是 64**。
- `scripts/bench_trainer.py --chunk_size 128`、`scripts/diag_gpu_busy.py --chunk_size 128`
  同样只是设了 config 再打印，**测的也是 64**。
- `scripts/bench_step.py` 的 `run_once()` 只做 `cfg.chunk_size = chunk_size`，注释还写着
  "其余从 config 读"——**这个信念是错的**。它第 118 行声明的 `--sweep` 参数在文件里**没有任何实现**（死参数）。
- 因此 `docs/15` §6 的"chunk 512/1024 反而更慢，最优是 128"**用当前代码不可复现**：
  任何一次扫描，只要走 Trainer 路径或 `bench_step.run_once`，测的都是同一个 64。
  我**不断言**该结论错，只说它当前**无法验证**。

**顺带一个好消息**：`tasks/v13_272m_2k.json` 里就是 `chunk_size: 64`，而实际路径也是 64，
所以 v13→v14 **没有 chunk 变化**，`docs/15` §8 担心的"改 chunk 会让 loss 跳变"这件事**碰巧没发生**。
反过来说：**如果谁现在把这行代码"修好"、让 128 真正生效，v14 续训会当场出现一次 loss 跳变。**
修必须在一次全新开跑时修，或者明确接受跳变。

## 3. 工程省显存（不动模型结构）

### 3.1 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 现在没开

`grep` 全仓 `*.py` 与 `tasks/*.ps1|*.bat`【代码】：**没有任何地方设置这个变量**，
`tasks/start_v14.bat` 只设了 `PYTHONIOENCODING` 和 `RETNET_FAST_CHUNKWISE`。
`docs/15` §3.1 只在撞 batch 2 时临时用过它。
它不减少 allocated，但能压掉 reserved 与 allocated 的 0.15 GiB 差额并抑制碎片化——
**零代码改动、零正确性风险**。验证：同一 task 跑 60 步对比 `bench_trainer` 的 reserved 与步时。

### 3.2 融合线性+CE：已被实测钉死，但**块大小没调**

`retnet_hf/fused_ce.py`【代码】的做法是前向分块算 logits、只保存 `lse`，
反向重算一遍 LM head 的 softmax。它**已经写好且数值等价**（`docs/15` §6：loss 逐位相同、
梯度相对差 ≤2.3e-4），代价是那个 `@torch._dynamo.disable` 的分块循环让 batch 1 慢 13%。

但 `LOGIT_CHUNK = 2048` 这个常量在 **batch 1 下等于不分块**（N = B·L = 2048），
所以 `lg` 仍然是完整的 `[2048, 20000]` fp32 = **163.8 MB**。
把 `LOGIT_CHUNK` 改成 256，峰值里那一项降到 20.5 MB：

| | 现在的损失头 | 融合 CE（c=2048） | 融合 CE（c=256） |
| --- | --- | --- | --- |
| batch 1（手算） | 409.5 MB | 164+82 = 246 MB → **省 163 MB** | 20.5+82 = 103 MB → **省 307 MB** |
| batch 2（实测锚点） | — | **省 452.7 MiB = 475 MB**【实测】 | 预计再省 ~288 MiB |
| batch 4（手算） | ~1.64 GB | ~0.25 GB → 省 ~1.39 GB | ~0.10 GB → 省 ~1.54 GB |

**注意 batch 1 的两个口径不一致**：实测（batch 2 的一半）给 **237 MB**，
本文的分析式给 **163 MB**——说明分析式对 `logits`/`logits.float()` 是否能被
inductor 融掉判断得过于悲观。**以实测为准，batch 1 的收益按 160–240 MB 记。**

（`82 MB` 是反向里 `weight.float()` 那份拷贝，与 c 无关。）
**结论：融合 CE 不是提速手段（-13%），是显存手段。要它就把 `LOGIT_CHUNK` 一起调小。**

### 3.3 参数的"乘性"压缩：精度 × 优化器

| 手段 | b | 272.3M 省 | 代价 | 是否已试 |
| --- | --- | --- | --- | --- |
| bf16 参数+梯度（1 维参数强制 fp32） | 10→6 | **−1.09 GB** | 数值风险；`docs/01` §3 已记录 GLA γ 在 bf16 下 16 个头塌缩 12 个，所以 **γ/norm/LN 必须留 fp32** | ❌ 未试 |
| Adafactor（β1=0，因子化二阶矩） | 10→8 | −0.54 GB | 优化器语义变了；**必须重开跑**（换优化器 = 丢 optimizer.pt） | ❌ 未试 |
| Adam-mini（块内共享一个 v） | 10→9 | −0.27 GB | 同上 | ❌ 未试 |
| Lion（只有一阶矩） | 10→9 | −0.27 GB | 符号型更新，与 Adam 不同族 | ❌ 未试 |
| `paged_adamw_8bit`（按需换出到内存） | 10（稳态） | 压力下最多 −0.5 GB | PCIe 往返；只在真的触发分页时才有收益 | ❌ 未试 |
| 梯度+优化器 CPU offload（ZeRO-Offload 式） | 10 | −1.6 ~ −2.7 GB | 每步多搬 3.3~5.4 GB，PCIe 4.0×8 下约 **+200~340 ms/步（+28~48%）** | ❌ 未试 |

> 选型建议：**先试 bf16 参数+梯度**（省得最多、改动最小、风险可测），
> 优化器类只在下次冷启动时一起换（`Adafactor` 或 `Adam-mini`，二者都不需要重算调度器）。
> CPU offload 在这个墙钟预算下性价比最差，除非目标是"跑一个更大的模型"而不是"跑得更快"。

### 3.4 梯度检查点是"容量杠杆"，不是"显存节省"

这是全文最重要的一处口径纠正。`docs/15` §3 把检查点当成"用 1/3 步时买 2.5 GiB"的败笔，
因为它当时的目标是**关掉它来提速**。但反过来看：

| | 激活 | 参数+梯度+优化器 | 总计 | 每步时间 |
| --- | --- | --- | --- | --- |
| 现在（关检查点） | 3.88 GiB | 2.54 GiB | 6.42 GiB | **713 ms**【实测 C】 |
| 打开检查点 | **~0.65 GiB** | 2.54 GiB | ~3.2 GiB | **≈936 ms**【实测：batch1×accum4 + 检查点】 |
| 打开检查点 + bf16 参数/梯度 | 0.65 GiB | 1.53 GiB | ~2.2 GiB | ~1 s |

（~0.65 GiB = 20 个块输入 84 MB + 单层重算瞬态 ~190 MB + 损失头 409 MB，取峰值而非求和。）
**代价实测 1.28×（936/732）；理论上限 1.5×（前向跑 3 遍 vs 2 遍）。**

**换来的 3.2 GiB 可以全部变成参数容量。** 这直接给出 (a) 的答案，见 §4.1。

## 4. 设计层面换结构（要重训 / 重新生长）

### 4.1 (a) 8GB 到底能装多大——量化回答

在"打开检查点"的配置下，激活几乎与层数无关（每层只多存 4.19 MB 的块输入），
所以**每层的边际成本 ≈ 状态 125.9 MB + 块输入 4.19 MB = 130.1 MB/层**（12.591M 参数 × 10 B）。
可用显存按 8.09 GB（8192−477 MiB）算：

```
L × 0.1301 GB + 0.2048 GB(嵌入) + 0.19 GB(单层重算瞬态) + 0.41 GB(损失头) + 0.15 GB(碎片) ≤ 8.09 GB
→ L ≤ 54.8  →  取 54 层  →  P ≈ 700M
```

| 目标规模 | 配置 | 每优化步（估） | 410M token 的墙钟 | 备注 |
| --- | --- | --- | --- | --- |
| 272.3M（现状） | 20 层、关检查点、8-bit Adam | **713 ms**【实测】 | **9.9 h** | 当前唯一在跑的配置 |
| 310M | 23 层、**关**检查点 | ~800 ms | ~12 h | 不打开检查点时的真实上限（可用 7.53 − 当前手算 6.42 = 只剩 1.11 GiB） |
| 390M | 30 层、**开**检查点 | ~1.4 s | ~19 h | 容量换墙钟 |
| **700M** | 54 层、**开**检查点 | ~2.3 s | **~33 h** | 容量上限 |

**所以 (a) 的正确提法不是"怎么装下更多参数"——打开检查点就能装 2.6×。**
真正的问题是：**每步成本随参数量线性涨，而 8GB 卡的算力是固定的。**
在这个意义上 8GB 的墙限制的是**吞吐**（物理 batch 与 GPU 占用率），不是容量。

### 4.2 那"更大参数"值不值？——本项目自己的证据

| 证据 | 数字 | 说明 |
| --- | --- | --- |
| 143M rp | 45,000 步、epoch 0.6155、eval_loss **2.6534** | 训练量 ≈ **172.7M** token |
| 272M rp | 20,000 步、epoch 0.1463、eval_loss **2.9946** | 训练量 = 20,000×512×4 = **41.0M** token |
| v10（272M） | 65,000 步（seq512×batch4）、eval_loss 2.3031（另一验证集） | **133M** token |
| v13（272M） | 12,500 步（seq2048×batch4） | **102.4M** token |
| v14（272M，在跑） | 50,000 步 × 8192 | **409.6M** token |

- 272M 线**累计**约 0.69B token（41+133+102+410）≈ **2.5 token/参数**；
  加上生长继承的 819M 预训练也不过 5.5 token/参数。文献里"数据不是瓶颈"的位置在 20+ token/参数。
- 272M rp 比 143M rp **多 1.9× 参数、少 4.2× token**，eval_loss 反而差 0.34。
  ⚠️ 这不构成受控实验（验证集口径未复核、并行步数不同），方向与"token 才是瓶颈"一致。
- 项目自己也发现能力提升不随参数走：v10 的 65k 步（+133M token）在 143 项基准上只 +0.026，p=0.084 不显著。

**结论：在当前数据/算力位置，把显存换成更多参数是低效的；换成更多 token / 更多 epoch 是免费的**
（v14 的 410M token 只覆盖 552.3M 数据包的 **0.74 epoch**，而 v10 那次 0.28 epoch 就跑到基准追平）。
**唯一的例外是 `docs/04` §4 认定的"尺度限制"能力（数学、结构化输出，0/0.06 分）——那条路确实要 ≥0.5–1B。**

### 4.3 结构候选逐条量化

| 代号 | 改动 | 激活 Δ | 状态 Δ | FLOPs Δ | 合计省 | 参数代价 |
| --- | --- | --- | --- | --- | --- | --- |
| **S1** | `value_dim 2048→1024` | **−1.13 GB** | **−0.63 GB** | **−24%** | **−1.76 GB** | −23%（→209M） |
| S2 | `ffn_dim 2048→1024` | −0.17 GB | −0.42 GB | −12% | −0.59 GB | −15%（→230M） |
| S3 | 去掉 `g_proj`，用 `v` 当输出门 | −0.17 GB | −0.42 GB | −7% | −0.59 GB | −15%（→230M） |
| S4 | 分 4 组层间权重共享（ALBERT 式） | 0 | **−1.89 GB** | 0 | −1.89 GB | 容量大减，必须重训 |
| S5 | MoE（8 专家 / top-2、每专家 ffn/4） | 0 | **+0.84 GB** | −17% | **+0.84 GB（反向）** | 见 §7.1 |
| S6 | GQA/MQA | 0 | ~0 | 0 | **0** | 见 §7.2 |

**S1 的算法**（激活部分，单层 14 组张量减半）：
`v、g、vr*value_decay、U、S_list、S_prev、inner、cross 右、inner+cross、permute 拷贝、
GroupNorm 输出、silu、dropout 输出` 各 −4.19 MB，`dropout mask` −2.10 MB
→ 单层 −56.6 MB → ×20 = **−1.13 GB**；
参数部分 `v/g/out_proj` 各由 1024×2048 变 1024×1024 → 单层 −3.146M → ×20 = 62.9M ×10 B = **−0.63 GB**。
FLOPs：每 token 从 281.3M MAC 降到 214.5M MAC（−23.7%，**已含 chunkwise 的 O(L·C) 形式**，不是 O(L²)）。

**S1 的代价与风险**：RetNet 原文用 `value_dim = 2·d_model`（本项目沿用），砍到 1× 等于把
每头的 value 维度从 128 降到 64；这是**没有小尺度证据**的方向改动，必须靠 A/B 论证。
好处是它同时减少 FLOPs 24% → 即使模型变小，**墙钟反而大概率更快**（§5.4）。

### 4.4 深度 vs 宽度（同一参数量下谁更省显存）——量化

激活值的线性部分 ∝ `层数 × seq × d_model`，参数 ∝ `层数 × d_model²`。
固定参数量 P 时 `d ∝ sqrt(P/L)`，于是**激活 ∝ sqrt(P·L)：层数越多越费激活**。
实测口径：把 20 层 d1024 换成 28 层 d896（参数量基本持平 272M→288M）：

- 逐层激活张量 ∝ L_seq×d：`28×896 / (20×1024) = 1.225` → **激活 +22.5%**
- chunkwise 保留项 ∝ 层数：**+40%**
- 内核发射数 ∝ 层数：**+40%**（当前 C 配置已经有 20.8% 的 GPU 空闲）

**结论：在这个显存-发射双受限的场景里，加宽比加深便宜。**（但 `MobileLLM`（arXiv:2402.14905）
一类的结论是"小模型深而窄更好"，两条证据方向相反——所以这条只作为**否决"用加深来省显存"**的依据，
不作为"应该加宽"的依据。）

## 5. 训得更快

### 5.1 现状定位（先确认还剩多少空间）

按 §1 的逐项 FLOPs（**chunkwise 的 O(L·C) 形式**）：

| 项目 | 每 token MAC | 占比 |
| --- | --- | --- |
| MSR 投影（q,k,v,g,out） | 167.8M | 59.6% |
| FFN 上/下 | 83.9M | 29.8% |
| retention 内块+跨块 | **9.2M** | 3.3% |
| LM head | 20.5M | 7.3% |
| **合计** | **281.3M MAC = 562.6 MFLOP/token** | |

每优化步（8192 token、fwd+bwd×3）= **13.84 TFLOP**（6ND 口径 13.39 TFLOP，差的那 0.45 就是 retention）。
713 ms/步 → **19.4 TFLOPs 持续 = 可达峰值 40 TFLOPs 的 49%**（与 `docs/15` §0.1 给 B 的"52% 效率"同量级）。
**理论下限 346 ms → 最大 2.06×。**

那 51% 的缺口里，`docs/15` §0.3 已经给出定性结论：GEMM 那半是**占用率/切分**问题（batch 1 的 M 太小），
逐元素那半是**带宽**问题（≈0.5–2 FLOP/byte，远低于 184 的脊点）。
两者都指向同一个方向：**提高物理 batch**。而物理 batch 卡在 §1.3 那 2.28 GiB 上。

### 5.2 唯一还没被排除的大杠杆：把 32 次 Python 状态扫描换成 cumsum 闭式解

`retention_fast.py:53-56`【代码】：

```python
for i in range(nc):                 # nc = L / C
    S_list.append(s)                # 每次 append 一个 [B,H,kd,vd] 的引用
    s = decay * s + U[:, :, i]      # 每次 2 个逐元素内核 + 1 次索引
```

**在真正生效的 chunk=64 下 `nc = 2048/64 = 32`**，即每层每微步 32 次循环 × ~2 内核
≈ 64–96 次发射 → ×20 层 ×4 微步 = **5,100–7,700 次发射**，
而 `docs/15` §0.2 实测 C 配置总发射数 **10,116**、GPU 空闲 **20.8%**。

数学上这个循环有闭式解（记 `d = decay`，`i` 为块序号）：

```
S_prev[i] = d^i · state + Σ_{j<i} d^(i-1-j) · U_j
          = d^i · state + d^(i-1) · cumsum_{j<i}( d^(-j) · U_j )
```

于是 32 次顺序迭代可以变成 **~6 次逐元素内核 + 1 次 cumsum**。

**数值安全（这一条最容易想当然，必须掰清楚）：**
`retention_fast._decay_tables` 里的 `chunk_decay = exp(log γ · C)` 是**块级**衰减 `d`。
`docs/12` §4 的实测门控范围是 `γ ∈ [0.3245, 1.0117]`，C=64 时

```
log d = C · log γ  ∈  [64×(-1.125), 64×(+0.0116)] = [-72, +0.74]
```

**直接 `c_j = exp(-j·log d)` 会溢出**：j 到 31 时指数是 +2232，连 fp64（上限 ~1.8e308，
即 exp(709)）都装不下。所以"升到 fp64 就行了"这句话**是错的**。

正确做法是**先把动态范围钳住**：

```
log_d = clamp(log(chunk_decay), min=-20)     # 每块衰减下限 2e-9
```

- 被截掉的是"隔两块以上"的贡献，量级 ≤ 2e-9 相对值，比 bf16 的分辨率（2⁻⁸≈4e-3）
  低 **6 个数量级**，在当前数据通路上不可观测；
- 钳位后指数上界是 `20 × nc = 20 × 32 = 640 < 709`，**fp64 双方向都不溢出**；
- 训练时 `_chunkwise_retention` 的入口 `state` 是 `None` → 全零，
  所以 `d^i·state` 这一项本来就恒为 0，要算的只有 `Σ_{j<i} d^(i-1-j) U_j`。

```python
c      = torch.exp(-torch.arange(nc) * log_d)          # [H, nc]，fp64
CU     = torch.cumsum(c[..., None, None] * U.double(), dim=2)
CU     = CU - c[..., None, None] * U.double()          # exclusive
S_prev = (d_pow_im1 * CU).to(U.dtype)                  # d_pow_im1 = exp((i-1)*log_d)
```

> **数值影响**：与现有 fp32 顺序循环的差在 1e-6 相对量级——**和现有 fast 路径
> vs 参考循环的 `rel_mean ~7e-7`（`docs/15` §2.3）同一档**。因此 E10 与 E9 不同：
> **它在一段续训中途做也不会有可见的 loss 跳变**，但仍必须先过等价性测试。

> **与 `docs/15` §6 已被否定的"Hillis-Steele 对数深度扫描"不是同一条路。**
> 那次是**结合性扫描**，每一轮 `torch.cat` 都要物化整个 `[B,H,nc,kd,vd]`，实测慢 2.8×；
> 这里是**前缀和**，只做一趟 cumsum + 几次逐元素。**这条没有被试过。**

验证：`tests/test_fast_chunkwise.py` 已经在测"fast vs 参考循环"的逐位等价（真实门控范围
0.668–1.0117 那一档），改完直接跑它即可；
但**必须补一档 γ=0.32 的极端用例**（v10 的门控最小值，也正是 `docs/15` §2.1 那个溢出 bug 的来源）。
时延用 `scripts/diag_gpu_busy.py`（读内核数）与 `scripts/bench_trainer.py`（读步时）对照。

**把握度声明**：`docs/15` §0.2 明确写过"C 有 20.8% 空闲，所以摘掉几个内核实测 0%"。
所以这条**可能同样颗粒无收**——它是本文最不放心的一条（§7.5）。

### 5.4 结构改动带来的速度（S1/S2/S3 的另一面）

S1（value_dim 减半）**同时砍 24% 的 FLOPs**，而它动的那部分正好是
"激活字节 × 逐元素遍数"——逐元素的搬运量也随之减半。
粗算（GEMM 占 49%、逐元素占 51%）：

```
GEMM     49% × (1 - 0.24)  = 37%
逐元素   51% × (1 - 0.27)  = 37%     ← 激活字节 −27%≈1.13/4.17
合计                         = 74%   →  1.35×
```

叠加上 §4.1 里"更小的状态 → 或许能上 batch 2"这一层，1.5–1.7× 是有希望的。
**但这是估算（±30%），S1 的质量代价没有任何小尺度证据**，所以它是一条"必须靠 A/B 兑现"的路线。

| S3 | 去掉 `g_proj`（用 v 当门） | −0.59 GB，FLOPs −7% | 门控与 value 耦合，破坏 MSR 语义 | 同上 | 🟡 风险高于收益 |
| S4 | 分 4 组层间权重共享 | −1.89 GB（状态） | 容量大减，必须重训 | 无短验证路径 | 🟡 只有 S1+S2 都试过、仍不够再考虑 |
| S5 | MoE | **+0.84 GB（反向）** | 见 §7.1 | — | ❌ 不值得 |
| S6 | GQA / MQA | **0** | 见 §7.2 | — | ❌ 不值得 |
| S7 | 加深度换容量 | 激活 +22.5%、发射 +40% | — | — | ❌ 不值得 |
| S8 | int8 / FP8 / 4-bit 全参训练 | ~0 甚至变负 | 见 §7.3 | — | ❌ 不值得 |
| S9 | LoRA / QLoRA 当主线 | −2.4 GB | 不再是全参训练 | — | ❌ 主线不值得（可做消融） |

## 7. 明确不值得做的

### 7.1 MoE —— 对 8GB 单卡是**反向**的

MoE 买的是"每 token 更少的 FLOPs"，代价是"更多常驻参数"。在 10 B/参数 的约束下，
**常驻参数量就是显存**。构造一个标准配方（8 专家、top-2、每专家 `ffn/4`）：

| | 稠密（现状） | MoE 等价 FLOPs |
| --- | --- | --- |
| 每层参数 | 12.591M | **16.78M**（FFN 4.19M → 8.39M） |
| 全模型参数 | 272.3M | **356M** |
| 状态（10 B/参数） | 2.72 GB | **3.56 GB（+31%）** |
| 每 token 激活参数 | 12.591M | 10.49M（−17%） |

**付 31% 的显存买 17% 的算力**——在这个"显存受限、算力尚有余量（GPU 空闲 20.8%）"的机器上完全反向。
另外三条独立否决理由：(i) 单卡无专家并行；(ii) batch=1 时按专家分桶后每个专家 GEMM 的 M 更小，
正好加剧 `docs/15` §0.3 认定的"occupancy/split"问题；(iii) 需要路由器与负载均衡损失，
在 272M 尺度是纯负担。参考文献：`Switch Transformers` arXiv:2101.03961、`Mixtral` arXiv:2401.04088。

### 7.2 GQA / MQA —— 在本架构上对训练显存**完全无效**

Transformer 里 GQA/MQA 省的是 **KV cache**（推理）和 k/v 投影参数。
本项目：`v_proj`【代码】是 `Linear(d_model, value_dim)`，**一个矩阵，不按头分**；
推理时 RetNet 用 O(1) state（每层 `key_dim × value_head_dim × num_heads`
= 16×64×128 ×2 B = **262 KB/层**，20 层共 **5.2 MB**，与上下文长度无关），根本没有 KV cache。
（`docs/01` §3 与 `docs/04` §3.3 写的"272M 约 2.4 MB"其实是 **100M 线**（12 头 ×12 层）的数，见 §2.2 第 8 条。）
即使强行把 `k_proj` 按 G=4 分组（省 15.7M 参数 = 157 MB，只占总显存 ~2.4%），
代价是 16 个头共享同一组 key、多尺度衰减的逐头语义被破坏。
`docs/04` §3.3 那三行建议（"GQA 式共享投影 / fp8 量化"）应当作废。

### 7.3 量化训练（int8 / FP8 / 4-bit）—— 省不到点子上

全参训练的内存是 `参数 + 梯度 + 优化器状态`。把**参与矩阵乘的那份权重**压到 8/4 bit，
省下的是"计算副本"，而 **fp32 master + fp32 梯度 + 优化器状态必须保留**：

| 方案 | 每参数字节 | vs 现在的 10 B |
| --- | --- | --- |
| int8 权重副本 + fp32 master + fp32 梯度 + 8-bit 状态 | 4+4+1+2 = 11 | **更差** |
| 纯 bf16 参数+梯度 + 8-bit 状态（E4） | 6 | −40% |
| 4-bit 冻结底座 + 适配器（=LoRA） | ~2（只对底座） | 见 §7.4 |

**全参训练的量化收益为 0 或负，唯一的正收益路径是"参数/梯度的 dtype"，不是"权重的位宽"。**
FP8 在 Ada 消费卡上的训练支持（torchao）尚不确定，**未核实，且不值得在这个项目上做第一例**。
参考：`8-bit Optimizers via Block-wise Quantization` arXiv:2110.02861（本项目已用其成果）。

### 7.4 LoRA / QLoRA 当主线

省得很多（2.72 GB → 0.28 GB），但它是**参数高效微调**，不是全参训练：
`LoRA Learns Less and Forgets Less`（arXiv:2405.09673）的结论是 LoRA 在大规模代码/数学域上
明显弱于全参微调。本项目的目标是继续提升一个 272M 模型的能力，
把它换成"冻住底座 + r=32 适配器"等于自愿放弃表达能力。
**它适合做便宜的消融（比如验证某个数据配方），不适合当主线**；而且中途从全参切 LoRA 不是续训。

### 7.5 已经被 `docs/15` §6 实测否定的（不再重复推荐）

无条件关检查点（batch4 OOM 14.5 GiB / 无 8-bit Adam 时颠簸 8×）·dropout 0.1→0 ·
chunk 512/1024 · 单序列 decode 的 compile/CUDA Graphs/bf16 · `adamw_torch_fused`（0%）·
"梯度累积但保留检查点"（零收益）· 分层梯度检查点（两块卡都打不过当前配置）·
去掉 `logits.float()`（0%）· CUDA Graphs 配梯度累积（硬冲突）· Hillis-Steele 对数深度扫描（慢 2.8×）·
`_rotations` 的 sin/cos 表缓存（0%）· `dataloader_num_workers` 0/2/4（0%）·
`_head_group_norm` 改布局（实测反而慢 9.2%，`modeling_retnet.py` 顶部 NOTE 已封板）。

**特别提示**：`docs/15` §0.2 的"C 有 20.8% GPU 空闲，但摘掉几个内核实测 0%"
是对 E9/E10 的直接反证。**E10 的上限最高、把握最低，做之前先接受"可能同样 0%"**。

### 7.6 其它不值得

- **靠加深来省显存**（§4.4：同参数下激活 +22.5%、发射 +40%）。
- **缩小词表省 LM head**：V=20000 的 head = 20.48M 参数（41 MB 状态）+ 20.5M MAC/token（7.3%），
  缩到 16k 只省 41 MB。不值得动 tokenizer。
- **自适应/稀疏 softmax**：头只占 7.3% FLOPs，而它会拆掉 tied embedding 的设计。
