# v21 训练监控与成功判据

> 2026-10-18 晚。这份文件是给"训练跑完之后回来核对"用的，记录判据、基线、以及
> 监控期间发现的坑，避免只靠对话记忆。

## 成功判据

**不能看 chat 验证集。** 主验证集（`chat_pack_v13` 的 833 行）是对话分布，而 v21 的
阶段 0–3 训的是网页、代码、教材；chat-val 在训练过程中**必然变差**，最后靠阶段 4 的
退火拉回来。用它在中期判断"有没有学到东西"会得出完全错误的结论。

**真正的判据是域内 held-out**：`data_cache/pretrain_v2/*val*.npy`，训练时被
`_FlatStage` 按文件名排除，从未进过梯度。

| 项 | 值 |
|---|---|
| 基线（ep3，6 文件 3,059,712 token，每文件限 60 万） | 3.6028 |
| 基线（ep3，5 文件 2,461,696 token，限 60 万） | 3.5456 |
| **基线（ep3，5 文件 4,454,400 token，全量分片）** | **3.6287** ← 最终用这个比 |
| 成功阈值（降 10%） | **≤ 3.2659** |

> 三个数字并存是因为评测口径变过两次：先是 6 文件、后因删 skypile 变 5 文件、
> 最后为与 v21 的测法一致改成全量分片（不再限 60 万）。**最终结论只能用同一口径的
> 3.6287 对比**，其余两个只用于历史追溯。

**中期检验（2026-10-18 16:45，step 15,000，即 20% 进度）**：

| 来源 | ep3 | v21@15k | 变化 |
|---|---|---|---|
| chinese_fineweb_edu_v2 | 3.8519 | 3.2353 | −16.0% |
| cosmopedia | 3.0564 | 1.9987 | −34.6% |
| fineweb_edu | 3.7223 | 2.9595 | −20.5% |
| open_web_math | 3.3976 | 2.6005 | −23.5% |
| wikipedia_zh | 3.6474 | 2.8145 | −22.8% |
| **加权平均** | **3.6287** | **2.8666** | **−21.0%** |

已超过 10% 的成功阈值，而这只是全程的 20%。

**学习曲线（同一口径 4,454,400 token）**：

| 步数 | held-out | 相对 ep3 |
|---|---|---|
| 0（ep3） | 3.6287 | — |
| 15,000 | 2.8666 | −21.0% |
| 17,500 | 2.8471 | −21.5% |

两点都在 stage 0（pretrain_v2）内部，所以收益已经**开始收敛**——同一份语料
能提供的边际信息在减少。后续换到网页/代码/教材时会重新出现下降段。

> 为什么是 5 个文件：清 skypile 分片时用 `skypile_*.npy` 通配符，把
> `skypile_val.npy` 一起删了。这不影响正确性（skypile 本就不参与训练，删掉它反而是
> 更干净的留出集），但基线必须用同一批文件重算——上表 3.5456 是由 6 文件基线与
> skypile 单独 loss 精确反推得到的，不是重新跑出来的。

|---|---|---|

评测命令：

```bash
python scripts/eval_holdout.py --model checkpoints/retnet_500m_v21 --tag v21
```

⚠️ 两个实现细节（都踩过）：
1. 本地 checkpoint 没有 `auto_map`（只有上传到 HF 的那几份加过），必须直接用
   `RetNetForCausalLM` 加载，`AutoModelForCausalLM` 会报"不认识的架构"。
2. chunkwise 模式在 bf16 下抛 `expected scalar type Float but found BFloat16`，
   评测走数学等价的 `parallel` 模式。

## chat 验证集的退化轨迹（预期内）

主验证集（chat_pack_v13，833 行）在 stage 0 内部就一路变差：

| 步数 | chat-val |
|---|---|
| 2,500 | 2.806 |
| 5,000 | 2.912 |
| 7,500 | 2.976 |
| 10,000 | 3.022 |
| 12,500 | 3.050 |
| 15,000 | 3.049 |
| 17,500 | 3.063 |

ep3 是 1.9459。**这不是训练出问题**，而是阶段 0–3（约 5.0B token）里没有任何
对话格式的 token，模型自然把对话能力挤掉了。它在 15,000 步之后走平，说明已经
收敛到“预训练文本模式”。

最后 6,000 步退火（0.39B token，约 0.71 个 epoch）负责往回拉。之所以给到 6,000
而不是最初的 2,500：2,500 只有 0.13 个 epoch，在接近最小学习率的情况下拉不回来。

**这里有一个明确的取舍**：退火多给 3,500 步是从代码段匀出来的（代码 28,545 →
25,045，token 1.87B → 1.64B）。选择保住 demo 的对话可用性，代价是代码暴露少
12%。若要反过来（代码优先），把这两个数字对调再热加载一次即可。

## 监控期间修掉的坑（按危害排序）

1. **`min_shards: 10` 用在只有 1 个分片的网页语料上**——会让段 1 永远不就绪，训练卡在
   35,205 步的等待循环里烧到天亮。这是最危险的一个，属于"不报错、只烧钱"。
2. **两个下载器实例并发写同一批文件**——交错追加产生"比期望还大"的坏文件。
   已加 `flock` 单实例锁。
3. **杀下载器不杀 curl**——孤儿 curl（ppid=1）被 init 收养后继续写，下载量会倒退。
   实测 463 MB → 425 MB。已加 `pkill -P 1 curl`。
4. **分词门槛写死"全部文件到位"**——改为按 `need_gb` 判断"够用就开始"。
5. **`release_raw` 用 basename 匹配带子目录的清单项**——命中 0 个文件，报"释放 0.00 GB"。
6. **大小正确但内容损坏的 parquet**——`Corrupt snappy compressed data` 会中止整次分词。
   已加中途容错 + 监督器 `scrub_corrupt`。
7. **`DefaultFlowCallback` 读的是 `state.save_steps` 而非 `args.save_steps`**——
   计划回调里的"存档节奏热加载"此前是假的。
8. **`need_gb` 超过数据集总量**——textbook 全量 0.28 GB 却要求 0.4 GB，永远不分词。

## 磁盘纪律

| 阶段 | 数据盘空闲 |
|---|---|
| 开训 | 41 GB |
| 代码分词峰值 | 19.9 GB |
| 全部语料就绪后 | 25 GB |

`_disk_guard.py` 每 2 分钟检查：数据盘 <10 GB 删原始包 + checkpoint 收到 2 个；
<5 GB 收到 1 个；系统盘 <5 GB 清 inductor/pip 缓存。**绝不碰最新 checkpoint、
计划正在读的分片、以及验证集分片**（已实测验证：GC 会删 46 个训练分片，
6 个验证集分片全部幸免）。
