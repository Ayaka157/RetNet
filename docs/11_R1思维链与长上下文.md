# 11 R1 思维链与长上下文

> 最后更新：2026-10-09 · 初稿 2026-08-25，结论已由 v10/v13 实测更新
> 相关：[`13_基准测试重设计与评测结果.md`](./13_基准测试重设计与评测结果.md) §2、
> [`04_路线与扩展研究.md`](./04_路线与扩展研究.md) §4

## 1. 问题的起点

v10 综合训练（65k 步，eval_loss 2.3031）的能力评估暴露两件事：
**`<think>` 标签泄漏到最终输出**（数学/菜谱/步骤题卡在 think 里答不完）+ **模型答不完整**。

后来的自动判分基准把这件事量化了：`retnet_272m_v10` 的泄漏率 **26.5%**（303/1144 样本），
而 `retnet_272m_rp` 是 **0%**。泄漏集中在 9 个项目上——
`cloze_formula / cloze_geo / qa_fact / qa_logic / qa_math / qa_recipe / st_json / st_list / st_steps`，
**正好是 R1 数据本来想改善的那几类**。

## 2. 根因：数据本体是好的，管线把答案切掉了

第一步先排除「数据源脏」这个可能。实查 `data_cache/a_grade/r1_110k_sft.jsonl`：

| 指标 | 值 |
| --- | --- |
| 行数 / 体积 | 110,000 行 / 647 MB |
| 语言 | **99% 中文**（抽样 417 条：中文 413 / 英文 2 / 混合 2） |
| 含 `</think>` 的比例 | **100.0%**（417/417） |
| output 长度 | 中位 **1,912** 字符 · p90 3,613 · 最大 14,287 |

**数据是完整、干净的。** 问题出在管线：**读取端和打包端的两级截断都从尾部切，而答案在尾部。**

抽样 3,010 条实测的漏斗：

| 环节 | 结果 |
| --- | --- |
| 原始 output 含 `</think>` | **100.0%** |
| 经 `clean(output, 1200)` 后仍含 | **71.7%**（中位 1,912 字符被砍到 1,200，**砍掉 52% 字符**） |
| 再经 512 token 打包后 | — |
| **只剩 `<think>` 没有 `</think>`** | **74.7%** |

也就是说：模型从训练数据里**一次都没见过「关上 think、给出答案」**。它学到的是
「`助手：` 之后输出 `<think>` 加一大段中文自问自答，然后停」。

这就是泄漏的完整机制——**不是模型没学会推理，是数据没给它答案。**

> 为什么 v9 里也有 `<think>` 数据却不泄漏：那些是 v9 基座里的**英文**创意写作 CoT
> （`<think> Okay, the user wants a short story…`），迁移不到中文题上。
> v10 加入的**中文** R1 才让它在中文题上泄漏。

## 3. 窗口账：512 下「完整答案」与「CoT」只能二选一

抽 2,018 条 R1 量 token：

| | 中位 token | p90 token |
| --- | --- | --- |
| think 段 | 618 | 1,907 |
| **答案段** | **583** | 1,227 |
| 全样本 | 1,421 | 2,674 |

| 512 窗口能装下 | 比例 |
| --- | --- |
| 完整 think + 答案 | **2.4%** |
| 答案单独 | 41.3% |
| 短 CoT（think 取头部）+ 完整答案 | 25.6% |

**答案中位数就是 583 token，加上提示词已经超过 512。** 所以在 512 窗口下必须取舍。

## 4. 正确的修法：窗口与字符上限必须同时抬

两级截断对应两个参数，缺一不可：

| 参数 | 旧值 | 新值 | 作用 |
| --- | --- | --- | --- |
| `--r1_max_chars`（读取端） | 1,200 | **4,000** | 别在字符级就砍掉 `</think>` |
| `--seq_len`（打包端） | 512 | **2,048** | 让完整 CoT 装得下 |

`scripts/build_chat_mix_v13.py` 就是这么做出来的。**实测效果**：

| 数据集 | 窗口 | token | `<think>` 行 | `</think>` 行 | **闭合率** |
| --- | --- | --- | --- | --- | --- |
| `chat_pack_v9`（基座） | 512 | 280.6M | 7,974 | 144 | 1.8% |
| `chat_pack_v10`（v10 用） | 512 | 482.3M | 117,333 | 27,796 | **23.7%** |
| `chat_pack_v12`（剥离） | 512 | 471.7M | 7,974 | 146 | 1.8%（think 被剥掉） |
| **`chat_pack_v13`** | **2048** | **552.3M** | 80,504 | **69,199** | **86.0%** |

R1 部分单独算 **95% 闭合**（剩下 7,974 个未闭合的是 v9 基座遗留的英文样本）。
R1 的 token 从 44.8M（剥离版）涨到 **147.9M**——那 100M 就是之前被切掉的推理过程。

### 4.1 一个必须避开的坑

**不要用 `build_chat_mix_v9.py --seq_len 2048` 从原始语料重建大窗口。** 实测长文本读取器会涨到
13.3 GB RSS 且以约 1 GB/分钟继续增长，系统可用内存只剩 1.8 GB 时被 OOM 杀掉。

正确做法是 `build_chat_mix_v13.py`：**只重切 v9 已有的 token 流**（流式，不走那些读取器），
仅对 R1/wiki/锐智吧**重新编码**——而这三者正是需要在宽窗口下重做的部分。

### 4.2 为什么 v11 的「扩窗」没修好这件事

`build_chat_mix_v11.py` 把 v10 那些**已经截断的 512 行**摊平后重新切片成 8192 宽的行。
截断在 v10 构建时就固化进 token 了，**重切窗口救不回来**。

所以当时那句「扩窗后 R1 截断率大降」的推论，**和被实现出来的东西不是一回事**。
8K/4K 那条路从一开始就不可能修掉泄漏。

## 5. R1 思维链该怎么训（文献结论）

### 5.1 DeepSeek-R1 官方方法

| 阶段 | 方法 | 关键点 |
| --- | --- | --- |
| R1-Zero | 纯 RL（GRPO）无 SFT | format reward 鼓励 `<think>…</think><answer>` 结构，推理行为**从 RL 涌现** |
| R1 冷启动 | 600k 高质量 CoT 样本 SFT | 从 R1-Zero 蒸馏推理轨迹，教「推理格式」 |
| R1 主训练 | RL 多轮迭代 | 数学/代码/科学推理强化 + 通用能力保持 |
| R1-Distill | 把 R1 输出蒸馏到小模型 | Qwen/Llama 做 **SFT**，直接学思考格式 |

**`<think>` 是 RL 的格式奖励与推理界面的约定，不是预训练语料自带的。**
小模型用 R1-Distill 数据 SFT，本质是**蒸馏**而非自然学习。

### 5.2 小模型蒸馏 CoT 的已知失败

*Small Models Struggle to Learn from Strong Reasoners*（ICML 2025）：强推理者的 CoT 常有
2,000+ 推理 token，小模型容量装不下，学到的结果是**要么复读要么崩**。
R1-Distill 的 Qwen-1.5B 版本就明显弱于 7B。

**对 272M 的启示：它比 R1-Distill 的 Qwen-1.5B 还小，直接蒸馏长 CoT 是逆天而行。**

### 5.3 四种处理方式

| 方式 | 描述 | 对本项目的评价 |
| --- | --- | --- |
| 保留完整 think | 原样学 R1 输出 | ❌ 272M 装不下（512 窗口只装下 2.4%） |
| **剥离 think** | 只留 `</think>` 后的最终答案 | ✅ 简单可靠；R1 的知识保留，不展示过程。代价：不学 CoT |
| think 降权 | think 段 loss 权重低、答案高 | ✅ 备选，需改数据管线 |
| **短 CoT（保结构）** | 保「开→推理片段→关→答」完整格式 | ✅ 512 窗口下唯一能保住格式的方案 |

**v13 走的是「保结构」路线**：窗口开到 2048 让完整 CoT 装得下（86% 闭合）。
如果受限于算力必须留在 512，则「剥离 think」是次优解。

## 6. 长上下文扩展

### 6.1 RetNet 的天然优势

- **推理 O(1)**：recurrent 模式每 token 常数状态，与窗口无关
- **训练 O(L·C)**：chunkwise 模式，C=64 → 激活随窗口**线性**增长（不是 Transformer 的 O(L²)）
- **xPos 可外推**：相对位置旋转编码

### 6.2 8GB 显存核算（272M fp32，已实测校正）

| seq_len | 实测显存 | 步时（batch 4, bf16） | 可行性 |
| --- | --- | --- | --- |
| 512 | 5.5 GB | 0.480 s/it | ✅ 宽松 |
| 2048 | **7.58 GB** | **2.283 s/it** | ⚠️ 贴合，只剩约 600 MB 余量 |
| 4096 | 超出 | 12.34 s/it（fp16 加固分支） | ❌ batch 4 放不下 |

**每 token 效率随窗口只轻微下降**：512 → 2048 掉 16%（4,267 → 3,589 tok/s）。
但时间预算要按总 token 算——2048 下 12,500 步 ≈ 512 下 50,000 步的 token 量。

### 6.3 实施路线

| 步骤 | 内容 | 状态 |
| --- | --- | --- |
| ① | 修 R1 截断（剥 think 或保结构） | ✅ v13 用「保结构」 |
| ② | 扩窗到 2048 并验证 8GB 下稳定 | ✅ 实测 7.58 GB |
| ③ | 评估长上下文是否解决完题/记忆问题 | ⏳ 需先让基准能测长上下文（[`04`](./04_路线与扩展研究.md) P0） |
| ④ | 渐进到 4096+ | ❌ 8GB 卡不可行，需 bf16 + batch 2 或更大显存 |

### 6.4 要改的代码

- `encode_dialogues_batch(max_len=...)` 已支持 `max_len`，只需把构建脚本的 `--seq_len` 改大
- **同时**要抬高读取端的字符上限（`--r1_max_chars`），否则字符级就砍掉了
- 训练脚本 `--chunk_size` 保持 64（自动适配窗口）
- 行宽 = `seq_len + 1`（v13 是 2049）
