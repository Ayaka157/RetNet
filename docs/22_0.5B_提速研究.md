### 0.1 更正：2,077 MiB 的「缺口」是我漏数

`[转引]` `docs/16` §1.2 的逐张量手算（batch 1、seq 2048、bf16、**关**检查点、chunk 64）：

| 项 | 值 |
|---|---|
| 单层被保存/峰值活着的张量 | **~188 MB** |
| × 20 层 | 3.76 GB |
| LM head / 损失（`logits` bf16 81.9 + `logits.float()` 163.8 + `log_softmax` 163.8） | 0.41 GB |
| **激活合计** | **4.17 GB = 3.88 GiB** |

`[实测]` 独立锚点：`logs/remote_2026-08-25/logs/mem_profile_out.txt` 的
`max_memory_allocated = 4.17 GB`。**两者逐位吻合。**

**所以 272M 的完整分解是**：

| 块 | 值 | 来源 |
|---|---|---|
| 参数（fp32） | 1.01 GiB | `[推导]` 272.3M × 4 B |

### 2.3 步时：换成一条**可校核的计算量模型**（本文第 2 处自我更正）

`[推导]` `scripts/flops_model.py`。上一版我用 `scripts/scale_speed.py` 的三种方法
（A 用 0.85/0.50 的次线性幂律、B 从旧运行拟合出 `P^1.151`），给出 1.54~2.03 s。

1.7 倍，而固定形状族下 FLOPs 对每 token 激活计算量是**严格线性**的。已废。

新模型的构造（**只用实测锚点，不做幂律外推**）：

```
T_step = floor · (L/20) + (713 ms − floor) · (MAC_active / MAC_基准)     [关检查点]
再 × ckpt 倍率带入目标尺寸（那里必须开检查点）
```

其中 `floor` 是发射/空闲地板，`MAC_基准` 是现状配置自己的每 token 前向 MAC

`MAC/token` 由逐张量形状数出来，四条独立校核**全部通过**：

| 单层 FFN 参数 = `2·d·ffn` | 83,886,080 | meta device 加宽 ffn 的实测差分 | **0** |
| 272M MAC/token | 282.8M | `docs/16` §4.3 的 281.3M | 0.54% |
| S1 MAC/token | 215.2M | `docs/16` §4.3 的 214.5M | 0.35% |
| **700M（d1024/L54）步时** | **2,358~2,423 ms** | `docs/16` §4.1 用**另一套方法**（每层边际 0.1301 GB 线性缩放）估 **~2,300 ms** | **~3~5%** |

### 2.4 `inner_scores` 随 chunk_size 二次增长，且被提升成 fp32（本文新发现）

`[推导]` 逐张量数 `retention_fast.chunkwise_batched`：

```python
inner = torch.matmul(
    torch.matmul(qr, kr.transpose(-1, -2)) * inner_mask[None, :, None, :, :], vr)
```

`inner_scores = matmul(qr, kr^T) * inner_mask` 的形状是 `[1,H,nc,C,C]`，
元素数 = **H·L·C**，对 chunk size 线性（nc=L/C）。
更关键：`inner_mask` 是 **fp32**，相乘后**整个张量被提升成 fp32**——是 bf16 的两倍。

| C | nc | `inner_scores`（单层） | 单层合计 | × 20 层（272M） |
|---|---|---|---|---|
| 64 | 32 | 8.00 MiB | 113.31 MiB | **2.21 GiB** |
| **128** | 16 | 16.00 MiB | 113.27 MiB | **2.21 GiB** |
| 256 | 8 | 32.00 MiB | 125.25 MiB | 2.45 GiB |
| 512 | 4 | 64.00 MiB | 155.25 MiB | 3.03 GiB |
| 1024 | 2 | 128.00 MiB | 218.25 MiB | 4.26 GiB |

**C=64 与 C=128 的激活总量完全相同**（其余项与 C 无关，`U`/`S_all` 随 nc 缩小正好抵消）。
而 `[实测]` 272M 的 chunk 扫描显示 64 与 128 速度也打平（663 vs 662 ms）。

**推论**：**128 是安全的默认；C≥256 要给激活让出 0.24~2.05 GiB。**
这给 `docs/16` §5.3 里"chunk 512/1024 已被否定"补了一条**机理层面**的原因
（原来只有实测慢，没说为什么不该退而求其次用 256）。

### 2.6 参数/算力解耦前沿——**`docs/16` §7.1 问的问题和用户问的不是同一个**

这是本文最有价值的一节，而且起点是我发现**自己上一版 §6 的论证有结构性缺陷**。

**先说那条恒等式**（`[推导]`，`scripts/flops_model.py` §1 校核 C/D 已验）：

固定形状族（`vdim/d`、`ffn/d`、`key_dim` 恒定）下，逐层

```
前向 MAC/token = κ(d, C) × P_active
```

`κ` **不是普适常数**，但跨配置散布只有 ±1%（实算，C=128：d1024/L20 = **1.0494**、
d1408/L20 = **1.0367**、d1408/L24 = **1.0370**、d1216/L26 = 1.0427；C=64 时普遍低约 0.01，
C=256 时高约 0.02）。所以 **`MAC/token ∝ P_active` 的线性关系是精确的**，
而 κ 本身随 `C` 涨、随 d 略降。
（⚠️ 本文早期版本写「κ = 1.033，与 d、L、heads 都无关」**是错的**：
1.033 对应 C=64 的窄深配置，且 κ 确实随 d 与 C 变化。**线性结论不受影响，那句话已撤回。**）
所以步时公式里

```
T_step ≈ launch_floor + 6 · κ · P_active · tokens / TFLOPs_eff
```

**只出现「每 token 激活参数量」`P_active`，不出现总参数量 `P_total`。**
这就是「参数翻倍 = FLOPs 翻倍」的严格形式，也是 §6 那个否定结论的证明。

**但同一条式子立刻给出了唯一的逃逸口**：既然成本只认 `P_active`，
那就让 `P_total > P_active`。穷举之后能做到这件事的机制**只有条件计算**：

| 机制 | 对 `P_total` | 对 `P_active` | 结论 |
|---|---|---|---|
| **MoE**（`E` 专家 top-1） | ↑ | **平** | ✅ 唯一能「加参数不加算力」 |
| **MoD**（部分层按容量跳层） | 平 | ↓ | ✅ 反向的同一个旋钮 |
| 权重共享（S4） | ↓ | ↓ | ❌ 减的是唯一参数，方向相反 |
| 量化训练 | 平 | 平 | ❌ 不改「每 token 要算多少」 |
| GQA/MQA | 平 | 平 | ❌ 本架构无 KV cache |
| 加宽词表 | ↑ | ↑ | ❌ 头也是 `V·d` MAC/token，同比例 |

**然后是 `docs/16` §7.1 的问题所在。** 它的原话是：

> MoE 买的是"每 token 更少的 FLOPs"，代价是"更多常驻参数"。在 10 B/参数 的约束下，
> **常驻参数量就是显存**。构造一个标准配方（8 专家、top-2、每专家 `ffn/4`）：
> ……**付 31% 的显存买 17% 的算力**……完全反向。

它问的是「**MoE 能不能省 FLOPs**」→ 答「不能，要付显存」。**这个答案是对的。**
但用户问的是「**能不能加参数不加 FLOPs**」——而 §2.2 刚刚证明
0.5B 稠密还剩 **2,052 MiB**、0.6B 还剩 **1,121 MiB** 预算。
**「本机显存受限」这个前提在 0.5B 的尺度上已经不成立了**，所以 §7.1 的否决理由
（付不起那份显存）在这个尺寸上失效。

**代进去算**（`scripts/flops_model.py` §2b，骨架固定 d1024/L20、每专家 `ffn=2d`、
top-1 → **激活 FFN 计算量与稠密逐位相同**）：

| E | P_total | P_active | MAC/token | 显存 | 余量 | 步时 | vs 713 |
|---|---|---|---|---|---|---|---|
| 1 | 272M | 272M | 286M | 3.20 GiB | 4,315 MiB | 713 ms | 1.00×（关检查点） |
| 4 | 524M | 272M | 286M | 5.55 GiB | 1,914 MiB | 951~1,074 ms | 1.33~1.51× |
| **5** | **608M** | 272M | 286M | 6.33 GiB | 1,114 MiB | 951~1,074 ms | 1.33~1.51× |
| **6** | **692M** | 272M | 286M | 7.11 GiB | 313 MiB | 951~1,075 ms | 1.33~1.51× |
| 7 | 776M | 272M | 286M | 7.89 GiB | **−487 MiB** | — | ❌ 装不下 |

> **每加 1 个专家：+83.9M 名义参数、+0 算力、+0.84 GiB 状态。墙在 E=6 与 E=7 之间。**
> 也就是说**在 272M 的步时预算里，名义参数能推到 ~0.69B**；
> 而稠密要到 0.6B 就得付 2.51~2.68×。
> **MoE 每单位步时换到的名义参数是稠密路线的约 2.5 倍。**

步时那一列已含条件计算的开销带（**+6~13%**，且这个带是**推导**出来的，不是猜的）：

| 开销来源 | 量 | 依据 |
|---|---|---|
| **固定容量 padding** | **2.5~7.9%** | 独立均匀路由下每个专家负载 ~ `Binomial(seq, 1/E)`，相对 sdev = `√((E−1)/seq)`。seq=2048、E≤6 → 相对 sdev ≤ **4.9%**，取 max 得 **cf ≈ 1.04~1.09**；Switch 工程默认 `cf=1.25`。padding 只作用于 FFN，FFN 占单层 MAC 的 **31.6%** → `(cf−1)×31.6%` |
| 路由器 + gather/scatter 内核 | 1~3% | 未实测 |
| 优化器要更新 `P_total` 份参数 | ~2.8% | E=5 时 +336M 参数 × ~15 B ≈ +5 GB 流量 ÷ ~200 GB/s ≈ +25 ms |

> 📌 **顺带一个对本项目有利的发现**：Switch 之所以需要 `cf=1.25`，是因为它序列短、
> 专家数多。本项目 **seq=2048 且 E≤6**，理想路由下 `cf` 只需 **1.04~1.09**，
> 即 padding 开销可以压到 **2.5%** 左右——**长序列在这里反而帮了忙**
> （每微批 2048 个 token 足以把专家负载平均掉）。
> 这是**唯一**一条对 MoE 路线的正面证据，但它只在"路由确实学得均匀"时成立，
> 需要负载均衡损失配合。

**顺带得到一条对稠密路线本身有用的结论**（`flops_model.py` §2b(a)）：同样是 ~700M，

| 配置 | 步时 | vs 713 |
|---|---|---|
| d1664 / L20 | 1,996~2,170 ms | **2.80~3.04×** |
| d1408 / L28 | 2,072~2,220 ms | 2.91~3.11× |
| d1216 / L38 | 2,189~2,305 ms | 3.07~3.23× |
| d1024 / L54 | 2,358~2,423 ms | **3.31~3.40×** |

**宽度胜出 15~18%**，因为 `floor ∝ 层数`：深度要付两次——激活 ∝ √(P·L)，
发射地板 ∝ L。`docs/16` §4.4 只在**激活**层面论证过「加宽更便宜」，这里补上了**步时**层面。

### 2.7 §2.3 的步时模型**偏保守**（新发现，单侧界）

`[推导]` §2.3 的模型把**全部** compute 按 MAC 比（∝ d²）缩放。但真实步时里有一大块是
**带宽受限的逐元素/归一化/损失** 算子，它们只随张量元素数（∝ d）走。
只要这两句成立，模型就**必然高估**——方向确定，不需要任何有争议的常数。

降幅有闭式：`降幅 = (1 − b) × (MAC比 − 元素比) / MAC比`，`b` = GEMM 占 compute 时间的比例。

| 方案 | MAC 比 | 元素比 | 逐元素占比 51% 时的降幅 |
|---|---|---|---|
| 0.5B 宽浅 | 1.829 | 1.375 | **12.7%** |
| 0.6B 宽浅 | 2.175 | 1.650 | **12.3%** |

**所以 §2.3 那张表要按单侧读**：完整区间是
**0.5B 1.79~2.26×、0.6B 2.10~2.68×**——比我原来报的 2.10~2.26 / 2.51~2.68 **更宽**。

`b` 的不确定性来自 `docs/15` §0.3 没写清「~49%」的分母是墙钟还是忙时；
由 10.28 TFLOP 与 batch1 形状峰值 26~42 TFLOPs 反推 `b ∈ [0.43, 0.70]`
（我采用可辩护的 `[0.49, 0.70]`）。**这是更诚实的结果，不是更好的结果预告。**

### 3.1 检查点代价：`docs/16` 的 `936/732` 与本文曾用的 `903/713` **都不是同口径**

我上一版拿 `903/713 = 1.266×` 当检查点代价，**错了**：

| 数对 | 分子 | 分母 | 混了什么 |
|---|---|---|---|
| `936/732`（`docs/16`） | batch1×accum4 + 检查点 | ？ | 分母 732 在这次记录里没找到同条件的对应跑 |
| `903/713`（我上一版） | **batch 4** + 全量检查点 | **batch1×accum4** + 关检查点 | **微批形状 1→4 与检查点开关同时变了** |

微批从 1 变到 4 本身就会改变 GEMM 的 M，`docs/15` §0.3 正是把「occupancy/split」列为已知问题。
所以 `903/713` 里**混进了批形状的增益**，真实的检查点代价比 1.266 更高。

**能拿到的最接近同口径的数对**是 `docs/15` §3.1 的
`batch1×accum4 + 检查点 = 936 ms` 对 `C = 713 ms`（两侧都是 batch1×accum4）：
**936/713 = 1.313×**。但它的分子那次跑**还在用 fp32 AdamW**（8-bit Adam 是后续的优化二），
所以这个比值又**偏高**（把 fp32→8-bit 的收益算进了检查点）。

**所以检查点代价只能给区间 `[1.27, 1.31]`，不能给点值。**
`flops_model.py` §1b 进一步证明：这个区间与发射地板 `floor ∈ [92,148] ms`
**只能定住一个**，另一个必须实测——**这正是 E1a/E1b 的任务**（同 batch、同 optim、
只切检查点开关，驱动已挂）。在那两个数出来之前，§2.3 的步时一律按区间报。

### 3.2 发射地板 `floor` 的**第三条独立约束**：GPU 空闲率与内核数

`docs/15` §0.2 用 `scripts/diag_gpu_busy.py` 在**同一次运行**里同时记了墙钟、
GPU 累计忙时和内核启动数（注意原文标注：**电池供电下测，比值可信、绝对值偏低**）：

| 配置 | 墙钟 | GPU 忙时 | GPU 空闲 | 内核启动数 | 每内核摊到的空闲 |
|---|---|---|---|---|---|
| B（batch 4 + 检查点） | 1,364.7 ms | 1,304.0 ms | 60.7 ms（4.4%） | 3,427 | **17.7 µs** |
| C（batch 1 × accum 4） | 1,156.6 ms | 916.5 ms | 240.1 ms（20.8%） | **10,116** | **23.7 µs** |

`[推导]` 两条换算都指向同一个量级：

1. **按空闲率**：C 的空闲占 **20.8%**。空闲率是比值，不受 profiling 绝对膨胀影响
   （profiling 把墙钟吹到 1,156.6 ms，真实稳态是 713 ms，膨胀 1.62×；
   若忙时也被同倍膨胀，则真实忙时 = 916.5/1.62 = 566 ms，真实空闲 = 713 − 566 = **147 ms**）。
2. **按内核数**：10,116 个内核 × 摊到的空闲 = 148 ms → **有效暴露发射成本 14.6 µs/内核**。

两条独立路径都给 **`floor ≈ 148 ms`**。而 17.7~23.7 µs 是**裸**发射延迟，
有效暴露成本 14.6 µs 比它小——因为下一个内核可以排队重叠，只有一部分延迟暴露出来。
这是物理上说得通的，也解释了为什么 `docs/15` §0.2 说「有富余，摘掉几个内核不改变墙钟」。

⚠️ **它带来一个必须写下来的张力**：若 `floor = 148 ms`，则要用 936 ms 那个点
反解出的检查点倍率是 **1.264**，**低于** §3.1 由同批形状比值得出的 `[1.27, 1.31]`。
两者不能同时成立到小数点后两位，可能的解释有三条，**现在无法区分**：

| 解释 | 后果 |
|---|---|
| profiling 的膨胀对忙时与墙钟不等倍，使空闲率被高估 | `floor` 应低于 148 |
| 936 ms 那次是 **fp32 AdamW**，比 8-bit 慢 | 真实倍率低于 1.313（8-bit 版约 **1.302**） |
| 4/3 的重算 FLOPs 倍率对时间不成立（重算那遍效率更高） | `ckpt` 可以低于 4/3 |

**唯一能分开这三条的就是 E1a/E1b**（同 batch、同 accum、同 8-bit Adam，只切检查点开关）。
在那之前，§2.3 的步时区间按 `floor ∈ [92,148] ms` × `ckpt ∈ [1.27,1.31]` 的组合给出——
这个组合**已经覆盖了上述三种解释的全部后果**，所以它是保守的，不是乐观的。

> **副产物**：C 配置一步要发射 **10,116 个内核**。这既是 20.8% 空闲的来源，
> 也是为什么 `docs/15` §6 里那一串「摘掉几个内核」的微优化全部测出 0%
> ——地板是 148 ms 的**总量**问题，不是某几个内核的问题。

**没有发现 `docs/16` 的结论性错误。** 本文的价值主要在 §2.6（解耦前沿）与 §0.1/§2.3/§3.1（我的自我更正）。

### 4.2 ✅ **恢复 L1（分层/选择性检查点）——它被 `docs/15` 否定是因为场景不对**

**`[转引]` `docs/15` §6 的原话**：

> 分层梯度检查点（只检查点前 K 层）❌ 笔记本：K=10/20 → **816 ms**，K=6/20 → **4457 ms**（颠簸）；
> 本机 3070：K=10/20 → **724 ms**（C 是 704）。**两块卡上都打不过 C**。
> 代码保留（`set_checkpoint_layers`），**但在「batch1 全不检查点」这个更优解存在时没有用武之地**。

**最后半句是全部关键**：它是**在 272M 上**被否定的，因为那里「全不检查点」（704 ms）装得下，
而分层检查点（724 ms）只是逼近它、并不更快。

**但在 0.5B/0.6B，「全不检查点」不存在了**：§2.2 已算，不关检查点的激活需求是
3.88 GiB × 1.852 ≈ **7.2 GiB**，远超可用显存。所以那个"更优解"消失了，
**分层检查点成为唯一能把剩余显存预算换成速度的手段**。

`[推导]` 它的收益。全量检查点的代价是 `c ≈ 1.29`（§3.1 区间中点，即额外 0.29）。
放开 `k` 层就免掉这 `k` 层的重算，所以**收益 ≈ (k/L) × 0.29**：

| 配置 | 余量（§2.2） | 单层未检查点激活（188 MB × 1.375） | 可放开层数 `k` | 收益 = (k/L)×0.29 | 残留代价 |
|---|---|---|---|---|---|
| 504 M | **2,052 MiB** | 258 MB = 246 MiB | ⌊2052/246⌋ = **8 / 20 层** | 0.4 × 0.29 = **11.6%** | 1.29 → 1.14 |
| 599 M | **1,121 MiB** | 246 MiB | ⌊1121/246⌋ = **4 / 24 层** | 0.167 × 0.29 = **4.8%** | 1.29 → 1.23 |

（余量换成 §2.2 的紧口径 7,593 MiB 后重算；层数与上一版相同，只有余量与百分比变了。）

而 `[转引]` `docs/15` §6 在 3070 上实测 K=10/20 = **724 ms 对 C 的 704 ms（仅 +2.8%）**，
远低于按比例外推的 +14%——**说明实测收益可能比我这个保守推导更大**。

> ⚠️ **但它是脆的，失败模式很凶**：`docs/15` 同一行记录笔记本上 K=6/20 → **4457 ms（颠簸）**。
> 放开检查点会推高峰值，**一旦越过显存墙就触发颠簸，代价是 6× 而不是 1.1×**。
> 所以这条**必须逐档实测**（E2），不能按公式选 K。

**接线需求**：`set_checkpoint_layers` 的代码已在
（`modeling_retnet.py:413`、`bench_trainer.py:139` 已会用），
但 `retnet_hf/train.py` 里**没有这个参数**（§2.5 的第 4 例死配置字段）。
要让它在真实训练里可用，需要 §7.2 那约 6 行接线。

### 4.3 结论：L1 从「撤回」变为「**目标尺寸下的第一优先实验**」

理由：它是**唯一**一条能把"必须开检查点"的代价换回来的路，而项目已有其机制与实测锚点。
代价是不确定性高（颠簸风险 + 需要逐档扫）。

## 6. 对用户目标的直接回答：**稠密没有解；条件计算有解，但解出来的不是你要的那个东西**

### 6.1 稠密：**没有「0.5–0.6B 同速」的解**（这条是定理，不是经验）

`[推导]` §2.6 的恒等式 `MAC/token = κ · P_active`。稠密下 `P_active ≡ P_total`，所以

```
T_step − floor ≈ 6 · κ · P_total · tokens / TFLOPs_eff     ← 对 P_total 严格线性
```

**要守住步时就必须守住参数量。** 这不是工程没做到位，是同一个恒等式的两端。
所有"看起来能逃"的想法都在 §2.6 的表里被逐条否掉了，其中最关键的两条：

| 想法 | 为什么不行 |
|---|---|
| S1（`value_dim` 减半） | 它把**参数与 FLOPs 一起**减（单层 24.73M → 18.40M MAC）。要维持 0.5B 就得加层把 FLOPs 加回来——**净 FLOPs 不变**。`flops_model.py` 实算：无 S1 的 0.5B = L20 / 504.2M / **522.7M MAC**；带 S1 的 0.5B = L27 / 510.1M / **525.0M MAC**——**+1.2% 参数换来 +0.4% 算力**。0.6B 更干净：L24 → L32，参数 599.4M 不变，MAC 621.6M → **617.0M（−0.7%）**。**S1 完全不可用于"同参数更快"** |
| 加宽词表 | 输入侧查表是 O(1)，但 **LM head 是 `V·d` MAC/token**。`P_total` 与 MAC 同比例涨 → 不改变比值 |

**所以稠密 0.5B = 2.10~2.26×，0.6B = 2.51~2.68×**（相对现状 713 ms，微基准口径）。
`docs/16` §4.1 的「线性涨」在这里第一次被推成可校核的恒等式。

**能抢回来的只有**：`docs/16` §5.3 的零散项（合计 < 10%）、已兑现的闭式解（1.08×）、
以及 §4.2 的 L1 分层检查点（0.5B 上约 9~11%）。**「用稠密守住速度」这个目标无法达成。**

### 6.2 条件计算：能守住速度，但换来的是**名义参数**，不是稠密容量

§2.6 给出：MoE 在 272M 的步时预算里能把**名义**参数推到 **~0.69B**（E=6，1.33~1.51×），
稠密要到 0.6B 得付 2.51~2.68×。

**但下面六条必须和这个数字一起读，任何一条被省略都是误导**：

| # | 反面证据 | 后果 |
|---|---|---|
| 1 | **名义参数 ≠ 稠密容量**。MoE 的尺度律（[arXiv:2402.07871](https://arxiv.org/abs/2402.07871)）是在**等激活 FLOPs** 下优于稠密；同 `P_total` 的 MoE 明显弱于同 `P_total` 的稠密 | 0.69B/272M-active ≠ 0.69B 稠密。**`docs/04` §4 那条「数学/结构化输出要 ≥0.5–1B」的证据是稠密尺度律，用它论证 MoE 的名义参数量无效** |
| 2 | **每专家数据被稀释**：top-1 下每个专家只见 1/E 的 token。E=5 时专家的等效数据量降到 1/5 | `docs/16` §4.2 已指出只有 ~2.5 token/参数，再除 5 = **0.5 token/参数**。E 越大越糟 |
| 3 | **会打断 `torch.compile`**：数据相关的专家分桶让形状变化。本项目 2.41× 的提速**全部**来自 compile + 融合 | 必须用固定容量路由（Switch 式 `capacity_factor`），代价是 FFN 多算或丢弃溢出 token。**这是最大的工程风险** |
| 4 | 单卡、batch 1 | 无专家并行；分桶后每个专家 GEMM 的 M 从 2048 降到 ~2048/E，正好加剧 `docs/15` §0.3 的 occupancy 问题 |
| 5 | FLOPs 模型**没算**的开销：路由器、gather/scatter 内核、优化器要更新 `P_total` 份参数（608M 对 272M：+5 GB 流量 ≈ +25 ms） | 已在表里用 +5~15% 的倍数带覆盖，但**没有实测** |
| 6 | **本项目零证据** | 模型代码里没有 MoE。要做先加实现 + 负载均衡 + 固定容量，再跑 A/B。272M 尺度上没有任何自己的数据支持它值得做 |

**结论：MoE 能兑现「0.69B 名义参数 @ 现状步时 + 40%」，但它兑现的不是用户要的那个 0.69B。**
把它当"神秘训练技术"直接用，最可能的结果是：**同时付两份代价**——
名义参数没换来能力（第 1、2 条），工程复杂度又吃掉了 compile 的收益（第 3 条）。

### 6.3 于是真正的分叉点（这才是要用户拍板的）

| 路线 | 名义参数 | 每 token 算力 | 步时 | 主要风险 |
|---|---|---|---|---|
| **A. 不动**，把数据喂够 | 272M | 286M | 1.00× | 与 `docs/04` §4 的尺度证据冲突 |
| **B. 0.5B 稠密**（推荐先做） | 504M | 523M | **2.10~2.26×** | 尺度收益可能不存在；余量 2,052 MiB 充裕 |
| C. 0.6B 稠密 | 599M | 622M | 2.51~2.68× | 同上，且余量只剩 1,121 MiB |
| D. MoE E=6（骨架不动） | 692M | 286M | 1.33~1.51× | §6.2 六条，尤其 1、3 |

**我的建议顺序**：

1. **先做 B**（0.5B 稠密）。它同时检验两件事：尺度到底换不换得到能力、
   以及 §2.2/§2.3 的预算与步时推算对不对。代码已经能跑，余量最充裕。
2. **B 若证实「尺度确实换来能力」，再考虑 D**——因为那时 D 的收益才有意义。
3. **B 若也证实不了，那就说明瓶颈在数据不在参数**（这与 `docs/16` §4.2 的方向一致），
   该做的是路线 A + `docs/21` §1.6 的 `replay` 取数修复，而不是继续加参数。
4. **无论走哪条，都先把 token/参数 从 2.5 提上去**：这是唯一条改变分母、
   且不需要改架构、不需要新代码的路。

**这条路的代价（`docs/21` §3.3 的独立数字，本文复算一致）**：
已落地语料 `docs/07` 共 **3.4 B token** = `3.4e9/8192` = 415,039 步。

| 配置 | 端到端 s/步 | 吃完 3.4 B 的墙钟 | token/参数 |
|---|---|---|---|
| 现状 272M | 0.79 | **3.8 天** | **12.5** |
| 0.5B 稠密 | 1.73 | **8.3 天**（`docs/21` 独立算 8.5） | 6.7 |
| 0.6B 稠密 | 2.05 | **9.8 天** | 5.7 |

Chinchilla 的 20 token/参数：272M 要 5.4 B（6 天）、0.5B 要 10.1 B（**25 天**）、
0.6B 要 12.0 B（**35 天**）。**同样喂一遍数据，参数量翻倍就让墙钟涨 2.2~2.6 倍**——
这就是「换参数 vs 换 token」的真实汇率，是 §6.3 分叉点里唯一有数的那个维度。

> **一句话**：稠密 0.5–0.6B 的速度代价是 **2.1~2.7×**，这个必须接受；
> 想不付这个代价就只能改成 MoE，而 MoE 换到的是**名义**参数量——
> 用它去兑现 `docs/04` 那条稠密尺度律是**无效论证**。

「这个数是在什么条件、哪台机器、哪次运行下测的」；拿不到同口径的第二个点就写「不可比」。

| # | 类型 | 具体 |
|---|---|---|

| 2 | 跨 regime | 关检查点的实测 vs 开检查点的估算 |
| 3 | 跨冷热 | 第二段的**冷**评测 95.5 s vs 第一段的**热**评测 57.3 s |

| 6 | **跨 chunk 口径** | 拿 chunk 128 的 MAC 除以 chunk 64 的基准，锚点行算出 722 而非 713（§0 第 7 条） |

**另外发现一处既有文档的不一致（不是错误，是口径没写清）**：
**788 ms** 出现在 `docs/19` §? 与 `docs/21` §3.4，**713 ms** 出现在 `docs/15/16/19`。
两者都对但不同口径：788 = v14 真实训练端到端（1.27 it/s，含取数/评测/日志/存盘），

**四条新增纪律**（都由本轮的教训换来的）：

1. **模型必须有锚点行**：任何预测脚本都要包含一行"现状配置"，且它必须**逐位复现实测值**。
   本文的 `flops_model.py` 现状行 = 713 ms（实测 713），`docs/16` 的 272M 参数量 = 272,304,448（逐位）。
   锚点行算不对，说明口径错了，不是模型"有一点误差"。
2. **引用别人结论前先确认问题相同**。见 §0 第 6 条。
3. **区间优于点值**，且要说清区间来自哪两个自由参数的端点组合
   （本文：`floor ∈ [92,148] ms` × `ckpt ∈ [1.27,1.31]`）。
4. **脚本自检**：`flops_model.py --check` 是四条独立锚点的断言，任一不过返回非 0 退出码。
   它抓到了我自己写的两个缺陷（§0 第 7 条）。

```powershell
python scripts\flops_model.py       # ★ 本文核心：计算量模型校核 + 解耦前沿 + 容量上限
```

### 8.1 本轮抓到的运行事故：**同一张卡上两个训练进程**（我自己的操作错误）

排查「笔记本 v14 为什么从 1.27 it/s 掉到 85 s/it」时发现：

**2026-10-10 20:21 与 23:58，笔记本上被启动了两次 v14 续训，两个进程都写同一个
`checkpoints/retnet_272m_v14`。**

| PID | 启动 | config | resume | 抓到时的状态 |
|---|---|---|---|---|
| 25124 → 32572 | 20:21:24 | `v14_272m_2k_resume.json` | **true** | 26,095 步，被拖慢到 **3.19 s/it**（原 0.81） |
| 10200 → 26336 | 23:58:06 | `v14_272m_2k_cont.json` | **false** | **16 步，86 s/it** |

**证据链（全部可复核）**：

| 观察 | 数值 | 说明 |
|---|---|---|
| 显存占用 | **7,915 / 8,188 MiB** | 96.6%，贴着墙 |
| 两个 python 工作集 | 4,571 + 5,984 MB | 合计 10.5 GB，物理上装不下 8 GB 显存 |
| 功耗 | **26.78 W @ 100% "利用率"** | 健康时是 84~96 W。**满利用率 + 极低功耗 = 显存颠簸**（GPU 卡在显存搬运上空转） |
| 健康进程 s/it | 0.81 → 1.24 → 2.56 → **3.19** 且持续恶化 | 被对方不断挤出的证据 |

**为什么第二个进程是纯浪费**：它 `resume: false`，从第 0 步重启（会丢掉已有的 25,000 步进度）；
而 86 s/it 跑完 50,000 步需要 **1,180 小时**。它同时还把健康的那个拖慢 **3.9 倍**。

**处置**：**先杀父进程 10200**（`auto_restart_max: 3`，先杀子进程会被自动重启），
再杀子 26336。结果：

| 指标 | 处置前 | 处置后 |
|---|---|---|
| 显存 | 7,915 MiB | **7,058 MiB** |
| 功耗 | 26.78 W | **86.93 W** |
| 健康进程步时 | 3.19 s/it | **0.787 s/it（1.27 it/s）** |
| 步时恢复倍数 | — | **4.1×** |

`checkpoint-{20000,22500,25000}` 三个检查点**逐字节未变**（model 1,089,253,536 B、
optim 677,014,765 B，时间戳仍是 22:40 / 23:14 / 23:47）——第二个进程只跑到第 16 步，
`save_steps=2500` 所以**没写过任何东西**，没有污染。

**教训（新增第 5 条纪律，性质和前六条不同）**：前六条是**数值口径**错误，这一条是
**资源竞争**错误。「同一张卡不跑第二个 GPU 作业」这条规矩我对**本机**执行得很严
（无人值守驱动专门等基准 PID 退出），**但它在跨机器时没有自动生效**——
我按「本机 GPU 忙不忙」判断，而笔记本是另一张卡。
**规矩要写成按设备实例判断，不能按"我这台机器"判断。**

**建议的加固（尚未实施）**：`run_task.py` 在启动前，若 `output_dir` 下已有 checkpoint
**且另一个进程正持有同目录**，应拒绝启动并报错。约 15 行，比事后人工发现便宜得多。
**现在不改**：健康进程正在跑，改 `run_task.py` 会在它下次自动重启时生效，
需要先设计好 stale-lock 的判定（按 PID 判活），否则可能把健康进程自己锁死。
