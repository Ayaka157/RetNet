# RetNet 放大可行性研究（理论）

> 最后更新：2026-10-09 · 初稿 2026-08-20
> 本文是**放大决策的理论底稿**。结论部分写于 100M 阶段，其中「从零训练放大不划算」的判断
> 已被实践验证并绕过——项目最终走的是本文推荐的**模型生长（net2net）**路线，见文末「实际结果」。

## 摘要

**在这台机器（RTX 3070 8GB / i7-10700K / 32GB RAM）上，把参数从 100M 提到约 200M 是硬件可行的，
但在能负担的 token 预算（3–6B）下，从零训练并不划算。**
推荐路线是「保持 100M 架构 + 大幅加长训练 + 角色扮演数据配比」，
把放大留到有 ≥4 天连续 GPU 时间时再做，并用**模型生长**热启动省掉约 30% 时间。

本文所有数字都来自本仓库实测（`logs/chat_v3`、`logs/train_loop`）与架构公式推导，
不是估计值套用别人的表。

### 实际结果（2026-10-09 补）

项目确实放大了，而且用的就是本文推荐的方式：

| 阶段 | 方式 | 结果 |
| --- | --- | --- |
| 100M → 143M | 深度生长 12→18 层（零残差插入） | 函数保持 |
| 143M → 272M | 宽度 d768→1024（`GrowthLayerNorm`）+ 深度 18→20 层 | **Δ7.25e-4** |
| 训练 | 272M RP-SFT，20k 步，3h42m | eval_loss **2.9946** |

**没有从零重训**——819M token 的预训练知识被完整继承。
生长原理与数值验证见 [`08_chunkwise_growth_research.md`](./08_chunkwise_growth_research.md)。

> 本文正文里的显存/吞吐数字按 100M 架构推算。272M 的实测吞吐见
> [`01_项目总览.md`](./01_项目总览.md) §4 与 [`10_远程部署笔记.md`](./10_远程部署笔记.md) §4。

## 1. 当前架构的精确参数账

`retnet/model.py` 的实现（`RetNetConfig`）：

| 项 | 值 |
| --- | --- |
| vocab | 20000（byte-level BPE） |
| d_model | 768 |
| layers L | 12 |
| heads H | 12 → key_dim = 64 |
| value_dim | 2·d_model = 1536（论文参数分配） |
| ffn_dim | 2·d_model = 1536 |
| lm_head | 与 embedding **权重共享**（tie_weights=True） |
| decay | γ_h = 1 − 2^(−5−h)，固定不学习 |
| 位置 | xPos 旋转（相对位置，可外推） |

每层参数（全部无 bias）：

```text
MSR : W_Q(d²) + W_K(d²) + W_V(2d²) + W_G(2d²) + W_O(2d²) = 8d²
FFN : d·2d + 2d·d                                        = 4d²
每层合计                                                  ≈ 12d²
```

于是总参数量有一个非常好用的闭式：

```text
P(d, L) ≈ 12·L·d² + V·d          (V=20000, embedding 因共享只算一次)
```

验算当前模型：`12×12×768² + 20000×768 = 84.93M + 15.36M = 100.29M`，
训练日志打印 `params=100.37M`（差值来自 LayerNorm/GroupNorm 的 1-D 参数）——公式可信。

## 2. 实测性能基线（用来推算放大后的时间）

| 配置 | 实测吞吐 |
| --- | --- |
| seq 256, batch 16, 不 compile | 18.5k tok/s |
| seq 256, batch 16, compile+inductor | 27–30k tok/s |
| **seq 512, batch 10, compile+inductor（当前 v3 训练）** | **28.8k tok/s 稳态** |
| seq 512, batch 8, 不 compile | 17.1k tok/s |
| seq 512, batch 12, compile | 29.5k tok/s（显存 7.5/8.0 GB，太满） |

换算算力利用率：`6·P·throughput = 6×1.003e8×28.8e3 ≈ 17.3 TFLOP/s`。
RTX 3070 的 bf16 稠密峰值约 40 TFLOP/s，即 **MFU ≈ 43%**——对单卡消费级 + Windows 已经算高，
说明「换更大模型」拿不到额外的效率红利，吞吐基本按参数量反比下降：

```text
throughput(P) ≈ 28.8k × (100.3M / P)      （L=512 时二次项占比仅约 1.4%，可忽略）
```

> 为什么二次项可以忽略：每 token 每层的 retention 二次开销是
> `2·L·(key_dim+value_head_dim) = 2×512×(64+128) ≈ 0.20 MFLOP`，
> 而参数项是 `2×12d² ≈ 14.2 MFLOP`，占比 1.4%。**这正是 RetNet 相对 Transformer 的优势**，
> 也意味着放大 seq_len 到 1024 只增加约 3% 计算（显存另算）。

## 3. 显存账：8GB 能装多大

训练态显存四块（AdamW + bf16 autocast，参数与梯度是 fp32）：

```text
参数 4P + 梯度 4P + Adam(m,v) 8P = 16 bytes × P
```

| 模型 | P | 优化器+参数+梯度 | parallel 模式激活（B=8,L=512） | 合计估算 | 8GB 可行性 |
| --- | --- | --- | --- | --- | --- |
| 当前 | 100M | 1.6 GB | ~1.6 GB | ~3.7 GB（实测 6.6GB，含 compile 缓存与碎片） | ✅ 宽松 |
| d1024/L16/H16 | 222M | 3.55 GB | ~2.1 GB | ~6.5 GB | ⚠️ 需省显存手段 |
| d1152/L20/H16 | 342M | 5.5 GB | ~2.6 GB | ~8.6 GB | ❌ 直接爆 |
| d1280/L22/H16 | 458M | 7.3 GB | — | — | ❌ 不可能 |

激活量公式（parallel 模式的主项就是那张 retention 分数矩阵）：

```text
score 张量 = B·H·L·L·2 bytes（bf16），每层前向保存 2 份左右
B=10,H=12,L=512 → 63 MB/份 → 12 层 ≈ 1.5 GB
```

三种省显存手段（按性价比排序）：

1. **chunkwise retention**（本仓库已实现 `--mode chunkwise`）：激活从 `O(B·H·L²)` 降到
   `O(B·H·L·C)`，C=64 时省约 8 倍激活。代价：当前实现是 Python 逐 chunk 循环，
   compile 后仍慢；要用得先把它改成批量化实现。
2. **梯度检查点**（未实现，约 30 行）：每个 `RetNetBlock` 包一层 `torch.utils.checkpoint`，
   激活降到约 1 层的量，计算 +33%。222M 模型加这个就能舒服跑进 8GB。
3. **优化器状态 CPU offload / 8-bit Adam**：本机 32GB RAM，`m,v` 放 CPU 可省 8P
   （222M 省 1.8GB），但 Windows 上 offload 每步要走 PCIe，实测常见 20–40% 掉速；
   8-bit Adam（bitsandbytes）在 Windows 上可用性不稳定，属备选。

## 4. 关键结论：token 预算决定了「不该放大」

固定墙钟时间 T，吞吐 ∝ 1/P，可训练 token 数：

```text
tokens(P, T) = 28.8e3 · (100.3e6 / P) · T
```

Chinchilla 最优配比是 `tokens ≈ 20·P`，两式联立：

```text
P* = sqrt(28.8e3 × 100.3e6 × T / 20)
```

| 连续训练时间 T | 计算最优参数量 P* | 对应 token 数 |
| --- | --- | --- |
| 12 h | 80M | 1.6B |
| 24 h | 113M | 2.3B |
| 48 h | 160M | 3.2B |
| 96 h（4 天） | 226M | 4.5B |
| 168 h（1 周） | 299M | 6.0B |

也就是说：**只有当你愿意连续训 4 天以上，222M 才不是「欠训练的大模型」。**
而欠训练的大模型在对话体验上通常明显差于充分训练的小模型
（SmolLM-135M 用 600B token 训出来，比很多 350M 少训模型更能聊）。

当前模型已经吃了约 819M（预训练）+ 123M（chat 恢复）+ 61M（SFT）≈ 1.0B token，
按 100M 参数算才 10 tokens/param，**连 Chinchilla 的 20 都没到，说明现在的瓶颈是数据量，不是参数量。**

## 5. 如果真要放大：推荐配置与生长方案

### 5.1 推荐配置（唯一值得做的一档）

```python
RetNetConfig(vocab_size=20000, d_model=1024, num_layers=16, num_heads=16,
             value_dim=2048, ffn_dim=2048)   # P ≈ 221.8M
```

- heads 16 → key_dim 64（与现在一致，xPos 旋转表不用改）
- γ_h = 1 − 2^(−5−h)，h=0..15：**最慢衰减头的记忆窗口从 2^17 增到 2^21 token**，
  对长角色设定 + 多轮历史是净收益。
- 预期吞吐：`28.8k × 100.3/221.8 ≈ 13.0k tok/s`（batch 6–8 + 梯度检查点，seq 512）
- 4.5B token ≈ 96 h。

### 5.2 用「模型生长」热启动，省掉约 30% 时间

不要从随机初始化开始，可以用已经训好的 100M 直接长大（net2net / depth-stacking）：

1. **宽度 768 → 1024**：对每个权重矩阵做分块拷贝，
   `W_new[:768, :768] = W_old`，新增行列用 `N(0, 0.02)` 小噪声，
   并把对应输出通道缩放 `768/1024` 以近似保持前向数值尺度（近似函数保持）。
2. **深度 12 → 16**：把原 12 层按顺序放入，新增 4 层插在中后段（如第 6/9/11/12 之后），
   新层的 `out_proj` 与 FFN 第二层 **零初始化** → 残差支路初始为 0，
   这是严格函数保持的（输出与 12 层模型完全一致，然后再慢慢学）。
3. **heads 12 → 16**：γ 序列重新生成即可（γ 不是学出来的，无需迁移）；
   但注意 `value_head_dim` 从 128 变 128（2048/16），恰好不变——迁移很干净。
4. embedding 直接拷贝前 768 维，新增 256 维零初始化 + LayerNorm 会自动适配。
5. 生长后先用小 LR（如 5e-5）跑 200–500M token 做「愈合」，再切正常 cosine。

经验上函数保持生长能省 25–40% 的预训练时间，是放大路线里唯一不浪费已有算力的做法。

## 6. 比放大更划算的四件事（建议现在做）

1. **加数据、加训练量**（当前 10 tokens/param → 目标 30–50）：
   3–5B token 的中文为主语料 + 小说/对白文本，直接提升语言流畅度与角色语感。
2. **角色扮演专门配比**：ChatHaruhi / RoleBench / CoSER / 网文对白 + persona 前缀格式，
   让模型学会「按设定说话」，这是体验提升最大的一项，几乎不花额外算力。
3. **seq_len 512 → 1024**（RetNet 二次项只占 1.4%，成本很低）：
   角色设定 + 多轮历史需要更长上下文，显存用 chunkwise 或 batch 减半即可。
4. **词表 20k → 32k（可选，需重训 embedding）**：中文压缩率提升约 10–15%，
   等价于「免费」多 10% 有效上下文与吞吐；建议与放大同批做，别单独做。

## 7. 一句话决策表

| 你有多少连续 GPU 时间 | 该做什么 |
| --- | --- |
| < 12 h | 只做 SFT / 配比调整，别动架构 |
| 12–48 h | 100M 继续预训练 +2–3B token，然后角色扮演 SFT |
| 48–96 h | 100M 吃满 4–5B token（tokens/param ≈ 45），做到这个架构的上限 |
| > 96 h 且愿意等 | 用 5.2 的生长方案上 222M，再吃 4.5B token |
