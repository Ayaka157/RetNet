## 0. 结论

**本版不换分词器**（用户拍板）。下一版从零开始时走**追加式扩展**，`vocab ≤ 32767`。

---

## 1. 前提的更正：生产分词器并不病态低效

最初怀疑「分词器导致极低 token 利用率」的依据是一个**拼错的数字**。
本文作者曾写下「`lc_d8k`：7409 个字符编码成 5744 个 token，约 1.29 字符/token」，
据此推断英文被浪费约 3 倍。**这个配对是错的**：

| 我写的 | 实际是什么 |
|---|---|
| 7409 字符 | 全部 **50 条** `lc_*` 题的字符数**最大值**（`lc_d8k_03`，纯英文） |
| 5744 token | 只对 **`lc_d8k` 这 6 条**取的 token 数**最大值**（`lc_d8k_01`，中文） |
| — | 两个统计量来自**两道不同的题**，被我配成了一对 |

`[复核]` 逐条实测：

| id | 字符数 | CJK 占比 | token 数 | chars/token |
|---|---|---|---|---|
| `lc_d8k_01` | 7353 | 66% | 5744 | 1.280 |
| `lc_d8k_02` | 7260 | 63% | 5617 | 1.293 |
| **`lc_d8k_03`** | **7409** | **0%** | **2073** | **3.574** |
| `lc_d8k_04` | 7304 | 68% | 5640 | 1.295 |
| `lc_d8k_05` | 7248 | 63% | 5610 | 1.292 |
| `lc_d8k_06` | 7338 | 65% | 5540 | 1.325 |

**英文实际是 3.574 chars/token，属正常水平。** 「1.29」是中文字符数除以中文 token 数得到的假象。

该错误**未进入任何交付物**——`docs/19` 里的 `8192` / `3.574` 命中分别是 MAC 数、
批次 token 数、以及 LR 值 `3.574538e-05` 的巧合。它只存在于对话与调研任务书里。

`[调研]` 与同规模参考分词器的横向对比（bench_v3 全库）：

| 分词器 | 词表 | bench_v3 chars/token | 中文侧 | 英文侧 |
|---|---|---|---|---|
| **本项目生产分词器** | 20,000 | **1.468** | 1.302 | 3.598 |
| Qwen2.5-0.5B | 151,665 | 1.472（+0.3%） | 1.285 | 4.472 |
| DeepSeek-LLM | 100,015 | 1.433（−2.4%） | 1.253 | — |
| GPT-2 | 50,257 | 0.645 | — | — |

一个 **2 万词表的分词器与 15 万词表的 Qwen2.5 打平**。英文侧差 19.5%，是真短板，但不是 3 倍。

## 2. 真正的低效来源：语料分布错配

`[调研]` 溯源：生产分词器只能由 `legacy/prepare_chat_corpus.py` 训出
（LCCC + GLM + ShareGPT-zh + 中文维基 + **wikitext103**，按字符约 63% 英文），
而 v13/v14 训练数据是 R1 数学 CoT + I_Wonder_Why + 角色扮演。
词表指纹佐证同源：旧语料 4M 字符重训的词表与生产词表交集 **14,571 / 20,000（72.9%）**，
用 v13 分布重训则只有 53.6%。

在**留出的 1500 行真实训练流**（与对照语料零重叠）上做同条件对照：

| 对照 | chars/token | 相对生产 |
|---|---|---|
| 生产分词器（基线） | 1.6868 | — |
| **同 vocab=20000，分布内重训** | 1.9290 | **省 14.35%** |
| 同分布 vocab 32,000 | — | 省 20.79% |
| 同分布 vocab 48,000 | — | 省 25.71%（**超 int16，见 §5**） |
| Qwen2.5-151k | — | 省 10.01%（**劣于** 20k 分布内重训） |
| DeepSeek-100k | — | 省 7.49% |
| 纯中文 20k 对照 | — | **差 2.2%** |

**「中文挤压英文」被否证**：纯中文语料重训的对照反而更差，其 Latin 效率 1.469 vs 生产 2.673
——生产词表里约 **41% 的 Latin 条目是承重的**。

**推论：换更大的词表不如把语料换对。** 一个 151k 的外部词表还不如本项目自己用对分布重训的 20k。

## 3. 影响量化

`[调研]` 内容侧指标：**1.6961 chars/token、3.7967 bytes/token**。
每个 2048 token 窗口含 **1,972.6 个内容 token**（96.32%），即 **3,346 字符 / 7,489 字节**。

| 项 | 数值 |
|---|---|
| v13 单独 | 12,500 × 4 × 2048 = 102.4M 槽位 = **18.54%** 一遍 |
| v13 + v14 累计 | 512.0M 槽位 = **92.70%** 一遍（本文档多处引用的 92.6% 口径） |
| v14 单独 | **74.16%** |
| 换分词器的等价收益 | 92.70% → **106.00%** 一遍的**内容量** |

⚠️ 最后一行必须理解对：这是「**每步多吃 14% 内容**」，**不是多跑 14% 梯度步**，
也**不修任何能力问题**。v14 从 `retnet_272m_rp` 起、并非从 v13 续，这一层关系也要注意。

## 4. 长上下文的责任划分（更正先前的归因）

`[复核]` 全部 50 条 `lc_*` 中超过 2048 token 的有 **33 条**（`[调研]`：换成 Qwen 是 32 条，几乎无差别）。

| | 早前的说法 | 实测 |
|---|---|---|
| 英文 8K | 「分词器把英文材料膨胀到超窗」 | `lc_d8k_03`：7410 字符 → **2073 token = 1.01 个窗口**，只超 26 个。分词器**100% 负责**，但缺口只有约 1% |
| 中文 8K | 同上 | 2.71–2.81 个窗口；`[调研]` 即使换 Qwen（1.60 c/t）也还要 2.21–2.24 个窗口 → **主因是 2048 窗口，分词器责任 ≈ 0** |

**结论：超窗的责任归属被先前说反了。** 33/50 这个事实成立，但它不是分词器的锅；
要进窗需要约 2.81× 于生产的字符效率，现实词表达不到。

## 5. 迁移分析：不存在真正的「非破坏性」

必须分三层看，`[调研]` 每层都给了实测：

### (a) id / 权重兼容 —— **能**

保留原 19,740 条 merge 前缀、只在尾部追加新 merge。实测：
- 基座 **19,996 / 19,996** 个非 special 条目全部仍可达，**0 条 merge 失效**
- **追加式永不使文本变长**：1500 行 × 5 个变体，变长条数 **= 0**
  （可证明：追加的 merge rank 最低，基座行为逐符号不变）

### (b) 分布不变 —— **不能**

同一段文本在新分词器下产生不同的 token 边界，已有表示必然漂移。实测边界一致率：

| 方案 | 边界一致率 |
|---|---|
| 追加 500 条 merge | 92.61% |
| 追加 8000 条 merge | 78.13% |
| 全量重训，同 20k | 69.98% |
| 换 Qwen | 70.68% |

### (c) 套用 GrowthLayerNorm —— **搬不过来**

GrowthLayerNorm 靠「**输入序列不变** + 新增维初值恒零」实现 `f_new ≡ f_old`。
换分词器改的**就是输入序列本身**：序列长度、`γ^(n−m)` 的相对距离、
逐位置非线性作用的次数全都变了。**没有任何 embedding 初始化能恢复旧激活。**
唯一严格函数保持的词表改动是「加入现有文本产不出的 token」，而那不带来任何效率。

### 反直觉但有价值的发现

| 方案 | 效率收益 | 边界漂移 |
|---|---|---|
| **追加式到 vocab 29,278** | **省 15.93%** | 76.70% |
| 同 vocab 全量重训 | 省 14.35% | 69.98% |

**追加式又省又稳**——因为追加永远不动已有 merge。这使「追加式 + 不重置优化器」成为合理路线。

### 最小损伤档

| 方案 | vocab | 省 | 漂移 |
|---|---|---|---|
| `app_top2000` | 21,822 | 8.32% | 13.22% |
| `app_top8000` | 27,597 | 14.78% | 21.87% |

两者老 id 语义均不变，**不必重置优化器**。

### 硬约束

`train.ids.npy` / `val.ids.npy` 是 **int16**（`retnet/packing.py:206-209`）→ **id 上限 32767**。
48,000 / 53,651 的候选在**当前存储下不可用**，除非改 int32
（`train.ids` 1.10 GB → 2.21 GB）。

重编码代价几乎免费：`[调研]` 实测 7.10 M 字符/s（生产）/ 4.74 M 字符/s（追加版），
552.33M 槽位纯编码 **2.2–3.8 分钟**。

## 6. 更正：embed_scale 与新增行的初始化

本文作者先前给调研的提示是「`embed_scale = √768` 而 `d_model = 1024`，
所以新行不能用 `N(0, 1/d)` 初始化，差 0.866 倍」。
**调研不同意这个理由，同意结论，且其证据更好：**

- `[调研]` 实测 v13 `embedding.weight [20000, 1024]` 全局 std = **0.035880**，
  而 `N(0, 1/d)` 的 std = 0.03125 —— **只差 14.8%**，不是 0.866 倍。
- `embed_scale` 是前向里的**全局标量**，做「新行量级匹配已有行」时自动约掉。

**真正该注意的是行范数强烈依赖 token 出现频率**：

| token 频次 | 行范数 | std |
|---|---|---|
| > 100k 次 | 0.47 | 0.016 |
| 从未出现 | 3.89 | 0.072 |

**差 8.3 倍**，而 `tie_weights=true` 时范数 8 倍的行直接产生 8 倍 logit。
所以初始化应按**频率档**取，不能用单一 σ。另实测：「组成片段取均值」偏小 15%、
「求和」偏大 65%。

## 7. 下一版的可执行方案

1. 语料先换对分布（这是 14.35% 里的主要来源），再考虑扩词表。
2. 词表扩展走**追加式**（保留原 merge 前缀），目标 `vocab ≤ 32767`。
3. 若必须要 > 32767，则先改 `packing.py` 的存储 dtype 到 int32 并重编码（2–4 分钟）。
4. **不要**假定 GrowthLayerNorm 那套能迁移；换分词器就是分布迁移，需要重训（非从零，但也不是续训同一损失面）。
5. 是否重启 cosine：本次未测，**存疑**。

## 8. 存疑 / 未核实（逐条抄录调研的自我声明）

- `[存疑]` v14 实际进度无法在本机核实（本机只有 `checkpoint-10000`）。
  → **本文档已代为解决**：笔记本 `checkpoint-15000/trainer_state.json` 显示
  `global_step = 15000`、`max_steps = 50000`；日志末行 `17008/50000 [1:37:54<7:11:26, 1.27it/s]`。
  按绝对目标算剩余 `(50000−15099)/1.21 = 8.01 h`，与显示的 7.99 h 吻合；
  按「再跑 50000 步」算应是 11.48 h。**故 `max_steps` 是绝对目标，74.16% 那个口径正确。**
- `[存疑]` 生产分词器语料：仓库只有 `legacy/prepare_chat_corpus.py` 一处能训出它，
  词表交集 72.9% 佐证同源，但 `data_cache/chat_mix_v20k/` 已不在，**无法做文件级终局验证**。
- `[存疑]` `orig_4M` 的「英文 63%」来自每源 400 条探针 × 原抽样条数的**推算**，
  数量级可信、小数点不可信。
- `[存疑]` `a_grade` 前 1500 条测试集与对照语料理论重叠约 0.45% 文档
  （最多让对照优势高估约 0.5pp）；bench 侧零重叠。
- `[存疑]` append 方案的收益**只测了 token 效率**，没测它在 loss / 基准上折成多少。
- `[存疑]` 调研过程中曾误以为「从 `.npy` 解码回文本」丢 13% token，
  实为拿两个不同语料在比；两个独立解码样本 1.6545 vs 1.6868（差 1.9%），
  真实损失只有丢掉的 `<eos>`：7.82 个/行 = 窗口的 0.38%。该自我更正已记入报告。
