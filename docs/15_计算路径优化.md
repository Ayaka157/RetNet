## 0.1 硬件上限：我们离它还有多远

`scripts/bench_peak.py` 在**本项目真实形状**上实测：

| 用途 | 形状 MxNxK | 可达 TFLOPs |
| --- | --- | --- |
| q/k 投影 | 8192x1024x1024 | 37.0 |
| v/g 投影 | 8192x2048x1024 | 40.8 |
| out_proj | 8192x1024x2048 | 40.4 |
| FFN 上/下 | 8192x2048x1024 | 41.2 / 39.9 |
| LM head | 8192x20000x1024 | 43.3 |

即 **可达峰值约 40 TFLOPs**（大方针 8192³ 能到 44.8）。
每步纯 GEMM 工作量 10.28 TFLOP → **理论下限约 257 ms**。

- 配置 B（929 ms）里 GEMM 占 496 ms = **52% 效率**
- 显存带宽实测 **217 GB/s**；一步约 11 GB 搬运只值 ~50 ms，**不是带宽瓶颈**

### 0.2 这一步是 GPU 受限还是发射受限（决定还有没有空间）

`scripts/diag_gpu_busy.py` 把**同一次运行**里的墙钟、GPU 累计忙时、内核启动数放在一起：

| 配置 | 墙钟 | GPU 忙时 | GPU 空闲 | 内核启动数 |
| --- | --- | --- | --- | --- |
| B（batch 4 + 检查点） | 1,364.7 ms | 1,304.0 ms | **4.4%** | 3,427 |
| C（batch 1 × accum 4） | 1,156.6 ms | 916.5 ms | **20.8%** | **10,116** |

（电池供电下测；比值可信，绝对值偏低。）

**B 已经 GPU 饱和（95.6%）**，没有空间。**C 有 20.8% 的 GPU 空闲、内核数是 B 的 3 倍** ——
这是 batch 1 四个微步的代价，也正是 C 里任何「摘掉几个内核」的微优化都测出 **0%** 的原因：
有富余，摘掉不改变墙钟。

理论上对付发射受限的手段是 CUDA Graphs，但它在**梯度累积**下不可用，见 §6。

### 0.3 算术强度：为什么「少搬多算」只对一半的时间有效

一个自然的追问是：**既然带宽是硬伤，能不能提高单次传输的计算量、变相减少传输次数？**
答案是**能，但它只作用于 GEMM 那一半**。把每一部分的算术强度（FLOP/byte）算出来就清楚了。
这块卡的脊点（ridge point）= 峰值算力 ÷ 带宽 = **40 TFLOPs ÷ 217 GB/s ≈ 184 FLOP/byte**。

| 部分 | 占步时 | 算术强度 | 相对脊点 | 提高 batch 有用吗 |
| --- | --- | --- | --- | --- |
| GEMM（投影/FFN/LM head） | ~49% | `2MKN / (2KN)` = **M** = batch×seq = 2048~8192 | **远高于**脊点 | ✅ 有用（B 的 95.6% 占用 vs C 的 79.2%） |
| 逐元素/归一化/损失 | ~51% | ≈ 0.5~2 FLOP/byte | **远低于**脊点 | ❌ **没用** |

**为什么对逐元素没用**：它的 bytes 与 FLOPs 都随 batch 线性增长，比值是 **batch 无关的**。
要让这部分的强度上去，唯一办法是**融合**——一次载入做更多运算——而这正是 inductor
已经在做的事（本文 §6 里那几次「摘掉融合核却 0% 收益」的负结果，从反面印证了
它已经把可融的都融了）。

**GEMM 那半为什么「提高 batch」有效，却不是靠带宽**：M=2048 时强度已达 2048 ≫ 184，
**GEMM 本来就不是带宽受限的**。batch 1 慢是因为 M 太小、切分后填不满 SM 的占用率
（实测 batch1 的形状峰值 11~21 TFLOPs，batch4 是 17~29）。所以它是**占用率/切分问题**，
不是带宽问题。

**结论**：这条思路能榨出的东西，在**物理 batch**上；而物理 batch 卡在 **8 GB 显存墙**上。
本文第 3、4 轮从四个方向撞这堵墙（8-bit Adam 腾 1.63 GiB、融合 CE 腾 0.45 GiB、
分层检查点、关梯度检查点），**没有任何一个组合能让 batch 2 在不颠簸的前提下装下**。

**结论：没有到硬件上限，但从「换更快的实现」这条路上能榨出的已经不多**——
51% 的时间是 Triton 逐元素/归约核，实测就在 DRAM 带宽上；**手写 CUDA 打不赢总线**。
自研 kernel 唯一能赢的地方是**减少搬运遍数**（更激进的融合），见 §6。


## 1. 先定位瓶颈：不是算力，是发射次数

基线 profile（`--profile`，一步的前向+反向 CUDA 时间 2,157 ms）：

| 算子 | CUDA 时间 | 占比 | 调用次数 |
| --- | --- | --- | --- |
| `aten::add_` | 545 ms | 25.3% | 6,362 |
| elementwise kernel | 481 ms | 22.3% | 5,160 |
| `aten::linear` | 477 ms | 22.1% | 562 |
| `aten::mm` | 409 ms | 19.0% | 563 |
| `aten::copy_` | 393 ms | 18.2% | **22,751** |
| `NativeDropoutBackward0` | 370 ms | 17.2% | 41 |
| `aten::matmul` | 338 ms | 15.7% | **9,241** |
| `aten::to` / `_to_copy` | 241 ms | 11.2% | **11,406** |
| `SliceBackward0` | 681 ms | 31.6% | **2,082** |

**纯 GEMM（`mm` + `bmm`）只占 528 / 1,514 ms = 35%。** 实测 5.6 TFLOPs，按 6N 规则
只发挥出 GPU 的一小部分。瓶颈是**内核发射次数与显存带宽**，不是算力。

`SliceBackward0` 那 2,082 次调用全部来自逐 chunk 循环里的 `q[:, :, sl]` 三件套切片。

> ⚠️ **profiler 的算子归因会误导。** 它把 `NativeDropoutBackward0` 记成 25%，
> 但把 dropout 从 0.1 改成 0.0 实测只省 **3.9%**（1,640 → 1,574 ms）。
> **一切以墙钟为准。**

## 2. 优化一：批量 chunkwise（数学等价）

`retnet_hf/retention_fast.py`，由环境变量 `RETNET_FAST_CHUNKWISE=1` 启用。
原实现每个 chunk 做 4 次小 matmul，seq 2048 / chunk 64 = 32 个 chunk
→ **每层每步 128 次矩阵乘，全模型 9,241 次**。

改成三个跨 chunk 的批量矩阵乘 + 一次极小的状态扫描：

```text
原：for i in range(nc):                      新：1. U = k_r^T (v_r * value_decay)      一次批量
        inner = (q_i k_i^T * mask) v_i           2. S_prev = scan(U, chunk_decay)    只在小张量上循环
        cross = (q_i * cd) S_i                   3. inner = (q_r k_r^T * mask) v_r   一次批量
        S = cd * S + k_i^T (v_i * vd)            4. cross = (q_r * cd) S_prev        一次批量
```

`matmul` 调用 **9,241 → 441**，`copy_` **22,751 → 3,031**，`SliceBackward` **2,082 → 0**。

### 2.1 踩到的坑：因式分解会导致 NaN

第一版用 `γ^i · γ^-j` 做块内衰减掩码，理由是「块内指数 ≤ C-1，不会爆」。
**这个理由是错的。** `retnet_272m_rp` 的 GLA 门控最小值是 **0.668**（不是固定公式的 0.969），
`0.668^-255 = 1e44` **超出 fp32 上限 3.4e38** → Inf → 前向 NaN。

`torch.where` 只丢弃结果，**不会阻止 Inf 被算出来**。

正确写法是**对数空间**：

```python
log_gamma = torch.log(gamma)                       # [H]
inner_mask = torch.exp(log_gamma[:, None, None] * delta.clamp_min(0))
inner_mask = torch.where(causal, inner_mask, 0.0)
```

`exp(log γ · delta)` 在两个方向上都正确饱和：γ<1 时下溢到 0（本就可忽略的贡献），
γ>1 时给出有限值。参考实现的 `γ ** delta` 恰好安全（只下溢不溢出），但换不成批量形式。

**症状是 `loss = nan`，eager 和 compiled 都一样** —— 它出在实现里，不在编译器里。

### 2.2 另一个坑：`torch.empty` + 切片赋值

状态扫描原本写进 `torch.empty` 的缓冲区。改用 list + `torch.stack`：
`CopySlices` 梯度路径更干净，也不必担心未初始化内存进反向。

### 2.3 等价性验证

`tests/test_fast_chunkwise.py`，三种 gamma × 五种 chunk：

| gamma 范围 | 单元级（fp32） | 模型级（bf16 autocast） |
| --- | --- | --- |
| 默认初值 0.9688–1.0000 | `rel_mean` ~2e-6 | logits **逐位相同** |
| **真实门控 0.6680–1.0117** | `rel_mean` ~7e-7 | 同上 |
| 极端 0.30–1.02 | `rel_mean` ~5e-7 | 同上 |

state 在全部组合下 **逐位相同**（`max|d| = 0`）。

> ⚠️ **测试必须覆盖真实门控范围。** 只用默认初值（都接近 1）时，
> §2.1 那个溢出 bug **完全测不出来**——这是它一开始溜过去的原因。

## 3. 优化二：关掉梯度检查点（必须先腾出显存）

**梯度检查点让每步多跑一整遍前向**——前向 1 遍 + 重算 1 遍 + 反向 1 遍 = 3 遍，
而不检查点是 2 遍。**整整 1/3 的步时是重算出来的。**

直接关掉会 OOM：batch 4 在 seq 2048 下激活值要 **14.5 GiB**（实测），8GB 卡装不下。
于是把「等效 batch」和「物理 batch」解耦：

```text
batch 1 × grad_accum 4   →  等效 batch 4，但激活值只需 1/4
+ adamw_bnb_8bit         →  优化器状态 2.18 GiB → 0.55 GiB，腾出 1.63 GiB
+ 关掉梯度检查点          →  省掉那 1/3
```

### 3.1 中途踩到的坑：内存颠簸会伪装成「算法变慢」

第一次尝试（还没有 8-bit Adam）得到的是这个：

| 配置 | 微步时 | 每优化步（8,192 token） |
| --- | --- | --- |
| batch1 accum4 **+ 检查点** | 234 ms | 936 ms（≈ 现状 929 ms，**零收益**） |
| batch1 accum4 **无检查点** | **1,437 ms** | 5,748 ms（**灾难**） |
| batch1 accum1 无检查点（孤立） | 169 ms | — |
| batch2 accum2 + 检查点 | 462 ms | 924 ms（零收益） |

**梯度累积本身完全正常**（234 ms，只比 219 ms 基准高 7%）——
灾难只出现在「无检查点 **且** 累积」这个组合。

原因：无检查点时激活值要常驻约 2.5 GiB，加上 fp32 参数/梯度 2.18 + fp32 AdamW 2.18 = 6.9 GiB，
已经贴到 8 GiB 边缘，驱动开始往系统内存溢出。**换 8-bit Adam 腾出 1.63 GiB 后，
同样的配置从 1,437 ms 直接掉到 183 ms** —— 8 倍差距，全部来自显存。

> 这个坑很值得记：**如果不查显存只调算法，会得出「关检查点更慢」的错误结论。**

装上 8-bit Adam 之后又量了一次，确认**内存墙就在 batch 1 与 batch 2 之间**：
batch 1 用 183 ms/微步，batch 2 直接掉到 **11,077 ms/微步（慢 60 倍）**，
即使 8-bit Adam 已经省下 1.63 GiB、即使开了 `expandable_segments:True`。
所以「关掉检查点」这条路**只能配 batch 1 + 梯度累积**，没有别的组合。

### 3.2 顺带查出的一个静默正确性 bug

`RetNetForCausalLM.forward` 签名末尾的 `**_kwargs` 会让 HF 的启发式判定
`accepts_loss_kwargs = True`，于是 `Trainer.training_step` **跳过**
`loss = loss / gradient_accumulation_steps`：

```python
not self.model_accepts_loss_kwargs or num_items_in_batch is None
# If the model does not accept loss kwargs, we need to normalize the loss ...
loss = loss / self.current_gradient_accumulation_steps
```

而本模型的 loss 是按权重码 `w.sum()` 自归一化的，**并不使用 `num_items_in_batch`**。
后果：梯度被放大 accum 倍，**等效学习率成倍上升**——静默、且只在 `accum > 1` 时发作。

实测症状是 loss 从 3.19 变成 **12.75 ≈ 3.19 × 4**。修正只需在模型类上声明：

```python
accepts_loss_kwargs = False     # 注意属性名没有 model_ 前缀；HF 找不到就会去猜签名
```

修正后 loss 立刻回到 3.1851 → 3.0148，与 batch 4 的 3.20 → 3.17 一致。

> 项目至今所有任务都是 `accum = 1`，所以这个雷一直没踩到。**一旦要用累积就必须先修。**

### 3.3 等价性

关掉检查点不改变数学——它只是不重算。实测两条 loss 轨迹：

| | 首 | 末 |
| --- | --- | --- |
| batch 1 + 检查点 | 3.3649 | 3.1860 |
| batch 1 无检查点 | 3.3649 | **3.1861** |

差在最后一位。`accum` 与真实 batch 4 的梯度则**不完全逐位相同**（微批平均 vs 整体平均），
但都是同一个期望的无偏估计——这是配方变更，不是数值等价，需知悉。

## 4. 优化三：让 `torch.compile` 真正生效（两个 bug）

`torch.compile(backend="inductor")` 在这个项目里一直**完全无效**。实测 0.0%，
在 Trainer 路径里甚至**慢 1.8x**。两个独立的原因，缺一不可。

### 3.1 Bug A：没有 Triton

```text
TritonMissing: Cannot find a working triton installation.
```

笔记本的 conda 环境没有 Triton。而 `retnet_hf/train.py` 的 `try/except` **接不住它**——
inductor 是**惰性**编译，错误要到第一次前向才抛，那时早已离开 `try` 块。
所以它不崩、不提速、静默地什么都不做。

```powershell
pip install triton-windows      # 笔记本：3.8.0 (cp311, win_amd64)
```

现在 `train.py` 会**先显式 `import triton` 并响亮失败**，不再静默。

### 3.2 Bug B：编译后的模型从未被调用（这是关键）

修好 Triton 后，`bench_step.py`（直接调模型）测出 **1.65x 提速**，
但真实训练**反而慢了 1.8x**。用 `scripts/bench_trainer.py` 复刻 Trainer 路径后拿到决定性证据：

```text
tr.model 包装链: OptimizedModule -> RetNetForCausalLM   ← 看起来对
dynamo counters: {}  ← 什么都没编译！
```

**原因**：`Trainer.__init__` 把**原始**模型存进了 `self.model_wrapped`，
而 `train()` 取的是 `self._wrap_model(self.model_wrapped)`。
`train.py` 只替换了 `trainer.model`，**编译后的模型永远不会被调用**。

修正：两处一起换。

```python
compiled = torch.compile(trainer.model, backend="inductor")
trainer.model = compiled
if getattr(trainer, "model_wrapped", None) is not None:
    trainer.model_wrapped = compiled
```

修正后 `dynamo counters: {'frames': {'total': 1, 'ok': 1}, 'unique_graphs': 1}`
—— **一整张图被完整捕获**，稳态 **928 ms/步**。

> 这个 bug 特别隐蔽：日志会印出 `torch.compile(inductor) applied`，
> 配置看起来生效了，速度却毫无变化（甚至更慢）。**只有查 dynamo counters 才能识破。**

### 3.3 数值验证

`scripts/diag_compile_numerics.py`：

| | eager | compiled |
| --- | --- | --- |
| batch0 loss | 2.592331 | 2.592230 |
| batch1 loss | 2.488926 | 2.488853 |
| batch2 loss | 2.571849 | 2.571787 |

8 步训练中 loss 差 ~0.4%、grad_norm 差 ~3%，**全程无发散**。

### 3.4 一个测量陷阱

`bench_step.py` 最初调的是 `model._forward_hidden(...)`，
而 `torch.compile` 只包装 `forward`——**私有方法绕过了 `OptimizedModule.__call__`**，
于是两次测的都是 eager，得出「compile 无效」的错误结论。
现已改为走公开 `forward`，并在代码里留了注释。

## 5. 推理路径审计（结论：单序列无解，杠杆在批处理）

`scripts/bench_decode_opt.py`，272M，prompt 11 token，生成 64 token：

| 方法 | tok/s | 加速 |
| --- | --- | --- |
| 参考 `generate`（单序列） | 73.0 | 1.00x |
| `torch.compile` | 74.5 | 1.02x |
| `mode="reduce-overhead"`（CUDA Graphs） | 72.8 | **1.00x** |
| bf16 权重（读取量减半） | 69.7 | 0.95x |
| **批处理 B=8** | 336（总） | **每序列等效 4.6x** |
| **批处理 B=16** | 435（总） | **每序列等效 6.0x** |

**单序列解码的三条路全部无效**，包括 CUDA Graphs。这否定了「瓶颈是内核发射」的假设：
若是发射受限，CUDA Graphs 应当大幅提速。真实原因是**每个权重只被用一次的 GEMV**，
本身就跑不满带宽（1.09 GB / 256 GB/s = 4.3 ms 理论下限，实测 12.5 ms）。

**bf16 权重也无效（0.95x）**，说明连带宽都不是限制——单序列 GEMV 的固有低效率。

**杠杆是批处理**，而它已经由 `bench/fastgen.py` 的 `BatchedDecoder` 实现
（独立序列共享一次前向，逐序列逐位一致）。交互式 `play.py` 天然单序列，无法受益。

> `bench/fastgen.py` 的注释说「Python 开销只占 3%」，这与本节一致：
> 删 Python 拿不到东西，批处理才行。

## 9. 第八轮（2026-10-10 晚）：内核级重定位 —— 以及 §0/§6 里两条被推翻的结论

### 9.0 方法上的错误：§0.2 的「20.8% GPU 空闲」是在**电池**下测的

§0.2 用「GPU 忙时 / 墙钟」判定 C 有 20.8% 空闲，据此推断「摘内核不会有用」。
在 AC 供电下用 `scripts/profile_kernels.py`（chrome trace → 按 **CUDA 内核**聚合，
而不是 §1 警告过的算子归因）重测：

| | GPU 忙时 | 墙钟 | 占用 |
| --- | --- | --- | --- |
| 配置 C（AC） | 156 ms/微步 | 166 ms/微步 | **94%** |

**AC 下 C 基本吃满 GPU，没有 20.8% 的空闲。** §0.2 的推断前提不成立，
「摘内核没用」这个结论当时是靠错误前提得出的。

### 9.1 真正的账：瓶颈是**内核发射次数**，不是算力也不是带宽

| 算子 | 每层耗时 | × 20 层 | 占微步 |
| --- | --- | --- | --- |
| `_decay_tables` | **410 µs** | 8.2 ms | 4.7% |
| 状态扫描（nc=32 串行 + stack） | **1127 µs** | 22.6 ms | **13.0%** |

两者合计只处理约 70 万元素。410 µs 花在 26 万元素上是不可能的计算量 ——
**成本全是发射延迟**：`_decay_tables` 约有 22 个相互依赖的小内核，扫描是
32×3+1 = 97 个，Windows 上每次发射约 18 µs。

### 9.2 结果（RTX 3070，真实 Trainer 路径，配置 C）

| | 优化步时 | 微步 | reserved |
| --- | --- | --- | --- |
| 改动前 | **695 ms** | 174 ms | 6.57 GiB |
| 改动后 | **662–663 ms** | 166 ms | 6.57 GiB |
| 变化 | **−4.6%** | | 不变 |

复测三次：657 / 662 / 663 ms。内核级佐证：Triton 归约类忙时 **47 → 20 ms**，
那个 469 µs 的 `triton_red_fused__to_copy_add_exp_log_mul_select_sum_view_zeros`
已从 Top-18 消失。

两处改动：
1. `_decay_tables` 缓存索引张量、并用同一个 `γ^j` 表派生 cross/value/chunk
   （3 次 `exp` → 1 次）。
2. 状态扫描改**闭式**批量矩阵乘。原写法是 nc 次串行 `s = decay*s + U[i]`
   加一次 `torch.stack`；因为 `decay = chunk_decay` 在循环里是**常量**，有
   `S_prev[i] = d^i·state + Σ_{j<i} d^(i-1-j)·U_j`，一次
   `[H,nc+1,nc] @ [B,H,nc,kd*vd]` 就能算完，多出来的第 nc 行正好是 `new_state`。
   **所有指数非负，不存在 §2.1 那种 `γ^-j` 溢出。**
   实测 eager：**1127 → 190 µs/层**。

### 9.3 ⚠️ `config.chunk_size` 一直是**死字段** —— §0 与 §6 的 chunk 结论全部作废

`RetNetForCausalLM.forward` 的签名里 `chunk_size=64` 是**函数默认值**，
而 HF Trainer 调模型时不会传这个关键字；`forward` 会 `getattr(self.config,"mode",…)`
读 mode，却**从不读 `self.config.chunk_size`**。实测：

```text
config.chunk_size = 64   -> loss 2.69759822
config.chunk_size = 128  -> loss 2.69759822     # 逐位相同 = 配置被忽略
config.chunk_size = 256  -> loss 2.69759822
显式传参 chunk_size=128  -> loss 2.69759798     # 参数本身是有效的
```

**所以本项目一直跑在 chunk 64，而任务 JSON、日志、文档全写 128。**
`bench_step.py` 的 `--sweep chunk_size=32,64,128,256` 扫的是空变量，
§6 里「chunk 512/1024 ❌ 反而更慢；最优是 128」**不成立**，§0 表格里的
「chunk 128」应读作 64。

已把 `forward` 改成 `chunk_size=None` 再回落到 config。补齐后**第一次有效的
chunk 扫描**（本机 3070，真实 Trainer 路径）：

| chunk | 优化步时 | reserved |
| --- | --- | --- |
| 64 | 663 ms | 6.73 GiB |
| 128 | 662 ms | 6.61 GiB |
| 256 | 685 ms | 6.90 GiB |

**64 与 128 打平，256 慢 3.5%。chunk 不是性能杠杆，这是管道正确性问题。**
（三次的 loss 首值 3.1866 / 3.1868 / 3.1867 不同，反证配置现在真的生效了。）

> ⚠️ **不要对正在跑的任务热切这个修复。** v14 的配置写 128 但实际跑 64；
> 修好之后它会变成 128，数值当场跳变。只能在**新开一轮**时使用。

### 9.4 本轮负结果

| 手段 | 结果 |
| --- | --- |
| `torch.compile(mode="max-autotune-no-cudagraphs")` | ❌ **0%**（662 vs 662 ms）。GEMM 走的是外部 cuBLAS，autotune 主要作用于 Triton matmul 模板，这个模型用不上 |
| `_head_group_norm` 改成「先归一化、最后 permute」 | ❌ **慢 9.2%**（190 vs 174 ms/微步）。参考实现把 permute 放在归一化**之前**，那次拷贝被随后的逐元素归一化吸收；挪到**之后**就直接喂给 `out_proj` 这个外部 cuBLAS 调用，再也融不进去。测试留在 `tests/test_head_group_norm.py` |

### 9.5 修掉一个坏掉的护栏：`tests/test_fast_chunkwise.py`

`modeling_retnet._chunkwise_retention` 在 `RETNET_FAST_CHUNKWISE=1` 时**直接转发给
`chunkwise_batched`**，而训练环境一直开着这个变量。于是测试里的「参考实现」就是
被测函数本身，**永远报逐位相同**。§2.3 那张「全部组合 state 逐位相同」的表
因此从未被真正验证过。

修法：加 `reference_path` 上下文管理器强制按下模块开关；判据从**绝对**阈值改成
**相对**量（γ>1 的头会把 state 放大到 1e13，绝对阈值 1e-4 毫无意义）。

修好后的真实结论（15 个组合全部通过）：

| gamma | out rel_mean | out rel_max | state rel_max |
| --- | --- | --- | --- |
| 默认初值 0.9688–1.0000 | ~1.4e-6 | 2.5e-7 ~ 6.8e-7 | 2.4e-7 ~ 7.0e-7 |
| 真实门控 0.6680–1.0117 | ~8.1e-7 | 9.0e-7 ~ 2.3e-6 | 5.1e-7 ~ 2.1e-6 |
| 极端 0.30–1.02 | ~6.2e-7 | 3.1e-7 ~ 3.6e-6 | 9.3e-7 ~ 2.7e-6 |

**即：快速 chunkwise 路径从来不是逐位等价，而是相对误差 1e-6 量级的近似**
（改动前后同量级，闭式扫描没有让它变差）。相对误差来自 fp32 累加顺序。

### 9.6 eval 边界的开销（与计算路径无关，但占 10% 的墙钟）

v14 实测：step 2500 是 33:40，step 2516 是 38:32 —— 16 步花了 292 s，
正常应为 13 s。**每个 eval 边界约 280 s**，其中约 200 s 是 eval 本身
（833 条 val 样本，`eval_runtime ≈ 201 s`），其余是保存 + 编译。

`eval_steps=2500`、共 50000 步 → **20 次边界 ≈ 67 分钟，占约 11 小时运行的 10%**。
`retnet_hf/train.py:101` 的 `per_device_eval_batch_size = batch_size * 4` 让 eval
形状与训练不同，必然重新编译一次（可复用，只付第一次）。

**结论：想省这 10%，调 `eval_steps` 或 `--eval_batches`，但那是评测粒度的取舍，
不是计算路径问题。**

## 10. 第九轮：GEMM 到底离硬件上限有多远（用编译图自报的形状算）

### 10.1 §0.1 / §0.3 引用的「batch1 形状峰值 11~21 TFLOPs」是错的

`scripts/bench_peak.py` 在本机 3070 上重测本项目**真实形状**：

| 形状 MxNxK | batch 4 | **batch 1（配置 C 实际用的）** |
| --- | --- | --- |
| 2048/8192 x 1024 x 1024 | 34.1 | **25.9** |
| x 2048 x 1024 | 36.0 | **31.8** |
| x 1024 x 2048 | 38.7 | **32.3** |
| LM head 20000 | 41.1 | **41.6** |

**batch 1 的形状峰值是 26~42 TFLOPs，不是 11~21。** batch1/batch4 的比是 0.84，
不是 0.55 —— §0.3 那句「batch 1 慢是因为占用率填不满 SM」的**幅度被夸大了**。
拿 42 TFLOPs（batch4 大方针）去当 batch1 的上限，会得出「只跑到 60%、还有 40% 空间」
的错误结论。

> `bench_peak.py` 有两处 bug 已修：`total()` 把 q/k 与 v/g 各漏乘一次（前向总量
> 偏低约 30%），以及第 117 行单位没除 1e12（打出 2.5e14 ms 这种数）。

### 10.2 精确下限：`scripts/gemm_ceiling.py`

不靠估算 —— 形状清单直接来自编译图的 dynamo counter **`aten_mm_info`**，
那是 torch.compile 捕获到的那张图**实际发出**的 aten::mm / aten::bmm 调用
（计数与 LM head 的 fwd+bwd 三条各为 1 完全自洽，所以那就是**一个微步**）。
每个形状的可达峰值现场测，且**不在调用之间 synchronize**（第一版就是栽在这里：
chunkwise 的批量乘单次只有 0.1 ms，被 sync 固定开销淹掉，实测被低估 3~10 倍）。

| 类型 | 形状 | 次数 | TFLOPs | 小计 ms |
| --- | --- | --- | --- | --- |
| mm | 2048x1024x2048 | 160 | 26.5 | 51.9 |
| mm | 2048x2048x1024 | 100 | 33.4 | 25.7 |
| mm | 2048x1024x1024 | 80 | 31.6 | 10.9 |
| mm | 1024x2048x2048 | 40 | 37.1 | 9.3 |
| mm | 1024x1024x2048 | 40 | 33.9 | 5.1 |
| mm | 2048x20000x1024 等三条 LM head | 1 each | 40~42 | 6.1 |
| bmm | 512x64x128x64 | 120 | **6.7** | 9.7 |
| bmm | 512x64x64x64 | 60 | **6.8** | 2.4 |
| bmm | 512x64x64x128 | 60 | **8.8** | 3.7 |

（bmm 的 batch=512 = B·H·nc = 1×16×32，正是 chunk=64 的 chunkwise 批量乘，
矩阵只有 64×64 / 64×128，所以只有 6.7~8.8 TFLOPs。）

**一个微步 GEMM 总量 3.457 TFLOP → 按实测形状峰值算的下限 124.6 ms/微步。**

### 10.3 结论：GEMM 这一半没有空间了

| | ms/微步 |
| --- | --- |
| 按实测形状峰值的下限 | **124.6** |
| profiler 实测 GEMM 忙时 | **104.0** |
| 比值 | **0.83x** |

**实测比孤立下限还低。** 也就是说，按逐形状孤立测量的口径，GEMM 已经跑在
「125% 的上限」——这个矛盾只有一个解释：孤立测量偏保守（真实图里张量常驻、
cuBLAS 选到更好的切分），或 profiler 把一部分 matmul 内核归到了 Triton 桶里。
**两种解释都指向同一结论：GEMM 没有可榨的余量。**

等价说法：实际跑到 **33.2 TFLOPs**（3.457 TFLOP / 104 ms），而加权形状峰值是
**27.7 TFLOPs**（3.457 / 124.6 ms）。**已经在这批形状的天花板之上。**

### 10.4 剩下的是什么

微步墙钟 166 ms 里：GEMM 104 ms（62.7%），**非 GEMM 62 ms（37.3%）**。
后者是约 3,500 个 Triton 逐元素/归约内核，实测平均 34 µs/个、约 350 GB/s ——
**贴着 DRAM 带宽跑**（本机实测拷贝带宽 359~396 GB/s）。这部分如 §0.3 所说，
算术强度 0.5~2、与 batch 无关，**只能靠融合，而 inductor 已经把可融的都融了**
（§6 那些「摘掉融合核却 0%」的负结果从反面印证）。

唯一还能下手的形态是**「一串相互依赖的小内核」**——不是单个融合核，
而是一条链上的发射延迟。本轮的 `_decay_tables`（22 个）与状态扫描（97 个）
就属于这一类，两处合计拿回了 4.6%。§6 里那些失败案例针对的是**单个**融合核，
两者不矛盾。

已排查的剩余项：

| 项 | 量级 | 状态 |
| --- | --- | --- |
| `aten::add_` 残差（`[2048,1024]` fp32，每微步 40 次） | 2.5 ms/微步（1.6%） | 实测 63 µs/次 = 25 MB ÷ 395 GB/s，**纯带宽受限**，无空间。唯一可疑处是它跑在 fp32——但收益上限 1.6% |
| `vectorized_elementwise_kernel<add<float>>` 732 次（3.6%） | 17.1 ms / 3 微步 | 未定位到发起者；量级上限 3.6% |
| `torch.compile(mode="max-autotune-no-cudagraphs")` | — | ❌ 0%（662 vs 662 ms）。GEMM 走外部 cuBLAS，autotune 只作用于 Triton matmul 模板 |
