## 1. 为什么再改一次

`docs/13` §3 给 v2 判了死刑：**143 项里 70 项（49%）区分度 < 0.05**。
一半的算力花在了「所有模型都过」或「所有模型都不过」的题上。
`docs/13` §5.1 与 `docs/04` §1 列了六条必做：

1. 每类 ≥10 项；2. 难的角色扮演探针（长设定 >300 字、设定冲突、诱导出戏、口癖保持）；
3. 多轮加深到 4–6 轮；4. 长上下文项；5. T=0 贪婪基线；6. think 泄漏作为一等指标。

v3 逐条落实，并且额外解决了一个 v2 没意识到的问题：**判据本身不可审计**。
v2 的判分函数和题面写在同一个文件里，143 项要读 646 行代码才能核对一条判据。
v3 把两者拆开——**题目是数据，判据是声明**。

### 2.1 为什么判据要写成 DSL

一条 `chk` 就是一串分号分隔的谓词，全部满足才得分：

```text
chk = "any:令狐冲,独孤九剑,华山;none:我是一个AI,语言模型;dedup:0.65,4,40;not_think"
```

好处有三个，都是实打实的：

1. **可批量校验**。编译器能在构建期就发现拼错的谓词名、恒真的正则、不可能达到的长度上限。
   实测抓到了 `re:range(1, 6),range(1,6)` 这类「看着对、实际切成两个碎片」的判据。
2. **出题人不必会写 Python**。本版的 630 项人工题由子代理按契约产出 JSONL，
   不需要它们写（或审）任何判据代码。
3. **题目和判据可以分别审计**。`anchors`（锚点在题面里白送分）、`lint`（弱判据）、
   `quota`（难度配额）三份报告是对**数据**做的，不是对代码做的。

### 2.2 元数与转义：两个踩过的坑

**坑一：逗号既是分隔符又是正则的一部分。**
`any:A,B` 里逗号表示「或」；`dedup:0.65,4,40` 里逗号是参数分隔。
实现上按**谓词元数**分流：多值谓词（`any` `all` `re` `num` …）按逗号切成 OR 候选；
单值谓词（`len` `dedup` `csv` `ascii` …）整个参数就是一个 spec，由谓词自己解析。
一开始没做这个区分，`dedup:0.65,4,40` 直接 `TypeError`。

**坑二：反斜杠。**
如果采用「反斜杠转义下一个字符」的常规写法，`re:\d` 会变成 `re:d`，
`re:\(` 会变成 `re:(` —— 而且**两种都还能编译**，只是匹配的东西变了。
这类 bug 在 1,000 题的规模上不可能靠肉眼发现。最终规则是：

| 写法 | 变成 | 说明 |
| --- | --- | --- |
| `\x2c` | `,` | 唯一转义成逗号的方式 |
| `\x3b` | `;` | 转义成字面分号 |
| 其它 | **原样** | `\d` 就是 `\d`，`\(` 就是 `\(` |

代价是「匹配字面逗号」要写 `\x2c` 而不是 `\,`。对一份以正则为主要载荷的 DSL 来说，
这个交换是划算的：**没有惊喜**。

### 2.3 难度分层是这一版的核心机制

每题必须带 `tier`：

| tier | 目标通过率（272M 线） | 配额 | 用途 |
| --- | --- | --- | --- |
| `E` | 0.70–0.95 | 20% | 热身与健全性检查 |
| `M` | 0.25–0.75 | **50%** | **主力区间**，能区分 checkpoint |
| `H` | 0.02–0.35 | 30% | 压力与天花板 |

报告按层分列通过率。**「这一批题整体偏易」以前只能靠总分猜测，现在看一眼层分布就知道**：
如果 `E=0.95 / M=0.90 / H=0.80`，尺子失效；如果 `E=0.60`，题目出难了。

实测本库的层配额：E 20.0% / M 49.9% / H 30.1%（目标 20/50/30）。

### 2.4 长上下文：深度阶梯而不是一堆长题

`docs/13` §5.4 说 4K 训练线「在能测之前不继续」。v3 的 50 项长上下文就是那把尺子，
设计成**受控实验**而不是「找些长文本来问」：

- 全部 2 轮：第 1 轮是一整段材料（2K/4K/6K/8K 字符，四档阶梯），第 2 轮才提问。
  被测模型必须先自己生成一句回复，事实要跨过**它自己的输出**活到第 2 轮。
- 事实埋在第 1 轮的**前 15%**；同类型干扰项（另一个编号、另一个人名）放在材料后段。
  判据锚定正确值并 `!any:` 干扰值——**「抓错了一个」是真实失败模式**，不是碰运气。
- 材料由 10 类真实文体组成（产品手册、会议纪要、气象记录、FAQ、行程、食谱、值班交接、
  校园通知、合同摘要、来电记录），中英混合，不是 lorem ipsum。

四档实测字符长度：`lc_d2k` 1808–2170 / `lc_d4k` 3603–5005 / `lc_d6k` 5403–5908 / `lc_d8k` 7223–7349。

> **权重是放大器。** `docs/13` §2.1 的教训是：v1 电池里「多轮」只有 1 项却占 24% 权重，
> 仅这一项就贡献了 +0.0321 的总分优势，而当时观察到的总分差只有 +0.0488。

### 3.1 编码与数学故意留着

`docs/04` §4 判定 CoT 在 272M 无效，这两类**必然贴地板**。
保留它们不是为了「救」，是为了**验证尺子在已知必败项上确实给 0**——
一把所有题都能过的尺子和一把所有题都不过的尺子一样没用。

## 4. 判据审计：三道闸

出题规模一大，「题目白送分」就成了主要风险。`compile_bench.py` 跑三道检查：

1. **锚点审计**（`check_anchors_in_prompt`）。如果判据要求的字符串**在题面里就有**，
   这题不看模型也能过。规则按「模型回答时能看到什么」分层：
   - **单轮题**：整个题面可见，锚点出现在里面就是白送 → **硬错误**。
   - **多轮题**：只有**最后一轮**在被测。第 1 轮给出的事实到第 4 轮才问，**不是白送**，
     那就是记忆任务本身（模型得跨过自己的回复把它带过来）。
   - **最后一轮点名了事实**：加 `!endswith:？,?` 反回声护栏——只会复读问句的模型过不了。
     `scripts/fix_recall_checks.py` 给 57 项补了这道护栏。
   - **对抗式探针**（用户先否认/追问，看模型守不守设定）：锚点出现在题面**正是设计意图**。
     这类进了人工复核白名单 `REVIEWED_ANCHOR_EXCEPTIONS`，**按 id 列出**，
     所以题目一改就会重新触发告警，不会继承豁免。

2. **弱判据 lint**。恒真正则、`len:0..` 之类空判据、开放式题没有退化护栏。

3. **难度配额**。某类偏离 20/50/30 超过 9 个百分点就点名。

### 4.1 修掉的一类真实缺陷：多轮记忆题可以抄

初版多轮记忆题长这样：

```text
第 1 轮  我叫小明，很高兴认识你。
第 2 轮  我叫什么名字？          chk = any:小明
```

**答案就写在上一轮里**——模型不需要记住任何东西，抄上下文即可，这题测不出记忆。
`scripts/fix_leaked_recall.py` 逐项定位（判据锚点出现在**更早**的用户轮）并改写问句：

```text
第 2 轮  我刚才让你记住的名字是什么？
```

只改问句，**不动事实、不动判据**，所以难度层、类别、测点全部保持。
60 项里 59 项自动改写，1 项（`mt_depth_03`）补了问句模板后人工处理。

## 5. 工程实现中的两次「以为」与实测推翻

### 5.1 以为瓶颈是 Python，实测是延迟

初版 `bench/fastgen.py` 的假设是：`RetNetForCausalLM.generate` 慢在 Python
（每步重建 list、每步一次 `.item()` 同步、重复惩罚在 Python 里遍历 `set(generated)`）。
为此重写了设备驻留版。

`scripts/bench_decode_profile.py` 实测（272M fp32，B=1）：

| 项目 | 耗时 |
| --- | --- |
| recurrent 前向 | **29.65 ms** |
| 前向 + `.item()` 同步 | 30.42 ms |
| **Python/同步开销** | **0.77 ms（3%）** |

**去掉 Python 只值 1.08x，不是 8x。** 30 ms 是读 272M fp32 权重（1.09 GB）
摊在两百来个小 kernel 上的延迟，与 Python 无关。这条记录留在 `fastgen.py` 的模块文档里，
免得下次再有人照着重写一遍。
（重写本身没白做：它现在是**逐位等价**的对照实现，`tests/test_bench_equivalence.py` 靠它钉住语义。）

### 5.2 以为 batching 是杠杆，实测只值 1.46x

接着试 batching。RetNet 的循环态形状是 `(bsz, heads, key_dim, value_dim)`，
天然按序列独立，所以 N 条请求可以共用一次前向。实测（`bench_batch_scaling.py`，48 项）：

| batch | 秒 | 秒/项 | 加速 |
| --- | --- | --- | --- |
| 1 | 45.0 | 0.94 | 1.00x |
| 8 | 30.8 | 0.64 | 1.46x |
| 16 | 30.7 | 0.64 | 1.46x |
| 32 | 30.7 | 0.64 | 1.46x |

**batch 从 8 涨到 32 完全不涨**——因为步成本由「把 272M 权重读一遍」主导，与 batch 无关。

而代价是实打实的：batch 的 GEMM 与单行 GEMM **不是逐位相同**，
~1e-6 的 logit 差异会偶尔翻转一次 multinomial 采样，之后整段回复就分叉了。
实测在 107 项抽样上 **8 项回复不一致**。

**决定：`--batch` 默认 1。** 逐位一致、可复现、与 `bench_v2`/`play.py` 直接可比；
`--batch 16` 保留给「要快 1.5 倍、且能接受小幅数值偏差」的场合，报告里会记下用的是哪种模式。
**用 1.5 倍的速度换掉可复现性，不划算。**

### 5.3 顺手修掉的一个真 bug

batching 实现过程中撞到一个更基础的问题：循环步的 `offset`（xPos 旋转位置）
**对整批是一个标量**，所以 prompt 长度不同的请求不能共用一步。
早期版本用「第一个活跃请求的长度」当整批的 offset，结果长度 12 的请求被按位置 47 旋转——
模型生成出一段**流畅但完全不相关**的文字，而且**不报错**。
这个 bug 在 smoke 测试里表现为「17 项全 0 分」，逐条看回复才发现每条回复都不像自己的题。

修法：按 `offset` 分组，**同一轮内**各组各自走一步（不能推到下一轮——
那样 `step_no` 会在请求缺席时前进，静默截断输出）。

### 6.1 可复现性保证

- **题库**：`bench/data/bench_v3.jsonl` + SHA256，写在 `manifest.json` 里。
  跑分报告记下被选子集的哈希，所以「同一份题」是可验证的说法。
- **采样的随机数流**：每条请求有自己的流（`rng_seed = blake2b(run_seed, item_id)`），
  第 k 个 token 用 `manual_seed(rng_seed + k)` 抽。
  这样**一条请求消耗的随机数与自己单独跑时完全一致**，与批大小、与邻居无关。
- **逐项温度**：`temp: 0.0` 的题走贪婪，其它走全局默认（不允许中间值，保证可比）。
- **断点续跑**：结果流式追加 JSONL，重跑跳过已有 `(item, seed)`。

### 8.2 这次实测说明的三件事

**一、尺子换了一档，不是模型退步了。** 同样这个 checkpoint 在 bench_v2 上拿 0.3587。

**0.145 比 0.36 更接近这个模型的真实水平。**

**二、主力区间上移了，而地板还在。** v3 里真正给出非平凡信号的类别是

### 9.3 贴地板的两个原因，实测区分开了

`docs/13` §3 说「结构化与数学是尺度限制」。v3 把「贴地板」拆成了两种，
`scripts/diag_hard_categories.py` 用对照实验分开：

**（一）格式不存在 —— 填空、语言、结构化。**
把同一个「填空」题改成两轮问句，或者加一句显式指令，**分数还是 0**：

| 探针 | 结果 |
| --- | --- |
| `太阳系中最大的行星是` | `太阳系中最小的行星是太阳系中唯一行星，主要由行星的表面…`（造了一个不存在的行星） |
| `太阳系中最大的行星是（只输出横线上的内容，不要解释。）` | `离太阳最近的星球是（只呈现横线上的行星，不需要解释）。` ← **把括号指令原样复读** |
| `The largest planet in the solar system is` | `The largest planet in Earth is the solar core of Earth, …` |
| `The Red Planet is (Answer with the missing words only.)` | `If the Red Planet has a significant connection to the planet, …` |

**模型对「填空」这个格式没有表征**：它把不完整的句子当成**续写**来对待（写下去），
把括号里的指令当成**正文**来复读。这不是「知识不够」——`clz_cap_major` 里的
「中国的首都是」它答得出（在 `qa` 里 0.05），是**格式**这一层就断了。
语言类（成语释义、拼音、量词）与结构化（JSON/CSV/YAML）同理。

**（二）真的取不回来 —— 长上下文。**
这是本版最有信息量的一条。50 项全 0，我做了**对照实验**排除格式解释：
把**同一段材料和同一个问题放进一轮**（模型训练时见过的形状），再测一遍：

| 题 | 两轮（原题） | 单轮（对照） | 材料长度 |
| --- | --- | --- | --- |
| `lc_d2k_01` | `本次联合评审会定在哪里？`（复读问句） | `材料二：材料二： 1. 材料二：（材料三` | 1,998 字 |
| `lc_d2k_02` | `本期采购` | `开头那写的本期合同编号` | 1,897 字 |
| `lc_d2k_03` | `To check the quarterly note, you can check the hub` | `The passage states that the hub` | 2,120 字 |
| `lc_d2k_05` | `本期菜的第一个名字是"番茄酱"…` | `第一个材料：材料：材料` | 1,915 字 |

**两种形状都拿不到那个事实。** 英文那两条尤其说明问题：模型**正确地理解了任务**
（"To check the quarterly note, you can check the hub…" 是标准的「根据材料回答」句式），
**只是把内容换成了幻觉**。所以这不是格式问题，是**检索失败**。

**结论：272M 在约 2K 字符（≈1.2K token）的跨度上就已经无法保留一个具体字符串。**
`docs/13` §5.4 说「长上下文在能测之前不继续」——**现在能测了，测出来的是 0**，
而且这个 0 是在**四档深度里最浅的一档**上取得的（2K/4K/6K/8K 全 0）。

### 9.4 下一版应该怎么改

按性价比排序：

| 优先级 | 改动 | 依据 |
| --- | --- | --- |
| **P0** | **把「填空 / 语言 / 结构化」从纯格式题改成问句题**，或在 `qa` 类里加倍补偿 | §9.3（一）：格式不存在，不是难度问题。不改这三类永远贴地板 |
| **P0** | **降档重标**：`指令遵循` 的 E 层要求过严（E 只有 0.12），把单约束题的通过率提到 0.5+ | §9.2 的层分布 |
| **P1** | **长上下文另立指标**：它不该进加权总分（全 0 会把总分压掉 1.5/16.2 权重），而应作为**独立的「检索深度曲线」**报告 | §9.3（二）：0 是真实且有价值的结论，但混在总分里只是噪声 |
| **P1** | 加**多种子**（≥3）才能把 55% 的真地板与约 280 项单种子假地板分开 | §9.2 注 |
| **P2** | 给开放题加**部分给分**（现在 0/1 太粗，续写只用锚点+护栏判） | §10 限制 5 |

**已经可以确定不必做的**：`docs/13` §5.1 的六条已全部落地，
其中第 2、3 条（难 RP 探针、深多轮）产出了 live 占比最高的两类；
第 4 条（长上下文项）产出了一个明确的、可证伪的结论。

### 9.5 结论：v3 该怎么用

- **可以立刻用**：`安全 / 鲁棒性 / 一致性 / 多轮 / 角色扮演` 这 5 类（355 项）
  是能区分 checkpoint 的，占了总权重 13.4/16.2 = 83%。
- **暂时只能当「地板探针」用**：`填空 / 语言 / 结构化 / 数学 / 编码 / 长上下文`，
  它们的作用是**证明某个能力确实不存在**，不是排序。
- **不要用总分做 checkpoint 选择**：总分被 8.4/16.2 的地板类权重拖成一个低分辨率的数。
  用「5 类对话行为的加权分」或直接看逐类。

## 10. 已知限制

1. **单种子。** 1,020 项 × 1 种子 = 1,020 次生成（约 42 分钟）。
   单种子会把「两模型恰好都没过」判成 floor——按 §9.2 的估算，840 个 floor 里约 280 个是假地板。
   要下「A 比 B 好」的结论必须多种子配对检验；
   `bench_v3.py` 已内置 McNemar 精确检验与逐类配对，但**没有多种子就没有统计功效**。
2. **一半以上的题贴地板**（§9.2）。这是本版**最大的问题**，且已有明确的修法（§9.4 P0）。
   在修好之前，**不要用总分做 checkpoint 选择**。
3. **长上下文只测到 8K 字符（约 4–5K token）**，因为项目最大的训练窗口是 2,048 token。
   深度阶梯的 8K 档超出训练分布，它在那一档上的失败**不能**直接读成「长上下文能力差」；
   但 2K 档的 0 是干净的（且已用单轮对照排除格式解释，§9.3）。
4. **`docs/11b` 的告警仍未解决**：生产尺度上 `parallel` 与 `chunkwise` 的 `max|diff|` 到 6.77。
   长上下文项默认用 `parallel` 预填（与 `generate()` 一致），
   `--lc_prefill chunkwise` 可切换，但两条路径的数值不等价，**切换会改变分数**。
5. **编码/数学贴地板是尺度限制**，不是题目问题（`docs/04` §4）。这两类保留作地板锚点。
6. **判据始终是「字符串层面的可判定代理」**，不是人工评分。
   开放题（续写、开放问答）用锚点 + 退化护栏近似，会漏掉「没跑题但很糟」的输出。
7. **bench_v2 与 bench_v3 的分数不可比**：题库、权重、判据全换了。
   v2 的结论（v10 略优于 rp，p=0.084）**没有被 v3 推翻**，但也不能用 v3 直接沿用。
