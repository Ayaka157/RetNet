# 25. 一步训练的计算构成：那 36% 的 elementwise + reduction 能压掉多少

> **数据来源与口径**：本文的数字来自一次 **纯静态分析**——逐算子读 `retnet_hf/modeling_retnet.py`、
> `retnet_hf/retention_fast.py`，按张量形状×(fwd+bwd) 遍数×字节宽度算流量，再除以标称带宽。
> 除标【实测】者外，**全部是推导，且是上界**：同一套算法在两处**已知消融**上高估了 2–3×
> （dropout 账 12.9 ms vs 实测 5.8 ms；CE 的 `.float()` 账 3.75 GiB vs 实测步时 0% 变化
> ⇒ cast 已被 inductor 融合）。**没有任何 GPU 作业被用来产生本文数字**（分析时正式训练正在跑）。
>
> 参照的实测基线（RTX PRO 6000 / batch 16 / seq 2048 / chunk 128 / bf16 / 575 ms 步）：
> GEMM 354.6 ms（61.6%）、Triton elementwise 160.5 ms（27.9%）、Triton reductions 48.5 ms（8.4%）、
> 其他 11.6 ms；SM 占用 81–100%（均 93%）、显存带宽 53–71%、功耗 480/600 W、无降频。

## 1. 结论三行

1. **能确定回收 ≈22–24 ms/步（占一步 575 ms 的 3.8–4.3%）**，全部来自三处**结构性冗余**：
   `rotate_every_two` 的 `torch.stack` 物化（≈8.3 ms）、`GrowthLayerNorm` 的 `cat`+切片（≈8.5 ms）、
   `inner + cross` 的独立 add（≈6.2 ms）。前两处改完可逐位一致，第三处用 `baddbmm` 数值略变（更准）。
2. **剩下 ~185 ms 是字节账，不是浪费**：逐算子数出的点式/归约流量 **≈274 GiB/步**
   （区间 150–300，取决于 inductor 已融合多少），按 1.79 TB/s 标称的下限是 **164 ms**；
   去掉 (A) 的 32 GiB 后是 **148 ms**。实测 209 ms ⇒ 这些核实际跑在 **≈1.41 TB/s = 79% 标称**，
   对混合广播/转置的点式核属正常水平。**36% 里没有藏 100 ms 的免费午餐。**
3. **唯一还剩 20–30 ms 余量的是「带宽效率」而不是「字节数」**（79% → 90%+）。
   静态判不了，必须先做 §5 的 E1 微基准。

## 4. 带宽下限推导 + 对既有结论的三处更正

数法：一遍 = 读+写；`mul` 反向 = 读 grad + 另一操作数、写 grad；`add` 反向是两个别名 = 0；
`cast` 视为已融合 = 0；反向 GEMM 不计入点式账。

- 274 GiB（= 294 GB）/ 1.79 TB/s = **164 ms**（纯带宽下限，含全部不可压项）
- 去掉 (A) 的 ~32 GiB → 242 GiB → **148 ms**
- 实测 209 ms ⇒ 实得 **1.41 TB/s = 79% 标称**；差的 ~37 ms 是"实际带宽 < 标称"的税
- 三类拆分：**(A) 结构可消除 22–24 ms； (B) 纯带宽下限 ≈148 ms； (C) 我的账错的部分**

**(C) 明确算错 / 可以排除的**

1. 最大嫌疑"衰减矩阵是 `[B,H,T,T]` 大张量"**不成立**：`T[h,i,j]=d_h^(i-1-j)` 是
   `[H,nc+1,nc]` = 22×17×16 = **5,984 个 fp32 = 23 KiB**（`retention_fast.py:156-161`）；
   `inner_mask` 是 `[H,C,C]` = **1.38 MiB**（`:82-84`）。真正的大张量是 `[B,H,L,*]`（88/176 MiB）
   与 `scores [B,H,nc,C,C]`（176 MiB）。
2. 训练路径里**没有** `torch.tril` / `masked_fill` / `clone`：快路径在对数空间用
   `clamp_min` + `torch.where`；`clone()` 只出现在 `__init__` 的 `gamma.clone()` 与 `generate()`。
   `slice_backward` 只来自 `GrowthLayerNorm` 的 `x[...,:768]/[...,768:]` 与 `S_all[:,:,:nc]`，
   合计 **≈3.5 ms（0.6%）**，**不是 8–10%** —— 见 `docs/22` 第 24 条。
3. **"融合 CE 省时间"在这张卡上是反的**：`fused_ce.py` 走 `h.float() @ weight.float().t()`，
   而 `train.py:166` 打开了 `allow_tf32` ⇒ 每次都是 **TF32** GEMM
   （32768×20000×1408 = 1.845 TFLOP；bf16 实测 4.62 ms ⇒ TF32 ≈ 9 ms）。
   融合后前向 1 次 + 反向 3 次 ≈ **36 ms**，而现状是 1 次 bf16 GEMM 4.6 ms + CE 点式 ~7 ms ≈ **12 ms**。
   **`RETNET_FUSED_CE` 必须保持关闭**（当前确实未设）。见 `docs/22` 第 25 条。
4. 本账在两处已知消融上**高估 2–3×**（dropout、CE 的 `.float()`）⇒ **表中每一项都应读作上界**。

## 5. 三个验证实验（每个 <5 min；等正式训练结束或换卡后跑）

- **E1（30 s）带宽微基准**：同尺寸 bf16 张量上的 6 种访问模式——contiguous copy/mul、
  broadcast-mul（`[H,C,C] → [B,H,nc,C,C]`）、transpose-copy、row-reduce(1408)、col-reduce。
  **可证伪预测**：contiguous ≥1.5 TB/s、broadcast 0.6–1.0、transpose 0.5–0.8。
  **若全部 ≥1.4 TB/s，则 209 ms 根本不是带宽问题，"79% 效率"不成立，重心应转向核实现。**
- **E2（2 min）核名普查**：`scripts/profile_kernels.py`（batch 16 / 4 步）后对 trace grep
  `triton_(poi|per|red)_`。预测：① `_per_`（persistent reduction，LN 统计）**≥15 ms 且被分类器
  归进"逐元素"桶** ⇒ 桶标签不可靠（48.5 ms 不是全部归约时间）；② 名字含 stack/cat 的 poi 核
  **≥10 ms** ⇒ 冗余确实被物化（§3 第 1/2 项成立）；若没有 ⇒ inductor 已融合，两项归零。
- **E3（2×90 s）融合 CE 反向验证**：`RETNET_FUSED_CE=1` vs 关，预测**开更慢 8–15 ms**。
  若实测更快，说明 TF32 速率的假设错了（那也是个有用结论）。
- 附 **E4（60 s）**：`GrowthLayerNorm` vs `nn.LayerNorm` 在 `[16,2048,1408]` 上 fwd+bwd，
  预测 growth 是 plain 的 2.3–2.8×，其中 `cat` 占 35–45%。

## 6. 静态分析**无法**确定、必须实测的项

1. inductor 是否已把 `stack`（rotate）、`cat`（GrowthLN）、`inner+cross` 的 add 融进邻核 ——
   (A) 的 22–24 ms 会在这三处之间摆动到 0。
2. 各类核的**实得**带宽（1.79 TB/s 是 GDDR7 标称，实例上从未量过 triad）。
3. "Triton elementwise 160.5 / reductions 48.5" 是**按核名分的桶**：`triton_per_*`
   （persistent reduction）落进"逐元素"，所以 reductions 那 48.5 ms 偏小。
4. 那次剖分的采样窗口是否包含优化器步（`prof.step()` 的位置有歧义）——
   本文账里 clip + Adam 只有 6.8 ms，只可能落在"其它 11.6 ms"里。
5. GLA 四张 mask 的反向流量（12 GiB/步 ≈7 ms）——**账里最大且最不确定的单项**，融合核可能减半。
6. `bnb AdamW8bit.step()` 的自定义核数量与流量（只确认了它没有 `clip_grad_norm`）。
7. **dmon 的 sm 81–100%（均 93%）与「CUDA 忙时 576 ms ≈ 墙钟 575 ms」互相矛盾**：
   若真有 ~7%（≈40 ms/步）的发射空隙，那是比点式融合更大的猎物，值得单独复核。

## 7. 两条影响归属的配置事实

- `use_swiglu=false` —— FFN 是 Linear+GELU+Linear，所以**没有**"`norm2` 被调用两次"那种
  SwiGLU 分支才有的冗余。
- `use_growth_ln=true, growth_old_dim=768` —— 41 次 `GrowthLayerNorm` 的 `cat` 来源。

## 8. 一句话可执行结论

**先把 §3 的 1/2/3 做掉（22–24 ms，风险低、可逐位验证），再用 E1 决定是否值得追那 ~37 ms 的带宽税；
CE 融合是负收益，别碰。** 想真正动那 148 ms 的带宽下限，只有两条路：降位宽（FP8 让激活字节减半，
与 `docs/24` §9.12 的 FP8 Amdahl 上限 1.45× 是同一杠杆的两面）或减少中间张量遍数（自写融合核替换
inductor 生成的 1027 个小核，工作量 L）。
