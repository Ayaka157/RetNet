### 1.6 ⚠️ 预训练池的入口只有一条，而且几乎没取到数

这条是清点时发现的**最有价值的缺陷**。`build_chat_mix_v9.py:274-296` 的 `replay` 段
是 `pretrain_v2` 与 `pretrain_merged` 进入对话配比的**唯一入口**（`build_chat_mix_v9.py:277`）：

```python
files = []
for d in ["data_cache/pretrain_v2", "data_cache/pretrain_merged"]:
    files.extend(sorted(x for x in p.glob("*.npy") if "_val" not in x.name))
    if (p / "train.ids.npy").exists():
        files.append(p / "train.ids.npy")

taken, chunk = 0, args.seq_len          # chunk = 512
for path in files[:30]:                 # ← 只取前 30 个文件（共 59 个）
    if taken >= 30_000_000:             # ← 意图上限 30 M token
        break
    src = np.load(str(path), mmap_mode="r")
    for start in range(0, src.shape[0] - chunk, chunk * 9973):
        train.add(piece.tolist(), [W_PLAIN] * chunk)   # 步长 = 512 × 9973 ≈ 5.106 M token
        taken += chunk
```

`[复核]` 按同一逻辑复现取数：

| 项 | 数值 |
|---|---|
| 候选文件 | 59（`files[:30]` 只用前 30 个） |
| 预训练池总量 | **4,128.7 M token** |
| 按脚本逻辑复现的 `taken` | **155,136 token** |
| `chat_pack_v9/meta.json` 记录的 `replay` | **155,136 token** ← 逐位一致 |
| 占池子比例 | **0.00376%** |
| 距离它自己的 30 M 上限 | **193 倍** |

**两个限制叠加造成了这个结果**：

1. `files[:30]` 把 59 个文件砍到 30 个；
2. 步长是 `chunk × 9973` ≈ 5.106 M token，而单个文件只有约 50 M token，
   于是**每个文件只能命中约 10 个 chunk**（≈5,120 token）。

即：**意图取 30 M，实际取到 0.155 M。** 所以模型在 272M 尺度上
**几乎从未见过预训练语料**——0.49 B 的已训 token 里，预训练只占 0.03%。

### 1.7 272M 有没有继承预训练

有，但**是继承来的，不是在 272M 尺度上做的**：

```text
retnet_100m_pretrain_v4  →  migrate_to_hf.py  →  retnet_100m_pretrain_v4_hf
                         →  grow_143m.py      →  retnet_143m_hf (143M)
                         →  grow_272m.py      →  272M
```

`[复核]` 所有 `tasks/*.json` 的 `data_dir` 只有
`chat_pack_v10 / v11 / v11_4k / v12 / v13`，**没有任何一个用 `pretrain_v2` 或 `pretrain_merged`**。
而 `checkpoints/retnet_100m_pretrain*` 系列目录说明 100M 那一代是做过预训练的。

**所以：272M 继承了 100M/143M 尺度的预训练成果，但 272M 本身只做过对话训练。**

## 2. 算力盘子：8 GB 能装多大，跑多久

### 2.1 显存：8 GB 到底能装多大（`[复核]` `scripts/vram_budget.py` 可复算）

**先纠正本文早先一版的错误**：那一版写「bf16 权重 2 B + fp32 master 4 B + 8-bit Adam 2 B = 8 B/参数」，
两处错：(a) 漏了梯度；(b) 以为权重是 bf16。
实测 `checkpoints/retnet_272m_v13/model.safetensors` 的**365 个张量全是 `F32`**
（1089.2 MB = 272.3M × 4 B），`train.py:148` 的 `from_pretrained` **没传 `torch_dtype`**，
`bf16=True` 只是 autocast，**不改变存储**。

#### 每参数常驻

| 项 | 字节/参数 | 依据 |
|---|---|---|
| fp32 权重 | 4.0 | safetensors 实测 F32 |
| fp32 梯度 | 4.0 | 与参数同 dtype |
| 8-bit AdamW m/v | 2.004 | uint8 各 1 B + absmax（块 2048，fp32） |
| **合计** | **10.004** | 272.3M → 0.507 GiB 优化器状态，与 `docs/19 §6.2` 独立记录的「0.55 GiB」吻合 |

#### 两个从实测反推的常数

| 常数 | 值 | 怎么来的 |
|---|---|---|
| 缓存分配器之外的占用 | **0.45 GiB** | C′ 配置 reserved 6.61 GiB，而 nvidia-smi 报 7226 MiB = 7.06 GiB，差 0.45 |
| 272M 的激活值（**关**检查点，batch 1，seq 2048） | **4.073 GiB** | reserved 6.61 − 状态 2.537 |
| 每多一个样本的激活 | **3.200 GiB/样本** | batch 1 → batch 2 的 reserved 从 6.61 涨到 9.81 |
| 固定项（workspace + 碎片） | **0.873 GiB** | 线性拟合 `act(b) = a·b + c` 的截距 |

#### 逐参数量核算（要求：全程开梯度检查点、batch 1、seq 2048）

可用预算 = 7.996（总量）− 0.20（安全余量）= **7.796 GiB**

| 参数量 | 权重+梯度+优化器 | 留给激活 | 结构估算的激活需求 | 判定 |
|---|---|---|---|---|
| 272 M | 2.537 GiB | 4.809 GiB | 0.26~0.46 GiB | ✅ |
| 400 M | 3.727 GiB | 3.619 GiB | 0.38~0.68 GiB | ✅ |
| 500 M | 4.658 GiB | 2.688 GiB | 0.44~0.78 GiB | ✅ |
| **600 M** | 5.590 GiB | **1.756 GiB** | 0.49~0.88 GiB | ✅ 有余量 |
| **700 M** | 6.522 GiB | **0.824 GiB** | **0.61~1.09 GiB** | ⚠️ **不能保证**（下限过、上限超） |
| 750 M | 6.988 GiB | 0.358 GiB | 0.61~1.09 GiB | ❌ 下限就超 |
| 800 M | 7.454 GiB | −0.107 GiB | — | ❌ 连状态都放不下 |
| 1 B | 9.317 GiB | −1.971 GiB | — | ❌ |

**所以「能塞 0.7B」这句话不成立——它落在线上，不是「能」。**
准确的结论是：**600M 可以，700M 不能保证，750M 以上不行。**

#### 激活需求是怎么估的

两项：**(a)** 每层存下来的输入 `L × seq × d × 4 B`；**(b)** 重算一层时的瞬时张量
（q/k/v/g + chunkwise 中间量 + MLP 隐层）。

| 配置 | L | d | (a) 存层输入 | (b) 重算瞬时（估） | 合计（估） |
|---|---|---|---|---|---|
| 272M 实测结构 | 20 | 1024 | 0.156 GiB | 0.10~0.30 | 0.26~0.46 GiB |
| 400M 例 | 24 | 1280 | 0.234 GiB | 0.15~0.45 | 0.38~0.68 GiB |
| 600M 例 | 28 | 1408 | 0.301 GiB | 0.19~0.58 | 0.49~0.88 GiB |
| 700M 例 | 32 | 1536 | 0.375 GiB | 0.24~0.72 | 0.61~1.09 GiB |

> **唯一的内部一致性检查**：272M 按结构估算、**开**检查点的激活 = 0.26~0.46 GiB；
> 而 272M **关**检查点的实测激活 = 4.073 GiB，比值 **8.8~15.6×**——
> 与梯度检查点通常省一个数量级的经验相符。
> **但这只是自洽性检查，不是对估算的验证。**

#### ⚠️ 这套账最大的窟窿

**开梯度检查点时的激活值，本项目一次都没有实测过。**
上面所有 400M 以上的判定，全部建立在「(b) 重算瞬时按 `L·d` 线性放大、
且在 272M 时落在 0.10~0.30 GiB」这个**推算**上。272M 那一点的 (b) 本身也是推算。

**决定性实验很便宜**：把 700M 的配置写出来，跑 40 步，看
`torch.cuda.max_memory_reserved()` 和 nvidia-smi。约 2 分钟 GPU 时间。
在跑之前，700M 的结论应当写作「未验证，结构估算跨在预算线上」。

### 2.1b 修正：按**训练进程本体**记账（本版推翻 §2.1 与 §2.1a 的结论）

§2.1 有两处**方法错误**：

1. 那个「分配器外开销 0.45 GiB」是拿**笔记本的 nvidia-smi（7226 MiB）**
   减去**桌面的 `reserved`（6.61 GiB）**——**两台不同的机器相减**，常数不可用。
2. 更根本的：`memory.used` 是**整卡**占用，不是单进程。桌面/系统进程也占。
   而 §2.1a 又拿「关梯度检查点的实测」去对「开梯度检查点的结构估算」，
   两个 regime 混在一张表里，于是看着差 10 倍。

#### 实测：每进程显存（笔记本，`Win32_PerfFormattedData_GPUPerformanceCounters_GPUProcessMemory`）

| PID | 进程 | 专用显存 |
|---|---|---|
| **32572** | **python（训练进程本体）** | **6,940 MiB** |
| 5288 | dwm.exe | 167 MiB |
| 33284 | WindowsTerminal | 43 MiB |
| 21252 | LegionZone | 37 MiB |
| 8144 | csrss | 34 MiB |
| 20680 | explorer | 32 MiB |
| 29300 | SearchApp | 21 MiB |
| 其余 4 个 | — | ~33 MiB |
| | **合计（计数器）** | **7,333 MiB** |
| | nvidia-smi `memory.used` | 7,226 MiB |

**桌面/系统那堆只占约 390 MiB，7 GB 基本全是训练进程的。**

> **已验证：7,226 MiB 就是峰值，不是稳态。**
> 2026-10-10 22:48–23:32 在笔记本上以 2 秒间隔采样 **约 1300 次、43 分钟**，
> `memory.used` **只有一个取值 7,226 MiB，零方差**；
> 其中 `checkpoint-22500`（时间戳 23:14:05）落在一个可识别的窗口内
> （利用率 97%→95%、功耗 86 W→96 W，持续约 45 秒），
> **该窗口内显存纹丝不动**。后续 60 次复采样同样只有 7,226 一个值。
> 所以**存盘不产生显存尖峰**，下面的预算用的是实测峰值。

#### 训练进程内部的账

| 项 | 数值 |
|---|---|
| 训练进程总占用 | **6,940 MiB（84.7% 的卡）** |
| 权重+梯度+优化器（10.004 B/参数） | 2,598 MiB |
| **激活 + workspace + CUDA context** | **4,342 MiB** |

> **这 4,342 MiB 是「关梯度检查点」的代价。** 项目自己的报告 §6.2 记得很清楚：
> B → C 之所以能快 1.26×，正是因为用 8-bit AdamW 腾出显存后**关掉了梯度检查点**。
> 而 §2.1a 那张表的 262~467 MiB 是**开**检查点的结构估算——
> 两者比值 **9.3~16.6×**，与「梯度检查点通常省一个数量级」相符。
> **但开检查点的激活值本项目从未实测**，这个比值只是自洽性检查。

#### 不改变任何其它设置（即维持「关检查点」）时，还能加多少参数

| 项 | 数值 |
|---|---|
| 余量（整卡 8188 − 训练进程 6940） | 1,248 MiB |
| 扣桌面/系统 ~390 MiB + 安全垫 205 MiB | **653 MiB** |
| 每 1M 参数常驻成本 | 9.54 MiB |
| **可再加** | **约 68 M → 总计约 340 M** |

且这仍是乐观值：关检查点时激活值随参数量线性涨（272M 那 4,342 MiB 就是它），
多 68M 参数的激活增量会把余量吃掉。**结论：不打开梯度检查点，几乎上不去。**

#### 逐参数量判定（要求：**打开**梯度检查点、batch 1、seq 2048）

进程可用预算 = 8188 − 390（桌面/系统）− 205（安全垫）= **7,593 MiB**

| 参数量 | 状态 | 进程可用余量 | 非状态需求（检查点激活估 + context/workspace 400~500 MiB） | 判定 |
|---|---|---|---|---|
| 272 M | 2,598 MiB | 4,995 MiB | 662~967 MiB | ✅ |
| 400 M | 3,816 MiB | 3,777 MiB | 794~1,201 MiB | ✅ |
| 500 M | 4,770 MiB | 2,823 MiB | 850~1,300 MiB | ✅ |
| **600 M** | 5,724 MiB | **1,869 MiB** | 905~1,399 MiB | ✅ 余量约 470 MiB |
| **700 M** | 6,678 MiB | **915 MiB** | **1,030~1,621 MiB** | ❌ **下限即超** |
| 750 M | 7,155 MiB | 438 MiB | 1,075~1,701 MiB | ❌ |
| 800 M | 7,632 MiB | −39 MiB | — | ❌ |

**结论收紧为：能稳妥上去的是 600M；700M 在乐观端也超预算 115 MiB，判为不行；750M 以上不行。**

而且这一切都建立在「**开**梯度检查点的激活值 ≈ 262~467 MiB（272M 尺度）」这个
**从未实测过的推算**上。**这是整份文档最大的不确定源。**

#### 可选的杠杆（都未实测）

| | 步时 | 吞吐 | 272M 到 Chinchilla |
|---|---|---|---|
| 优化前 A（逐块循环、chunk 64、batch 4、检查点、无 compile） | 2176 ms | 3,765 tok/s | **16.8 天** |
| 优化后 C′（本文） | 662 ms | 10,396 tok/s | **6.1 天** |

**3.29× 的加速把「272M 跑满算力最优」从 17 天压到 6 天。** 这是能做这个决策的前提。

## 3. 已决定：扩到 0.5B–0.6B，速度靠工程手段守

**决策（2026-10-10）**：参数量扩到 **0.5B–0.6B** 为止，剩下的靠训练工程而不是继续加参数。

### 3.1 为什么 0.5B 这个尺寸立得住

| 理由 | 依据 | 强度 |
|---|---|---|
| **跨过项目记录的 CoT 门槛下沿** | `docs/04:81`：「有效下限：约 0.5–1B（需大模型蒸馏 CoT 数据）」——272M 在门槛**下方**，扩到 0.5B 是跨结构性门槛，不是"升级" | 强（但 `docs/04` 是**对外部研究的记录，非本项目实测**） |
| **热启动而非从零** | 现有 100M→143M→272M 血统已吃约 0.5B 对话 token + 预训练；`grow_272m.py` 那套函数保持式增长可复用，等效 token 远高于 3.4B | 中（增长脚本存在，但 0.5B 尺度未做过） |
| **任务窄** | 靶子是中文对话/人设/指令遵循，不是开放域知识 + 代码 + 数学 + 29 语言 | 中（定性） |

### 3.2 ⚠️ 「Qwen 也有 0.5B」这个类比**不成立**

`[复核]` 从 [Qwen2.5 Technical Report](https://ar5iv.labs.arxiv.org/html/2412.15115) 取数：

| | Qwen2.5-0.5B | 本项目目标 0.5B |
|---|---|---|
| 参数量 | ~0.49 B | 0.5 B |
| 架构 | 24 层 / 14 Q 头 / 2 KV 头（GQA）/ tie embedding / 32K 上下文 | 20 层 / 16 头 / 128 key / 2048 value |
| 预训练 token | **~18 T**（系列口径，报告**未按尺寸拆分**） | **~3.4 B**（`pretrain_v2` 2.817 B + 对话 0.55 B） |
| token / 参数 | **~36,700** | **~6.8** |
| 语料差距 | — | **少 5,294 倍** |
| 后训练 | SFT 100 万条 × 2 epoch + 离线 DPO 15 万对 + 在线 GRPO | 尚未做 |

**Qwen2.5-0.5B 能用不是因为它小，是因为它吃了 18T token。**
所以「同样 0.5B ⇒ 同样可用」不成立；尺寸是**必要条件**，token 预算才是约束。

### 3.3 这个尺寸的代价（按 §2.2 吞吐）

| 目标 | 内容 token | 墙钟 |
|---|---|---|
| 把已落地语料吃一遍 | 3.4 B | **8.5 天** |
| 0.5B 的 Chinchilla（20×） | 10.0 B | **25.0 天**（需约 3 遍） |

### 3.4 于是研究目标变成

不再是「能扩到多大」，而是：**在这个尺寸上，每分钟买到多少能力。**
即两条同时做：(a) 让 0.5–0.6B 的步时尽量接近 272M 的 788 ms/step；
(b) 让每个 token 的信息量更高（配比、课程、蒸馏数据权重）。

## 5. 本文的方法与不确定性

- token 数：`.npy` 一律**读 shape 精确计数**；`.jsonl/.csv` 一律**抽样 2–4 MB 按 bytes 外推**，
  抽样取每个目录**最大的几个文件的前若干 MB**，**可能有排序偏差**。

  所以给的是区间 2.8–8.5 B 而不是单值。
- §2.1 显存、§2.2 步时**全部是推算**，没有一个 400M 以上的实测点。
  唯一实测锚点是 272M 的 6.61 GiB / 662 ms。
- `docs/07` 目录里「已投入使用 2739.4 B」不等于进了模型，见 §1.1 的说明。
