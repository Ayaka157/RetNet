### 0.2 容量无关 vs 容量相关（本文最重要的产出）

一句话版本：**格式、闭合、开火时机、度量口径——全部容量无关，全部能修；
推理内容（算术、代码、跨 1.2K token 检索）——容量相关，改数据改不出来。**

### 1.2 `<think>` / `</think>` 的 token 事实（已在代码层核实）

用 `BPETokenizer.load("data_cache/chat_pack_v13/bpe_tokenizer.json")`（词表 20,000）实测：

```text
<think>   = [5690, 533, 2605, 33]        4 个 token
</think>  = [5690, 18, 533, 2605, 33]     5 个 token
```

两者**只差一个 token：id 18（`/`）**。逐 id 解码：`5690='<'`、`533='th'`、`2605='ink'`、`33='>'`、`18='/'`。

三条必须写下来的推论：

1. **闭合是一个"在某个位置插入 1 个 token"的二元决策**，不是"生成一长串格式"。
   它天然是容量无关的。
2. 它们是**普通 BPE token，不是注册的特殊 token**（`tok.special_id` 只管 bos/eos/pad/unk）。
   所以 `skip_special_tokens=True` 不会剥掉它们，泄漏在输出里是**可见文本**；
   也因此 `bench/runner.py:150` 用 `reply.find("<think>")` 判定泄漏是可行的。
3. 任务描述里"`<` `>` `/` 是词表里的独立特殊 token"**不完全准确**：
   `'<'`=5690、`'>'`=33（无前导空格）与 19965（`' >'` 带前导空格）是两个不同 token、`'/'`=1788 与 18 也是。
   在 `<think>` 里用的是无空格版本。这一点影响的是**逐位字符串判据**，改判据时要按 id 而不是按字符串。

### 1.3 训练量算术（0.19 epoch 到底是多少）

| | 计算 | 结果 |
| --- | --- | --- |
| v13 训练量 | 12,500 步 × (2048×4) token | **102.4M token = 全包的 18.5%** |
| v13 用掉的"行" | 12,500 × 4 / 269,561 | 18.6% |
| 1 epoch 要多少步 | 269,561 行 ÷ 4 行/步 | **67,390 步** |
| 1 epoch 在优化路径上的时间 | 67,390 × 713 ms（[`15`](./15_计算路径优化.md) §0 配置 C） | **13.4 小时** |
| 1 epoch 在优化前的时间 | 67,390 × 2,176 ms | 40.7 小时 |
| v10 的训练量 | 65,000 × (512×4) / 482.3M | **27.6% epoch** |
| 3 epoch（优化路径） | 3 × 13.4 h | 40 小时 |
| Chinchilla 口径参考 | 272.3M × 20 | 5.45B token；项目累计 ≈ 0.82B 预训练 + 0.55B SFT ≈ **1.37B（25%）** |

**这张表的作用是给"容量"这个词去魅**：v13 只训了 18.5% 的一遍数据，v10 是 27.6%。
两个模型加起来都没有把这份 552M token 的数据看完过一遍。
所以"272M 学不会 CoT"这句话，目前**只被长上下文 0.000 与 v10 的数学 0 支持**（见 §5.5），
不被"训了很多遍还是不会"支持——因为**没有"训了很多遍"这回事**。

## 2. 最重要的一条修正：52% 的"泄漏率"是评测口径造成的

### 2.1 证据一：每个题目有自己的生成预算，而且极小

`bench/registry.py:167` 要求每项带 `max_new`（校验范围 [8, 512]），`bench/runner.py:129` 用它做
`max_new_tokens`。实测冻结题库 `bench/data/bench_v3.jsonl` 的 1,020 项：

- **`max_new` 的取值全部落在 16–160 之间**（众数 32/56/100/120）。
- **生成被预算截断**：单轮项 **644/879**（判据 `n_new == max_new`，这个判据是精确的）；
  多轮项 96/141（用 `n_new >= max_new × 轮数` 判，是保守下界）。合计 **740/1020 = 72.5%**。

而训练数据里 CoT 的长度是：**中位 570 token，p10 377，p90 1,072**（§1.1 实测）。
**给出 16–160 token 的预算，一个中位要写 570 token 思考的模型在物理上不可能闭合。**

### 2.2 证据二：把预算放开，泄漏就消失了

主跑（`logs/bench_v3/v13.T0.7_s1.jsonl`，1,020 项）按"是否被截断"切开：

| 子集 | 项数 | 泄漏率 | 判据通过率 |
| --- | --- | --- | --- |
| 单轮项 · 被预算截断 | 644 | **82.1%（529/644）** | 2.95% |
| 单轮项 · **未被截断** | **235** | **0.0%（0/235）** | 20.0% |
| 多轮项（141 项） | 141 | 1 项 | — |

**530 个被判"泄漏"的项里，529 个是单轮项，且全部是被预算截断；剩下 1 个是多轮项。
没有被截断的样本里，泄漏数是 0。**

再看大预算复测。仓库里已经有两份这样的结果（不是新跑的）：

| 文件 | 项数 | 预算 | 泄漏 | 命中天花板 |

**结论**：
1. v13 的**真实闭合率是 14/15 = 93.3%**，比训练数据的 91.1% 还略高——
   说明"闭合"这个行为它**已经学会了**，而且是泛化的（这 15 项是特意挑出来的泄漏案）。

   不是"永远不收尾"，是"**在预算根本不够的题上仍然开 think**"。

### 2.3 v13 真正的缺陷（修正后的版本）

把两条事实放在一起：

- 训练集里带 `<think>` 的样本只占 **5.60%**（117,973 / 2,107,335）；
- 基准上 **52% 的题目**触发了 `<think>`。

**条件在"中文指令式提问"这个形状上时，模型开 think 的概率被高估了约 10 倍。**
原因是训练数据里只有 R1 一个来源带中文 think，而 R1 的 **100%** 样本都带；
v9 基座里那些"不带 think 的同类问题"来自别的数据集、措辞分布不同，
不足以把这个条件概率压回去。

后果是：在 `max_new=24~160` 的题目上，模型把**整段预算**花在"嗯，我需要先弄清楚用户想要什么……"上，
然后被裁判截断——**这直接制造了七个零分类里的 5 个**。

### 2.4 七个零分类的可解释性审计

按类别统计"被预算截断的比例"（单轮项用 `n_new == max_new`，多轮项用 `n_new >= max_new × 轮数`，后者是保守下界）：

| 类别 | 项数 | 中位预算 | 被截断 | 泄漏率 | 得分 | **这个 0 能读出什么** |
| --- | --- | --- | --- | --- | --- | --- |
| 结构化 | 60 | 120 | **60/60（100%）** | 1.00 | 0.000 | ❌ 读不出"不会"，只读出"预算被 think 烧光" |
| 编码 | 25 | 48 | **25/25（100%）** | 0.88 | 0.000 | ❌ 同上（但地板锚点的作用不受影响） |

## 3. 数据侧还剩下的真缺陷：8.88% 的未闭合样本

既然泄漏的主因是评测口径，那数据里那 8.9% 的未闭合样本还重不重要？
**重要，但它是"把上限从 91% 抬到 100%"，不是"把 52% 降到 0"。**

### 3.1 精确账（逐条复刻管线算出来的）

我用 `retnet.packing.clean(raw, 4000)` + `retnet.chat.encode_dialogue(max_len=2048)`
把 `data_cache/a_grade/r1_110k_sft.jsonl` 的 110,000 条**完整重放**了一遍：

| 环节 | 数量 | 占比 |
| --- | --- | --- |
| 原始 `output` 含 `</think>` | **110,000 / 110,000** | **100.0%** |
| 经 `clean(out, 4000)` 后 `</think>` 已丢失（字符上限砍掉） | 6,270 | 5.70% |
| 保住 `</think>`、但对话超出 2048 token 窗口 | 3,499 | 3.18% |
| **最终进入训练、但没有 `</think>`** | **9,769** | **8.88%** |
| 最终进入训练、`</think>` 完整（闭合） | **100,230** | **91.1%** |
| 其中 ids 恰好 2048 token（= 被窗口整段截断，末尾写死 `<eos>`） | 9,431 | — |

交叉验证（两条独立路径给同一个数）：
- npy 实测：新区 `<think>` 出现 109,634 − `</think>` 99,896 = **9,738**；
- 新区 `nonpad == 2048` 且以 `<eos>` 结尾的行 = **20,775** → 其中 9,738 个是未闭合的，
  另外约 **11,000 个（10%）是"闭合了但答案被砍断"** 的样本。

**两条路径的差是 31（0.3%），在噪声范围内。**

### 3.2 这条缺陷的性质

- 9,769 条未闭合样本 × 约 2048 token ≈ **20.0M token 的"开 think → 漫谈 → `<eos>`"监督**，
  占全包 **3.6%**、占回复 token 质量的 **5.6%**。
- 它们全部由 `encode_dialogue()` 的截断分支产生：
  `ids[-1] = tok.eos_id`（`retnet/chat.py:69-73`、`119-123`）。
  **也就是说：管线主动把"在思考中间停下来"写成了正确的目标。**
- 但请注意比例：**9,769 个"think 内 eos"决策 vs 100,040 个"正确闭合"决策**，
  样本级不平衡只有 **9.2% : 90.8%**。它**不足以**单独解释 52%（现已证明 52% 是假象），
  但它是"训练集闭合率 91.1%"这个上限的**唯一来源**。

所以修它的意义是：**让训练数据的闭合率变成 100%，从而让"泄漏率"这个指标变成一个干净的 0/1 诊断**，
而不是"永远有一个 9% 的地板"。代价极低（见 §8），没有理由不修。

### 3.3 还有一个被忽略的次生缺陷：答案被砍断

约 **11,000 条（10%）** 样本 `</think>` 完整、但答案被窗口砍掉。
它们教的是"关掉 think，然后说一半就 `<eos>`"。
这可能是"短答题答一半就停"这类行为的来源之一。修法与 §3.1 同源：
**先给答案留预算，再给 CoT 留预算**（见 §8.1 的"保结构截断"算法）。

## 4. 容量无关的手段

每条给出：**打哪个指标 / 代价 / 本项目最小验证实验**。
指标代号：**M1 泄漏率**（修口径后）、**M2 think 开火率**（新指标）、**M3 大预算闭合率**、
**M4 零分类通过率**（在"未被截断"子集上报）、**M5 live 五类加权分**、**M6 中间结果召回曲线**。

### A1（P0）修泄漏度量口径

- **做什么**：`bench/runner.py:140-159` 的 `_judge()` 目前无条件判
  `think_leak = "<think>" in reply and "</think>" not in reply[leak_at:]`（L150、L155）。
  增加一个 `budget_cut` 标志（调用方已知道 `n_new` 与 `item.max_new`），并把泄漏定义改为
  **"未被截断 且 没有 `</think>`"**；报告里把 `budget_cut` 率作为一等指标单列。
- **打哪个指标**：M1。修完之后 v13 的 M1 从 52.0% 变成 **0%（235 个未被截断样本中 0 个泄漏）**。
- **代价**：0 GPU 训练；改 20 行 Python；用现成的 `logs/bench_v3/v13.T0.7_s1.jsonl` 重算 0 成本。
- **最小验证实验**：改完后用 `scripts/bench_report.py`（只读重出报告）重算
  `logs/bench_v3`，确认：(a) M1 的重算值与本文 §2.2 的表一致；(b) 报告里出现 `budget_cut` 率。
  **不需要 GPU**。
- **附加**：题库的 `max_new` 设计（16–160）与 CoT 模型不兼容——它隐含假设"答案长度 = 总长度"。
  建议把每项的预算定义为 **CoT 预算 + 答案预算**，或对全部项统一给 `--min_budget 600`。

### A2（P0）清掉并尽量救回未闭合样本

- **做什么**：见 §8.1。两步：(1) 编码后**硬过滤**任何"有 `<think>` 无 `</think>`"的样本；
  (2) 对会被砍的样本改用**保结构截断**（砍 CoT、保答案），把 9,769 条救回来。
- **打哪个指标**：M3（训练数据闭合率 91.1% → 100%）、M1 的地板。
- **代价**：0 GPU；`build_chat_mix_v13.py` 约 +25 行；重建包约 1 小时 CPU；
  不加 (2) 的话丢 9,769 条（全包 3.6% token），加 (2) 则几乎不丢。
- **最小验证实验**：重建后跑本文用的那 20 行 numpy 审计（`<think>` 计数 == `</think>` 计数，
  且逐样本无未闭合），**CPU 约 2 分钟**。通过标准：未闭合样本数 = 0、
  新区 `nonpad==2048` 行数从 20,775 降到 ~0。

### A3（P0）给 R1 形状的 prompt 配 no-think 版本（治"开火率"）

- **做什么**：把 R1 的一部分样本**去 think**（只留 `</think>` 之后的答案）作为额外的监督样本，
  使"中文指令式提问"这个条件下 `</think>` 与"直接作答"两种行为都存在。
  这是 `docs/04` §4 表格里的"剥离 think"，但**不是替代长 CoT，而是与它并存**。
- **打哪个指标**：**M2（新的核心指标）**、M4（结构化/指令遵循/填空/编码/数学五个被截断的零分类）。
- **代价**：0 GPU；CPU 约 1 小时（v12 的 `--strip_think` 路径已存在，见 `build_chat_mix_v10.py:51-52`）。
- **配比建议**：R1 样本里 50% 保 CoT、50% 去 CoT（现在是有 CoT 的那部分里 8.9% 还坏了）。
  同时保留 v9 基座的 52M instruct token 不动。
- **最小验证实验**：**同一 checkpoint 上先测，不用重训**——用 `play.py` 或一段 30 行的解码脚本，
  在 v3 的 100 道"短答题"（`max_new ≤ 64`）上测 M2：现在应该是 ~60–100% 开 think，
  目标是降到 20%。判读标准：如果模型在无 CoT 数据上开火率不降，说明（a）配比无效，或
  （b）需要重训才能显现——那就进 A2+A3 的联合重训（2.5 小时）。
- **理论支持**：[Chain of Draft](https://arxiv.org/abs/2502.18600)（arXiv:2502.18600）
  说明"写少一点"在多数任务上不掉分；
  [Do NOT Think That Much](https://arxiv.org/abs/2412.21187)（arXiv:2412.21187）
  说明过长的思考在简单题上是纯浪费。对我们的意义是：**短答题不该进 think 通道**。

### A4（P1）收尾 token 加权 + think 段降权（改 loss，不改 token）

- **做什么**：在 `retnet/chat.py` 增加两个权重码，在 `modeling_retnet.py` 的 loss 里加权：
  - `W_THINK = 4` → 权重 `think_loss_weight`（建议 0.3）
  - `W_CLOSE = 5` → 权重 `close_loss_weight`（建议 10~20）
- **为什么这样有效**（这是本节唯一的定量论证）：
  - 闭合决策在 CE 里是"2048 个 token 里挑 1 个"——正确闭合的 `/` 决策只有 100,040 个，
    占回复 token 质量 **0.028%**。**这个梯度信号天然被稀释了三个数量级。**
    任何数据清洗都改变不了这一点，只有显式加权或换目标才能改。
  - think 段降权的理由是：think 占回复质量的 **23.7%**（85.0M / 358.9M），
    而它对应的能力（多步推理）在 272M 上测不出来（数学/编码 0.000）。
    把 23.7% 的监督质量从"学不会的推理"挪到"能学会的答案格式"是划算的。
- **打哪个指标**：M1（泄漏地板）、M3、M4（把预算花在答案上）。
- **代价**：训练侧 2.5 小时/次（12,500 步）；改 3 个文件、约 15 行；
  **不改 token id，只改权重码，所以推理路径完全不受影响**——这一点很重要，
  它是"训练与推理共用 `chat.py`"这个设计中唯一安全的改动类型。
- **最小验证实验**：两组对照各 12,500 步（同一份 A2/A3 修好的数据）：
  ① 不加权；② `think=0.3 / close=15`。看三个数：M3（大预算闭合率）、
  平均 CoT 长度（是否塌成 0 = 过度闭合）、M5（live 五类是否退化）。
  判读标准：M3 ≥ 0.95 且 M5 相对 ① 退化 ≤ 0.02。
- **风险**：过度闭合。护栏是"平均 CoT 长度"这个数（现在 570，不要掉到 200 以下）。

### A5（P2）短 CoT 课程（从短到长）

- **做什么**：先训 CoT 短的子集，再放开到全长。可以用 A2 的"保结构截断"直接造短样本。
- **本项目的硬约束（实测）**：R1 的 CoT 天生就长——

  | CoT 长度阈值 | 样本数 | 占比 |
  | --- | --- | --- |
  | ≤ 256 | **980** | 1.0% |
  | ≤ 384 | 11,199 | 11.2% |
  | ≤ 512 | 38,065 | 38.1% |
  | ≤ 768 | 76,226 | 76.2% |

  **p10 就是 377 token。所以"自然短 CoT"几乎不存在**（≤256 只有 980 条，做不了课程）。
  这条路只有两个走法：**(a) 用 A2 的保结构截断人工造短 CoT**；
  **(b) 用 API 模型针对 bench 的 7 个地板分类重新合成 200–400 token 的中文短推理**（几十元量级）。
- **打哪个指标**：M3、M4（填空/结构化）。
- **代价**：(a) 0 GPU + CPU 半小时；(b) API 成本 + 1 天。
- **最小验证实验**：只做 (a)：用"CoT 砍到 ≤384、答案完整"的子集单独微调 3,000 步
  （从 v13 或 rp 出发），测 M3 与 M4。**判读标准**：如果短 CoT 课程能到 M3 ≥ 0.95 且
  填空类从 0.00 抬到 0.10+，说明"格式 + 长度适配"是真的杠杆；
  如果 M3 到了但 M4 纹丝不动，说明格式与能力确实是两回事。

### A6（P0，诊断用，不训练）解码期强制闭合 / think 内禁 EOS

- **做什么**：改 `bench/fastgen.py` 的采样循环（这是一个 30 行的对照实现，改动安全）：
  (a) 在检测到"已开 `<think>` 未闭合"时，把 `<eos>` 的 logit 置 `-inf`（logit bias）；
  (b) 到第 N 步仍未闭合则直接续上 `</think>`（即 [s1](https://arxiv.org/abs/2501.19393)
  （arXiv:2501.19393）的 **budget forcing**）。
- **为什么这是最划算的一步**：它把"格式"与"能力"**在同一批题目上机械地分开**。
  做完之后，"七个零分类到底是不会还是没说完"就有了直接答案——
  这正是 A1 之后所有其他实验的前置条件。
- **打哪个指标**：M1（构造性归零）、M4。
- **代价**：0 训练；1–2 小时 GPU 推理（1,020 项 × 1 种子约 42 分钟，改动后相近）。
  注意：这是**推理侧**改动，不影响权重，随时可回退。
- **最小验证实验**：同一 checkpoint 跑三次 bench_v3（1 种子）：
  ① 原状；② 禁 EOS 在 think 内；③ 禁 EOS + 600 token 强制闭合。
  对比每类的 M4 与 M1。**判读标准**：
  - 如果 ②/③ 让结构化/指令遵循/填空的通过率显著上升 → 那些零是"预算被烧光"，A3+A4 值得做；
  - 如果纹丝不动 → 那些零是**能力**问题，docs 04 §4 的判断成立，应当停止在这些类别上投数据。

### A7（P2）格式 DPO（无 reward model 的唯一可行偏好方法）

- **做什么**：构造偏好对，直接惩罚"预算内不闭合"。**不需要 reward model，不需要 RL 基建**：
  - `chosen` = `<think>{完整 CoT}</think>{答案}`
  - `rejected` = `<think>{CoT 前 400 token}<eos>`
  两者共享同一 prompt，全部**离线合成**（从 R1 现有数据切）。
  更诚实但也更贵的版本是 rejected 用模型自己采（on-policy）：500 条 prompt × 600 token ≈ 2 小时生成。
- **打哪个指标**：M1、M3。
- **代价**：DPO 要两次前向，显存在 8GB 上仍然可行（batch 1 × accum 4 + 8-bit Adam，
  参照 [`15`](./15_计算路径优化.md) §3 的配置）；200–500 步，lr 5e-7 起，约 1–2 小时。
- **最小验证实验**：从 `retnet_272m_rp` 出发跑 300 步，
  测 M3 与 M5。**判读标准**：M3 上升且 M5 不掉 → 可用；
  如果 M5 明显退化（把 RP 训坏了）→ 说明离线合成的 rejected 太容易被区分，
  需要 on-policy 对，优先级下调。
- **文献**：[DPO](https://arxiv.org/abs/2305.18290)（arXiv:2305.18290）、
  [SimPO](https://arxiv.org/abs/2405.14734)（arXiv:2405.14734）。
- **反向文献（必读）**：[Let Me Speak Freely?](https://arxiv.org/abs/2408.02442)（arXiv:2408.02442）
  说明**过强的格式约束会掉推理分**。这正好是我们 A4/A7 的风险面，
  所以每一项都要配"live 五类不退化"的护栏。

### A8（P0，一次性判容量）"中间结果召回"探针

- **做什么**：CoT 能起作用的**唯一机制**是"把中间结果写进上下文、几百 token 后再读回来"。
  所以**直接测这个能力**，不必绕道算术：
  1. 让模型记住一个随机字符串（如 `编号 K7Q3`）；
  2. 插入 N 个无关 token（N = 128 / 256 / 512 / 1024 / 2048）；
  3. 再问 `编号是什么？`，用精确匹配判分。
- **为什么这是判容量的关键实验**：训练数据的 CoT 中位 **570 token**、p90 **1,072 token**。
  如果召回曲线在 512 之前就塌掉，那么**无论怎么训，272M 都不可能用 CoT 做多步推理**——
  因为 CoT 的每一步都要在 ~570 token 的距离上读回上一步的中间结果。
  这是一个**与算术能力无关**的、干净的容量判据。
- **已有的相关数据**：v3 的长上下文类别在 **2K 字符（≈1.2K token）** 上是 0.000
  （docs 14 §9.3 已用单轮对照排除格式解释）；多轮 E 层 0.44 说明 100–300 token 的短期记忆还能用。
  **570 token 正好落在"已知能勉强工作"与"已知完全失败"之间的未测区。**
- **打哪个指标**：M6（新指标，横轴是距离）。
- **代价**：0 训练；约 2 小时 GPU 推理（5 档 × 100 条 × ~1,000 token 生成为主，可批量）。
- **最小验证实验**：就是这个探针。**判读标准**：
  - 曲线在 ≥512 处仍 ≥0.5 → 容量不是硬墙，继续投数据/训练量；
  - 曲线在 ≤256 就塌到 0 → **CoT 在本尺度上物理不可行**，
    `docs/04` §4 的 0.5–1B 门槛得到独立佐证，此后应把全部精力放在 RP/多轮/一致性（live 五类，占权重 83%）。

## 5. 容量相关的手段（修不了推理质量）

### B1 PRM / ORM（过程奖励 / 结果奖励）—— **本项目不可行**

- **为什么**：ORM 在可验证域上等价于一个精确匹配的验证器，本来就不需要模型
  （[Training Verifiers to Solve Math Word Problems](https://arxiv.org/abs/2110.14168) 的思路）；
  PRM 需要**步骤级标注**（[Let's Verify Step by Step](https://arxiv.org/abs/2305.20050)，
  arXiv:2305.20050）或自动步骤标注（[Math-Shepherd](https://arxiv.org/abs/2312.08935)，arXiv:2312.08935，
  ACL 2024）。而我们**在数学/编码上的通过率是 0.000**——PRM 训练集里一条正样本都没有。
- **结论**：**不可行**。等模型在某个可验证域上有非零通过率之后再谈。

### B2 RL 类（GRPO / RLVR）—— **格式维度上可行但无必要，能力维度上不可行**

- **能力维度**：GRPO（[DeepSeekMath](https://arxiv.org/abs/2402.03300)，arXiv:2402.03300）
  依赖可验证奖励。数学/编码的奖励**恒等于 0** → 组内奖励方差为 0 → **梯度为 0**。
  这是纯粹的数学事实，不是工程问题。**不可行。**
- **格式维度**：[DeepSeek-R1](https://arxiv.org/abs/2501.12948)（arXiv:2501.12948，Nature 645:633）
  的 R1-Zero 用 format reward 让 `<think>…</think>` 结构"涌现"。
  但我们的问题是**反过来的**：模型已经会闭合（93.3%），需要的是**少开 think**，
  而"少开 think"可以通过数据配比（A3）直接得到，**不需要 RL**。
- **结论**：**不要上 RL。** 数据过滤 + 加权能拿到同样的格式收益，且成本低两个数量级
  （本项目没有 RL 基建，任何 GRPO 实现都要从零写 sampling/advantage 循环）。

### B3 拒绝采样 / 迭代自蒸馏 —— **被离线数据支配**

- **方法**：[STaR](https://arxiv.org/abs/2203.14465)（arXiv:2203.14465）、
  [Beyond Human Data (ReST^EM)](https://arxiv.org/abs/2312.06585)（arXiv:2312.06585）。
- **为什么在本项目无效**：拒绝采样只能用"模型自己生成得对"的样本
  （需要过滤器）。而：
  - 数学上的过滤器有，但**模型通过率 0.000**，无正样本可采；
  - 格式上的过滤器有，但实测 v13 大预算闭合率 **93.3%**——采出来的样本
    比现成的 R1 数据**差**（R1 是 100% 闭合的完整推理）。
- **结论**：**离线数据严格优于自采样数据，所以自蒸馏被支配。**
  在 A2/A3 把数据修好并训出第一版可用模型之前，不要在这条路上花时间。

### B4 训练量：一次 1 epoch 对照（**必做，但不是"容量"实验**）

- **做什么**：同一份修好的数据，跑满 1 epoch（67,390 步，13.4 小时优化路径）。
- **注意 lr 调度**（这是 `docs/02` §5 那个"锯齿"坑的现代版本）：
  v13 的 cosine 是**按 12,500 步走完**的，所以它停在"学习率已经衰减到 0"的状态。
  **续训不能重启一条新的 cosine**（文档里 `train_loop.py` 的锯齿就是这么来的）。
  正确做法二选一：
  - 重新起跑，`--lr_total_steps 67390`（干净，但丢掉 12.5k 步）；
  - 或从 v13 续训，用**低学习率 warm restart**（如 1e-5，cosine 到 0 覆盖剩余 54,890 步）。
    代价：轻微跳变，并且 `docs/15` §8 提醒 **`chunk_size` 必须与开跑时一致**（v13 用的是默认 64）。
- **打哪个指标**：M1/M3（收敛）、M4、M5。
- **代价**：13.4 小时（优化路径）/ 40.7 小时（优化前）。
- **预测**：见 §6。核心是——**这一步的价值不在"可能涨分"，而在"把容量问题与训练量问题分开"**。
  现在这两个问题在 v13 上是混在一起的，任何结论都不可靠。

### B5 272M 的容量上限：诚实的判断

**证据支持"修不了"的部分：**

1. **长上下文 = 0.000，且已排除格式解释**（docs 14 §9.3 的单轮对照）。
   272M 在 **2K 字符 ≈ 1.2K token** 的跨度上无法保留一个具体字符串。
   这是**与 CoT 同机理**的能力：CoT 依赖把中间结果写进上下文再读回来。
2. **数学/编码全 0，且 v10（65k 步、0.28 epoch、更强的数据混合）也是 0。**
   历史上唯一一次"投入更多步数"的实验（v10，133M token）在数学上零收益，代价是 10.7 小时。
3. **蒸馏下限**：[Small Models Struggle to Learn from Strong Reasoners](https://arxiv.org/abs/2502.12143)
   （arXiv:2502.12143，ICML 2025）指出强推理者的 2,000+ token CoT 小模型装不下，
   学到的结果是"要么复读要么崩"；R1-Distill 的 1.5B 都明显弱于 7B，而我们是 272M。
4. **反证一下"涌现门槛"这个说法本身**：[Emergent Abilities](https://arxiv.org/abs/2206.07682)
   （arXiv:2206.07682）式的门槛是**度量依赖**的
   （[Are Emergent Abilities a Mirage?](https://arxiv.org/abs/2304.15004)，arXiv:2304.15004）。
   所以 `docs/04` 的"0.5–1B"是经验法则，不是定律。

**证据支持"还没试过"的部分（必须写清楚，否则就是自欺）：**

5. 这个模型**从未看过一遍自己的数据**（v13 18.5%、v10 27.6%），
   累计 token 约为 Chinchilla 口径的 25%。
6. **反例是存在的**：[TinyGSM](https://arxiv.org/abs/2312.09241)（arXiv:2312.09241，NeurIPS 2023）
   用一个 1.3B 模型在 GSM8K 上做到 80%+，靠的不是规模而是**高质量合成数据 + 反向课程**。
   这条证据的意思是："小模型做不了推理"这个结论**高度依赖数据质量**，而我们的数据刚刚才被证明
   有 8.9% 的样本在教错误的行为、10% 的样本答案被砍断。
7. **LIMO**（[Less is More for Reasoning](https://arxiv.org/abs/2502.03387)，arXiv:2502.03387）
   用 817 条精选样本就大幅超过 100k 规模的基线，主张推理是"**诱发**"而不是"注入"。
   对 272M 是否成立未知，但它说明**样本量与课程设计比"喂多少"更重要**。

**我的判断（明确写成可证伪的形式）：**

> **272M 不可能做出连贯的长 CoT 推理。** 最强的一条证据是长上下文跨 1.2K token 的检索为 0——
> 而 CoT 的每一步都需要在几百 token 的距离上读回中间结果。这条证据**与数据无关**。
> 但本项目的"数据侧"确实从未干净过（8.9% 负样本 + 10% 答案被砍 + 评测口径错误），
> 所以我接受一个**受控的证伪条件**：跑完 §A8 的召回曲线，
> **如果召回率在 512–1024 token 处仍 ≥ 0.5，我就承认容量不是硬墙**，
> 届时应把预算投到数据与训练量而不是扩参。

```python
def r1_reader(path, max_chars=20000):     # 注意：默认值从 1200 抬到 20000
```

#### 改动 2（必做）：`scripts/build_chat_mix_v13.py:115-126` 的编码循环

把"编码 → 直接入包"改成"编码 → **闭合审计** → 保结构截断"：

```python
# 常量放在文件顶部
THINK  = (5690, 533, 2605, 33)
CLOSE  = (5690, 18, 533, 2605, 33)

def _find(ids, pat):
    n = len(pat)
    return next((i for i in range(len(ids) - n + 1) if tuple(ids[i:i + n]) == pat), -1)

def encode_closed(tok, user, cot, ans, max_len):
    """优先保 <think>…</think> 结构；装不下就砍 CoT，绝不砍答案。"""
    ans_ids = tok.encode(ans)
    cot_ids = tok.encode(cot)
    head = tok.encode(f"用户：{user}\n助手：")
    # 预算：bos(+1) + head + cot + ans + eos(+1)
    room = max_len - 2 - len(head) - len(ans_ids)
    if room < 0:                      # 答案都装不下 —— 直接丢弃，不要教半句话
        return None
    if len(cot_ids) > room:
        cot_ids = cot_ids[:room]      # 砍 CoT 的尾巴
        # 若砍完丢了 </think>，就补一个（这就是"保结构截断"）
        if _find(cot_ids, CLOSE) < 0:
            keep = max(0, room - len(CLOSE))
            cot_ids = cot_ids[:keep] + list(CLOSE)
    ids = [tok.bos_id] + head + cot_ids + ans_ids + [tok.eos_id]
    # 最后一道闸：绝不产出未闭合样本
    if _find(ids, THINK) >= 0 and _find(ids, CLOSE) < 0:
        return None
    return ids, None                   # codes 由调用方按段构造
```

主循环里替换：

```python
for (user, (cot, ans)) in batch:
    r = encode_closed(tok, user, cot, ans, args.seq_len)
    if r is None:
        dropped += 1
        continue
    ids, _ = r
    if len(ids) < 16:
        continue
    ...  # 原有 val/train 分流不变
```

**为什么不用"编码完再检查"（更省事的写法）**：那会把 9,769 条整条丢掉。
用保结构截断能救回绝大部分——**答案完整、格式合法、只是 CoT 短一点**，
这正好也就是 §A5 想要的短 CoT 样本，一举两得。

```python
"think_leak": bool(not budget_cut and leak_at >= 0 and "</think>" not in reply[leak_at:]),
```

- 报告（`bench/analysis.py:169、198`）里把 `leak` 与 `budget_cut` 并排报。

#### 改动 11（A1）：题库预算策略

`bench/data/bench_v3.jsonl` 的 `max_new` 全部在 16–160。两种修法：
- **便宜**：加一个 `--min_budget N` 覆盖参数（只对"诊断跑"生效），
  用 N=600 重跑一个分层子集（如每类 10 项 = 150 项，约 40 分钟）；
- **正确**：把每项的预算重新定义为 `CoT 预算 + 答案预算`，
  并在 `bench/CONTRACT.md` 里写明"预算必须覆盖 CoT"，这是 CoT 模型的尺子该有的语义。

#### 改动 12（A6）：`bench/fastgen.py`

在采样循环（L314 附近）加两个可选开关：
`--ban_eos_in_think`（未闭合时把 id 2 的 logit 置 `-inf`）、
`--force_close_at N`（第 N 步强行续 `</think>`）。
这是 [s1](https://arxiv.org/abs/2501.19393)（arXiv:2501.19393）的 budget forcing。

#### 改动 13（A8）：新增召回探针

`scripts/recall_probe.py`（新文件，约 80 行）：按 §A8 的设计生成 5 档距离 × 100 条，
输出"距离 → 精确匹配率"曲线。**这是判容量的唯一一次实验，不要和别的实验混在一起跑。**
