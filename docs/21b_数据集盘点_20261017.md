## 2. 12 个 chat_pack 的谱系：只有 v13 值得留

用 `meta.json` + 构建脚本互相印证，这条链是**同一个数据体的 12 次重打包**，不是 12 份语料：

```
v3  (int32, 512)      194.7M  lccc/glm/ultrachat/sharegpt4/belle/smoltalk/coig/firefly/zhihu_kol/ruozhiba/replay
 └► v4  (int16, 512)  217.2M  + haruhi×3 / coser / limarp / roleplay_zh_gpt4 / webnovel
     ├► v5            233.9M  + style_rp
     ├► v6            209.9M  同源、抽样更少（回退版）
     ├► v7            223.3M  + cornell_rp / wikisource_*_rp
     ├► v8            225.0M  + gutenberg_rp
     └► v9            280.6M  + a_grade 10 个源（nana/meow/longevo/novelist/hundredcv/4 个纯文本）
         ├► v10       482.3M  v9 基座 + R1(55.8M，被 1200 字符截断) + i_wonder_why(117.3M)
         │   ├► v11     442.5M  ← v10 重打包到 8 192（**纯格式转换，内容不变**）
         │   ├► v11_4k  442.6M  ← v10 重打包到 4 096（**纯格式转换**）
         │   └► v12     471.7M  ← v10 + strip_think
         └► v13       552.3M  ← v9 重切 2048 + R1 全 CoT(147.9M) + wiki(118.9M)  【当前在用】
```

**关系判定（有据）**：

- `v11` / `v11_4k` 的 `meta.json` 原文写着 `"source": "v10 re-pack to 8K"`，`train_tokens` 与 v10 只差 0.2%（442.5 M vs 442.3 M）——**同一份 token 流换了 `row_len`**，无新内容。
- `v13` 的构建脚本 `build_chat_mix_v13.py` 第 34–54 行 `reslice()` 直接读 `chat_pack_v9/{train,val}.ids.npy` 展平重切——**v13 的 280.6 M 基座就是 v9 的 280.6 M**。
- `v12` 与 `v10` 的 `prompt_tokens` 完全相同（144,457,677）、`plain_tokens` 完全相同（32,846,848），只有 `reply_tokens` 差 11.1 M——**v12 = v10 去掉 `<think>` 段**。
- 因此 12 个 pack 合计 **3,976.2 M token 中，唯一内容 ≈ 552.3 M，重复系数 7.2×**，约 **3.42 B token（≈10 GB，12 个包实测占 11.5 GiB）是纯重复**。

**处置建议**：除 `chat_pack_v13` 外全部可视为归档；`v11`/`v11_4k`/`v12`/`v9`/`v10` 有明确的新信息量（窗口长度、think 处理），可作为"不同窗口的实验对照"，但不应再被当作新语料计入配比。

### 2.1 v13 的实际构成（`wcode` 直方图，实测）

| wcode | 含义 | token | 占比 |
|---|---|---:|---:|
| 0 | pad（浪费） | 16,126,035 | **2.9%** |
| 1 | reply（**进入 loss**） | 358,896,326 | **65.0%** |
| 2 | prompt（不计算 loss） | 144,461,792 | 26.2% |
| 3 | plain（纯文本，计算 loss） | 32,846,336 | **5.9%** |

> 对照：v9 的 reply 只占 37.0%、plain 占 11.7%；v10/v12 的 pad 高达 8.3%/8.5%。v13 的 pad 比例最低（2.9%），是这 12 个包里打包效率最高的。

**这条是"知识 0.000"的直接解释**：5 轮训练里，模型见到的连续自然文本只有 `32.8 M × 5 = 164 M` token；而 reply 部分（对话/问答/CoT）被重复了 `1.79 B` 次。参数 0.5 B 的模型想记住事实，需要**十亿量级**的连续文本，164 M 差两个数量级。

### 4.4 分词代价

实测吞吐（取自各 `meta.json` 的 `sec` / `tokens`）：

| 场景 | 实测吞吐 | 例 |
|---|---:|---|
| 小文件（已读进页缓存）+ 短样本 | **0.9–1.35 M tok/s** | v13 的 r1：147.9 M / 155 s；i_wonder_why：118.9 M / 96.7 s |
| 中等文件 | 0.2–0.4 M tok/s | haruhi_expand 43.1 M / 185.6 s |
| 超大文件（必须整文件顺序读） | **0.014–0.04 M tok/s** | refined_anime 1.79 GB 只出 15.0 M token，耗时 **1,057.8 s**；moegirlpedia 780 MB / 324.8 s |

**结论**：4.04 B token 的文本池，按 0.2–1.2 M tok/s 混合估算 → **约 1.5–5 小时单进程**；瓶颈是 JSON 解析与 15.9 GB 顺序读，不是 BPE（BPE 本身 ~1 M tok/s）。
产出磁盘：int16 ids **8.1 GB** + uint8 wcode **4.0 GB**（若再存 `_plain` 变体另加 4 GB）。
若只做一次 `--r1_max_chars 4000` 式的合理截断，实际可压缩到 2.5–3 B token / 40–60 分钟。

### 5.2 三个"完全没有"

1. **代码：0 条、0 token。**
   唯一的间接来源是 `cosmopedia`（英文合成教科书，抽样 0.7 个 code marker/千字符）和 `pretrain_merged` 90% 偏移处的少量教材代码块。按 0.7/1000 字符 × 403 M token 粗估，**代码类 token < 3 M，占比 <0.1%**。
   `docs/05_数据源档案.md:102` 记录过尝试：`smollm-corpus (python-edu)` —— "仅 blob 引用无文本，无法流式"，**失败未获取**。
   → 这是"编码 0.000"的根因，且**现有素材无法弥补**，必须外部引入（The Stack / StarCoder / Python-Edu / CodeContests 之一）。

2. **中文数学：0 条专用语料。**
   `open_web_math` 是真数学，但 **ASCII 占比 98–100%，纯英文**。中文数学只存在于 `r1_110k_sft` 的题目里，而那份已经 100% 进 v13 且被重复 5 遍。
   → "数学"如果想涨，需要中文数学题库（如 `Math23K`/`CMATH`/`MetaMath-zh`）或英文数学 + 混训。

3. **中文百科式连续文本没进 loss。**
   `wikipedia_zh` 203 M 就躺在 `pretrain_v2` 里，**一次都没被训练过**；v13 里的知识全部以"问答对"形式出现（i_wonder_why 120 M），模型学到的是"问-答映射"而不是"世界知识"。

| 缺口 | 严重度 | 说明 |
|---|---|---|
| **代码语料** | 🔴 致命 | 0 token。无代码则"编码"永远 0。最小可行：`python-edu` 或 The Stack 的 Python 子集 50–100 M token |

### 6.3 三条硬提醒

1. **训练量本身才是主要瓶颈**：0.5 B 参数 × 5.5 token/参数。即使把 4 B 预训练流全接进来，也只到 ~8 token/参数（Chinchilla 的 40%）。**先解决"喂进去多少"，再解决"喂什么"。**
2. **不要再加 R1 切片**：`r1_110k_sft` 的 147.9 M 已经 100% 在 v13 里、重复 5 遍（740 M 次曝光）。推理分数上不去更可能是 token 预算不够，不是 CoT 数据不够。
3. **v13 的 pad 占 2.9%（16.1 M token）**，`wcode==0` 的位置应当从 loss 里排掉；若当前训练脚本没有按 wcode 掩码，这 16 M 是纯噪声。**建议核对训练脚本是否真的用了 `wcode`。**
