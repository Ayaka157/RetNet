# 2026-08-27

## RetNet Kaggle TPU 训练 f32/bf16 精度报错根因分析

目标：定位 `retnet-kaggle-train-8k (8).ipynb` 在 TPU v5e-8 上 cell-6 报 "f32 和 bf16 精度不同"（形状 [4,16,64,128] = scan 的 recurrence carry/state）的根因，并尽量在静态分析阶段修复。

### 关键源码证据（pytorch/xla master，已用 GitHub MCP 核对）
- `torch_xla/csrc/autocast_mode.cpp`：TPU autocast 三档策略：
  - `lower_precision_fp`（保持 bf16）：conv*/bmm/mm/addmm/linear/matmul/einsum 等。**不含 layer_norm / group_norm / gelu / silu。**
  - `fp32`（提升）：batch_norm、_softmax/log_softmax、pow(Tensor_Scalar)、cross_entropy_loss/nll_loss/mse_loss 等 loss。
  - `promote`：stack/cat/index_copy。
  - ⇒ 结论：TPU 上 norm/gelu/silu/matmul **不会**被 autocast 提升到 fp32。
- `torch_xla/experimental/scan.py`：`value_and_grad_partitioned` 用 `torch.empty_like(v, dtype=v.dtype)` 造 fake 张量，`with torch.enable_grad()` 跟踪（**不禁用 autocast**）；`_scan_impl_flat` 用 `xb.create_placeholder_tensor(v.shape, v.dtype)` + `builder.add_param(val)` 给 fn_computation 与 While 参数定型，全文不引用 autocast。scan 的 carry 形状 = init 张量形状。

### previous_analysis 的两处瑕疵（已指出）
1. 它断言 "autocast 把 fp32 提升 cast 注入 scan 递归状态边界（经由 norm）"——但 TPU autocast 根本不提升 norm，机制不成立（未经 C++ 验证的猜测）。
2. 它自承静态分析找不到那个 fp32×bf16 的 matmul（§7），最终含糊归因为 "XLA autocast 非标准行为"。

### 真正机制
报错是 scan 的 XLA `While` 里 `call fn_computation` 的参数 dtype 与 fn_computation 形参 dtype 不一致（HLO verifier 拒绝）。唯一 [4,16,64,128] 形状的操作数是 recurrence carry/state：
- 当前磁盘代码里 `state` 已显式 `dtype=torch.bfloat16`（line 234）、`chunk_decay = (gamma ** chunk_size).to(bf16)`（line 249）已中和唯一的 pow.Tensor_Scalar 提升。scan body 与所有 xs 都是 bf16 → 静态看 scan 路径本身一致。
- 因此残留/顽固错误来自 `torch.autocast("xla")` 包裹 `model(...)` → scan 被包在 autocast 内，而 scan 的 AOTAutograd 跟踪与 `_scan_impl_flat` 的 XLA LoweringContext 重跟踪是两条独立的 trace 通道，autocast 的 cast 注入在这两条通道间可能不一致，制造 carry 的 f32/bf16 签名边界。这是官方未处理的边界情况。

### 修复
- 生成 `retnet-kaggle-train-8k (fixed).ipynb`：删除 train_worker 训练循环与 evaluate 里的两处 `with torch.autocast(device_type="xla", dtype=torch.bfloat16):` 包裹（autocast 在 XLA 上冗余：`XLA_USE_BF16=1` + `model.to(bf16)` + `set_default_dtype(bf16)` 已使整图 bf16）。
- 保留：`logits.float()` + `F.cross_entropy`（唯一 fp32 路径，梯度自动 cast 回 bf16）、scan body 内所有 `.to(bf16)` 防御性转换。
- 实测需在 TPU 上跑验证（开 TPU 排队，故仅静态修复）。

## 第二轮：GLA 修复 + 手动混合精度（最终版）

用户要求：修 GLA 未启用 bug、改手动混合精度（不用 autocast）、删冗余 .to(bf16)，产出报告+最终版。

### GLA bug 根因（已证实）
- checkpoint `blocks.N.msr.gamma` 是 **F32 [16]**；但代码 `gamma.to(bfloat16)` 存储 + `model.to(bf16)` 强转。
- bf16 在 1.0 附近分辨率仅 2^-8：RetNet decay 谱 `gamma_i=1-2^(-5-i)` 有 **12/16 头塌缩为恰好 1.0**（位运算精确复算；head8 的 gamma**64：fp32=0.9922 vs bf16=1.0）。慢头衰减全失效 + bf16 主权重梯度更新被量化吞掉 → 门控注册了 Parameter 但数值上是死的。
- previous_analysis §6 说"g 门控没接"不准确：`F.silu(g)*output` 输出门控对所有 mode 生效；真 bug 是 bf16 塌缩。

### 最终修复（retnet-kaggle-train-8k-final.ipynb，9 处改动）
- gamma fp32 注册 + model.to(bf16) 后恢复 fp32 主权重（optimizer 创建前）；decay 四件套/norm/loss 为 fp32 岛屿，边界 cast bf16；scan 入口全 bf16 由构造保证。
- AdamW 按 ndim 分组：1 维参数（门控/norm/bias）无 weight decay。
- 删除两处 autocast 包裹；删除 scan body 9 处 + xs 7 处 + q/k/v 3 处冗余 cast。
- 验证：autocast=0、全 cell 编译通过、state_dict 键不变（366）。注意：optimizer 分组变化 → 旧 training.pt 不可 resume。
- 报告：`RetNet_TPU_修复分析报告.md`。

## 第三轮：run1 上 TPU 实测仍崩 → 确诊 scan 本身是病根 → final2 弃用 scan

- run1（=final 逐字节）TPU 报错：`parameter 2 shape: f32[4,16,64,64], argument: bf16`（老错是 param0 [4,16,64,128] carry）。位置随 body 变化而移动 → f32 由 scan 内部 trace 机制产生，与模型代码无关。
- scan 边界张量逐一验证全 bf16；`create_placeholder_tensor` 源码确认保 dtype；pytorch/xla issue #7839（While 参数顺序/额外张量映射脆弱）、#8783 佐证 scan 机制不可靠。
- 决策：没有 TPU 环境无法再向机制内部钉，且每试一次烧一次排队 → **final2 弃用 `torch_xla.experimental.scan`，改普通 Python chunk 循环**（逐运算等价），走标准惰性张量 trace 路径。
- 展开 128×20 → 必须开逐 block 梯度检查点（`_block.gradient_checkpointing = True`，否则 ~0.6GB/层×20 必 OOM）；首步编译时间显著变长（一次性）。
- 产物：`retnet-kaggle-train-8k-final2.ipynb`（S1-S5 改动），报告已加 run1 复盘章节。
- 教训：torch_xla.experimental.scan 在此栈（bf16 + RetNet chunkwise）不可用；autocast 移除、GLA fp32 门控、手动混合精度等 final 的改动在 final2 中全部保留。

## 第四轮：上游定性（用户要求记入报告，不提交 issue）

- 拉取 pytorch/xla 上游 issue 实锤：scan/while-loop 的参数映射脆弱是**已知且未修复**缺陷。
  - #7839 "While loop can't yet handle additional tensors"（2024-08-12 开，维护者亲自报告，逾 2 年未修）— 直接描述额外张量被 trace 成额外 parameter、参数顺序/类型映射不可靠，正是 ki 形参被错标 f32 的机制。
  - #8918 "Standardize XLA loop APIs"（2025-04-01）— 官方计划重写/统一 scan/while-loop/fori-loop，**不做热修**当前 scan。
  - #8783 "scan forces inputs to be differentiable"（PR #9083 未合）；#9405（已关，确认 scan 依赖 AOTAutograd、非 aten op 不支持）。
- 结论：框架层陈年老 bug，用户侧无法根治（调 dtype/cast/autocast/fp32 decay 均无效，报错随 body 漂移）；唯一出路是绕开 scan（final2 已做）。
- **用户决策：不提交新 issue**（#7839 已覆盖，f32/bf16 变体不值得另开）。已把上述引用 + "不可修复/不提交" 定性写进 `RetNet_TPU_修复分析报告.md` §-1「上游定性」块，并给 §1 原崩溃回顾补了"必要条件非充分条件"免责说明。
